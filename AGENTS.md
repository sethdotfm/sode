# Sode — notes for agents

Keyboard-first web patching for one SW-P-08 router (Ross Ultrix). User-facing settings table and protocol summary: README.md.

## Commands

```sh
go test ./...        # all tests (the Dockerfile build runs them too)
go vet ./...
go test ./internal/app -run TestWaiterAlreadyRouted -v   # one test
node --test 'web/test/*.test.mjs'                        # browser-side tests (filter language, histRows, imports)

go run ./cmd/swp08sim                                    # simulator on :8910, see SIM_* in cmd/swp08sim and README
SODE_ROUTER=127.0.0.1:8910 SODE_DEBUG=true go run ./cmd/sode   # :8080; SODE_DEBUG hex-dumps SW-P-08
docker compose --profile sim up --build                  # server + simulator
```

Without `SODE_CONFIG`, config comes from `SODE_*` env and is not persisted. The web UI is embedded with `go:embed` (`web/web.go`): restart after frontend edits.

## Key decisions

- Go, stdlib-first. Only deps: coder/websocket, yaml.v3. Distroless static image, HTTP :8080 (TLS is the user's proxy). Keep it light: no frameworks, no new deps without asking.
- SW-P-08 over TCP to one router, **single matrix**, always **extended** commands (16-bit src/dst). Protects are honored. Auto-reconnect + keepalive. Names come from the router, re-polled (default 60s).
- Levels: wire = level + configurable offset. Internally levels are UI 1..N everywhere (history, `defaultLevels`); `levelNumbering` (`1` / `0` / `va`) only changes display (`Level.Label` from `LevelMap`) and typing (`parseLevels` in `levelview.js`). `levelTypedBase` is a dropped setting kept so old files load (`KnownFields`). No free-text level names (removed at the user's request).
- Config: `/data/config.yaml`, edited in the Settings dialog; `SODE_*` env only seeds the file on first start. Save writes and stays open; Exit/Esc/Back with unsaved server settings warns once, a second try discards.
  - Settings PIN: PBKDF2 hash in `settingsPin` (`json:"-"`, never sent to browsers; `SaveSettings` carries it over). Unlock is per WebSocket connection *for that hash* (changing/removing the PIN relocks everyone) and relocks when Settings closes. `unlock` is handled in line in the read loop so a following `lock` wins. Wrong PINs are counted globally, one check at a time, waits double from 30s after the 5th, `pinMaxTries` (default 10, 0 = never) locks until `-reset-pin` or restart. A non-hash `settingsPin` stops startup. `SaveSettings` runs one at a time (`cfgMu`) and re-checks the lock.
  - Device defaults (#49): `deviceDefaults` (`config.DeviceDefaults`: theme, layout, clock, flip, scrollTop, searchFilters, setStack, nextMode) is what "This device" follows until a browser chooses its own. Not router-side, so saving never reconnects. A browser's value is a localStorage string (`sode-theme`, `sode-layout`, `sode-clock`, `sode-flip`, `sode-scroll-top`, `sode-search-filters`, `sode-set-stack`, `sode-next-mode`); missing/unknown = "Global". `resolve()` in `web/prefs.js` (pure, Node-tested): own value, then global default, then built-in. `device.js` `pref(name)`/`setPref(name, v)` (`''` removes) are the only readers/writers; `applyPrefs` re-applies live and emits `prefs`. The last global defaults are cached in `localStorage['sode-device-defaults']` on every `hello` so index.html's pre-paint script (and log.html's, theme only) follows them; that script is the one classic `web/prepaint.js` (loaded synchronously in each page's `<head>`; the other pages pass `data-only="theme"`) and repeats `resolve()` inline, keep the two in step.
- **Settings search**: the box above `#settings-toc` (end of `settings.js`) searches an index built from the page's fieldsets and their labels (`label[for]`, `.sode__field-label[id]`, `.pb-check`, `[data-find][data-label]` for anything else, e.g. buttons). `web/settingsindex.js` is pure (Node-tested, has its own scorer, not `core.js` `search`): `buildIndex`, `find`, and `DICT`, the words people type, keyed by section slug (legend text, e.g. `this-device`) and by control id; unknown ids are ignored. **A new settings section must add its slug to `DICT`; `settingsindex.test.mjs` fails otherwise.** Add terms for new settings too. Esc in the box clears it first (stopped there), the next Esc leaves Settings; its input events don't reach the form (so the unsaved warning stays). The Communication Log link is in Settings > History; the bottom `.sode__open-log` link only shows while Settings are locked.
- Frontend: vanilla JS ES modules, no build step. Follow patchbay rules exactly (https://github.com/sethdotfm/patchbay llms.txt): pb- classes only, tokens only, no Bootstrap utilities, no border-radius, status always with text. Patchbay is vendored under `web/vendor/patchbay`; copy missing icons from upstream, don't fake them. Vendored version is in `web/vendor/patchbay/VERSION` (v2.1.0; upgrade guide: upstream `transition.md`). Rules from v2: the whole UI scales with `html { font-size: 125% }` (phone 100%), never `zoom`; sizes in rem; numbers use `--pb-font-num` (set to Sans here), `--pb-font-mono` is real mono for code/hex; no per-theme CSS, tokens switch themselves; tooltips are `data-pb-tip` (+ `pb-tip--end`), the script-placed cut-off tip is `.pb-tip`; green buttons are `pb-btn--ok`; icon-only ghost buttons need `pb-btn--icon`; `layout.js` sets `data-pb-layout="phone"` next to `data-layout`.
- Users never ride the `hello` (it goes to locked pages too): `hello()` blanks `cfg.users`. Names come in `lockState.names` (only when the page isn't locked; `S.userNames`), PIN lengths in `lockState.lens` for everyone, and the Users editor asks `usersList` (needAdmin, reply `usersListResult`). Keep a new user field out of anything sent before unlock.
- Confirm dialog: random churning letter + lockout (default 500ms; Enter optional).
- Version (#95): `Version`/`Stage` in `internal/app/version.go` (`MAJOR.MINOR.PATCH`), sent in `hello` as `BuildLabel()` (with the short `Commit` the Dockerfile injects), shown in Settings, noted in README's `**Version:**` line. **Every release bumps both** and gives `CHANGELOG.md` a section for it (#147); `TestVersionNoted` fails if they differ, or (with `SODE_RELEASE_TAG=v1.5.0` or `v1.5.0-rc.1`) if the tag differs or the heading still says unreleased. Release flow and image tags (`latest` only by `promote.yml`, never by an rc or `edge`): `RELEASING.md`. Nothing may push `latest` except `promote.yml`.

## History, ext and follows

JSONL history plus a shared server-side recent/undo list. Routes made elsewhere are `ext` entries (`ext.go`, split into `ext_burst.go`, `ext_ownership.go`, `ext_follows.go`):
- Connected messages none of our takes sent, plus `found` entries (#57): a tally (resync or interrogate) differing from a *known* cached value that isn't a take in flight or one that just gave up (`awaited`, `late` keys for 5s). Found entries are never follows, are grouped apart from announced ones, and show as `found`.
- `own` holds each take's (dst, wire level, src) for `ownFor`; keys are used up by the router's answer, so the same route made elsewhere right after still logs. Changes are collected into bursts (end after 500ms quiet or 3s total), logged one entry per dst+src; a burst over several dsts shares a `group`.
- **Follows** (#53): an `ext` change of the same src to another dst within 500ms of one of *our* takes (`waiter.cause` → `a.causes`). Of several that fit, the one whose last confirm came latest wins (`followed`). Panel changes are never followed. Followers of a take in a multi-take confirm aren't tied to a destination: they carry `followGroup` and `histRows` lists them as `f.followers` (a Followers row at the bottom of the folder, not in `f.entries`, so Undo all leaves them; desktop keyboard stop `w<group>`). Otherwise the follow is written with `follow` = the take's ID, ungrouped, and `histRows` attaches it as `e.follows` unless filters hide the take. Undo plans carry follows as `plan.extra` (one per dst, the oldest), sent only if the confirm's box is ticked. A burst that might follow a take still in flight waits for it (`extAwaitsTake`), only once its connects went out (`cause.sent`). An undo's confirm flags levels where dst no longer has the undone take's source (`changedSince`; skips `Failed` levels and entries without `Failed`).
- Repeated same-dst/same-levels `ext` entries within 30s merge into one row (newest, oldest's `prev`, `merged` count, `chain`); any other entry on that dst, even hidden, breaks the chain. `stackSteps` in `widgets.js` shows a stack as a timeline; older steps have Restore (`restorePlan`, `plan.at`).
- `histRows` then applies this browser's Recent filter (`filterstore.js`, `localStorage['sode-filter']`: kinds plus `src`/`dst` expressions). Folders keep every entry in `f.entries` (Undo all covers the whole confirm) and visible ones in `f.shown`.
- Stacked sets (#131): set buttons toggle (`toggleSet`). One set is `sode-filter-active` as ever. Two or more are a stack, `sode-filter-stack` `[{scope,name}]`, with no active set; `filter` is the first one's, each set's saved filter judges an entry by `stackAllows` (`filter.js`, pure) and pref `setStack` says whether all must allow (`and`) or any may (`or`; a set's excludes and kinds count only inside it). `useSets` is the one builder (missing sets drop out, one left is that set, none is All); `setActive` the one writer, which also drops the stack's cached matchers. `setFilter` is the edit path and leaves a stack. `snapshot`/`restore` put set or stack back (share-link Undo). The dialog shows "A + B", edits the first, and turns off Save as and the share link while stacked.
- Filter language: `web/filter.js`, pure, no imports; the server's `hiddenDsts` uses it too and is evaluated only in browsers. Filter sets come from the built-in All, `cfg.filterSets` and `localStorage['sode-filter-sets']`; active one is `sode-filter-active` `{scope, name, base}`; `followGlobal()` on hello applies a changed global set unless the browser edited it. Names unique per scope, ignoring case.
- Quick search (`setSearch`, `[data-search]` boxes): not kept, doesn't merge rows, reads back in 500-entry pages (`history` takes `n`, server caps at 500). Ignores the filter unless `sode-search-filters` is `on`. `web/filters.js`: the dialog, share links (`?f=` base64url JSON, applied and stripped in `main.js`), empty-state note.

- **Redo** (#153): every history row and folder has one Retry/Redo button ("take this line again", `againPlan` in `plans.js`; `againButton` in `widgets.js`). Failed takes retry (linked to their entry, a folder with failures retries just those); every other row redoes: src to dst on its levels as a plain new take, including undo, ext/found and follow rows. Skipped only with no real source or no existing level (`canRedo`). Frontend only. Undo, Redo and Retry are all outlined `pb-btn--sm` buttons; Undo carries `undo-2` and Redo `redo-2` as a mirrored pair, Retry is text only. The phone's swipe-reveal Undo (`sode-m__undo`) hides the icon in CSS. Verb wording lives in `VERBS` (`plans.js`); only a `patch` resets the boxes (`VERBS[verb].resets`; `preset` is a verb too). The confirm shows "Already there" (`alreadyThere`, from the tally) when dst already has the source on every level. Desktop keyboard mode: `r` does whatever the button says.

## Shared saves and owned fields

- Filter sets and presets save through one path: `saveShared` (`app/shared.go`: takes `cfgMu`, `guardSave(c, true)` re-checks the settings PIN or a trusted user inside it (the policy table checked it on arrival; the main lock does not cover settings), `update` mutates a copy then Normalize+Validate+save, optional broadcast of one small message, not a hello) and `replyOp(c, kind, id, n, noun, err)` (logs the command as `kind`, answers `<kind>Result` echoing `id`, sets `locked`). New "saved apart from Settings" features use both. The name rules (count, empty, 32 runes, unique ignoring case) are `validateNames` in `config/names.go`.
- **Owned fields**: Config fields saved outside the Settings form carry the tag `owned:"true"` (filterSets, presets, settingsPin, deviceDefaults, users). A Settings save (`saveSettings`) does `cur.KeepOwned(live)` (reflection, `config/owned.go`), so a stale or huge browser copy can never change them; only the PIN dialog and `keepDefaults` handle the PIN and device defaults after that. A field the form saves instead carries `guard:"router|pin|open"`: `router` (reconnects; `applyConfig` asks `config.Changed(old, c, "router")`), `pin` (only the settings PIN may change it) or `open`. `TestEveryFieldChooses` fails if a new Config field has neither tag, so adding a field forces the choice. The Settings dialog also strips owned lists from its `config` message (the socket read limit is `wsReadLimit`, 64 KiB; `TestMessageSizes`, `TestSettingsIgnoresOwned`).

Grid (full-page button panels at `/grid/<link>`) is parked on branch `archive/grids` (issue #150); `grids:` and `gridConfirm:` in an old config.yaml still load and are ignored.

## Users and locks (#151)

Optional and off by default (no users, no locks = nothing changes). `cfg.Users` `[{name, pin hash (json:"-"), len, trusted, persistent}]` (`config/users.go`, <=12, unique names ignoring case, PINs 4-12 digits and unique across users), `cfg.Locks{main,log}`, `cfg.AutoLockMinutes`. A lock needs >=1 user and a settings PIN (`Validate`; `-reset-pin` turns locks off). The user list (and `maxPinLen`) is saved only by the `users` message (`SaveUsers`), which needs a settings PIN to exist and the connection settings-unlocked (a trusted user is NOT enough); `saveSettings` carries it over, like `settingsPin`. **Locks and auto-lock are ordinary Settings fields** (Settings > Access, saved by the main Save) tagged `guard:"pin"`: only the settings PIN may change them (`trustedMayNotChange`, `guardedErr`), and a `config` message WITHOUT a `locks` / `autoLockMinutes` key keeps the live values (`configMsg` records presence; a missing key must never read as every lock off). They are top-level config keys (YAML and JSON) that browsers read, not one struct; web `GUARDED` in `lockrules.js` mirrors the tag.
- **Policy table** (`internal/app/policy.go`): ONE map from every client-to-server message type to what it needs, checked once by `admit` before the read loop's `switch` runs, and closed: a type not in the table is dropped. `TestPolicyCoversEveryMessage` parses `http.go` and fails if a `case` is missing from the table (or the table lists a type the loop doesn't handle). The table is written out one line per type in the file's header comment. Needs: `open` (`hi`, `userUnlock`, `userLock`, `userSetPin`, `unlock`, `lock`, `history`; each has a comment saying why), `needTake` (`batch`: the main lock), `needMain` (`refreshNames`; `clearHistory` also `needAdmin`), `needLog` (`sent`, `uptime`; admitting `sent` sets `c.sent` in the same step under `mu`), `needAdmin` (`users`, and `clearHistory`: the settings PIN unlocked when one is set, **and not the main lock**: a locked wall panel, which has no lock screen, must still be able to save with the PIN), `needTrusted` (`config`, `filterSets`, `presets`: the settings PIN unlocked, OR the connection unlocked as a user who still exists with the same PIN hash AND is `Trusted` *now* in the live config (`trustedLocked`, so unticking takes effect at once, a changed PIN relocks)). `config` is `needTrusted` unless the message carries `pin` or `clearPin` (`rule.strict`, applied by `rule.forMsg` in the read loop): then it is `needAdmin`, so a trusted user can't set, change or clear the settings PIN. `guardSave(c, trusted)` repeats the check under `cfgMu` (`saveSettings` passes `trusted=false` when pin/clearPin are set). A refusal logs a `locked` command and answers the same way everywhere: `lockState` for a page lock, the `locked` message for a settings PIN, and for a type with a result a failure echoing the id (`<op>Result` with `locked`; a refused `batch` gets a failed `takeResult` per item).
- **What the locks cover**: the main and log locks cover *actions and log reads*, not data. `hello`, names, tally, recent history and history reads keep streaming to a locked browser by design (the lock screen hides the page, it isn't a secret). Main lock: `batch`, `refreshNames`, `clearHistory`. Log lock: reading the sent log and uptime graph. The page declares its type with `hi` (`{page, token}`, sent on every new socket by `lock.js`; default `main`); `/healthz` and `/api/health` stay open. History `Client`, `Why.By` and event `By` use `c.who()` (user name, else IP).
- **Access state** (`users.go`): `client.u` is a `connUser` (page, session token under `mu`; the unlocked `*config.User` in one `atomic.Pointer`, so `who()` needs no lock). `pageAllowed(c, gate)` is true when the gate's lock is off or the connection is an unlocked user who still exists with the same PIN hash (a removed user or changed PIN relocks). `settingsUnlocked(c)` is the settings PIN; `trustedLocked(c)` is PIN or trusted user. `...Locked` always means "caller holds `mu`". `syncAccess(c)` sends the lock state (`user`, `trusted`, `persistent`, read from the live config) and, as its explicit side effect, stops the sent feed for a connection no longer allowed it.
- **PIN pools** (`pin.go`): `pinPool{state, wait, maxTries, resetOnOK, forget, what}` and ONE method, `tryPin(pool, from, check)`, which takes and releases `mu` itself. Two pools: `a.pin` (settings PIN): waits double from 30s after the 5th wrong try, up to an hour, and `pinMaxTries` locks it for good; `a.userPin` (user PINs, `userUnlock`): the same waits capped at 5 minutes, no permanent lock, and a right PIN does NOT reset the count (a PIN says who typed it, so a holder of one valid PIN could otherwise guess the rest without end): the count is forgotten after an hour (`forget`) with no wrong PIN. The settings pool starts over on a right one (`resetOnOK`). A success or lockout in one never touches the other. PIN only, no name; a PIN of a length no user has is just a wrong try (the page's `sendDelay` only sends lengths some user has).
- **Persistent sessions** (`tokens.go`, user flag `persistent`, "Never log out"): `userUnlock` for a persistent user also issues a token (`issueSession`, after the unlock; disk I/O never under `mu`): 32 bytes of crypto/rand, base64url; only its sha256 is kept, in memory and in `tokens.json` beside the config (0600, atomic, loaded once in `New`). A record is `{user, pin hash, at}`; `tokenStore.user(t, cfg)` re-reads the live user on every use, so a changed PIN, a removed/renamed user or an unticked Persistent kills the token at once, whatever the file holds. At most `perUserTokens` (8) per user, the oldest dropped; `issue` also prunes dead ones. The result is `userUnlockResult.token`; the browser keeps it in `localStorage['sode-session']` and sends it in `hi`; a valid one brings the connection up unlocked as that user with no PIN (a wrong one is ignored: the normal pad). `lockState` carries `persistent`, so the page's idle timer skips that session (`idleLock`); the server stays the authority. `userLock` ALWAYS revokes the connection's token (and relocks other connections holding the same token, i.e. other tabs of that browser), so Lock, Log out and Ctrl+L can't be undone by a reload. A non-persistent user is exactly as before: idle timer, reconnect asks for the PIN again. An old `tokens.json` of admin tokens (`{pin, at}`, no user) loads as nothing; a damaged file is forgotten.
  - **Catching up (#159)**: a token is otherwise issued only when the PIN is typed, so a user already logged in when Never log out was ticked, or who just changed their own PIN (which kills their old tokens), would be asked for the PIN again at the next reload. `catchUpSessions` (end of `applyConfig` and `UserSetPin`, off `mu`) gives every connection unlocked as a persistent user that holds no good token one, sent as `{t:"session", token}`; `lock.js` keeps it while the page is logged in. `issueSession` is idempotent and drops its token if the connection was locked, or given a good one by a racing call, while the file was written. Each tab of a browser that is already in gets its own token this way (they share the 8-per-user cap).
  - **localStorage, not a cookie**: the WebSocket `hi` already carries the token, so no HTTP endpoint (`POST /api/session`), cookie flags (SameSite=Strict, Secure only over https behind the user's proxy) or CSRF/Origin thinking is needed. Trade-off: a cookie could be HttpOnly (unreadable to script), which localStorage can't be; but the page builds all router-supplied text with `el()` (no `innerHTML`), the token only works as that user's session, and a server-side cap and revoke exist. Either way it is as strong as the browser profile: whoever can read it is that user.
- **Hardening (fix/trusted-hardening)**: revocation is durable: `tokenStore.prune(cfg)` deletes every record invalid against the live config, run at the end of `a.update` (so after every config apply, `SaveUsers`, `UserSetPin`, filter sets...) and in `New`; untick/re-tick Persistent, rename A->B->A or a PIN changed and restored never revive a token. Tokens die after `tokenMaxAge` (90 days) unused: a `hi` with the token, or its connection still being open (`touchSessions`, hourly from `periodic`; `tokenStore.touch` rewrites a token only when over a day old), renews it, so a wall panel that never reloads stays signed in. `userSignOutAll {name, id}` (`needAdmin`, `SignOutAll`, button per user in Settings > Users) deletes a user's tokens and relocks their connections. `UserUnlock` clears the connection's token (token as X then PIN as Y must not carry X's token). `tokens.json` is written via `os.CreateTemp` in the same dir, 0600, fsync, rename, dir sync. A trusted-only Settings save may not change `router`, `trustedProxies` or `pinMaxTries` (`trustedMayNotChange`; error `guardedErr`, which counts as `errLocked`, so the page asks for the PIN; `guardedEdited` in `lockrules.js` makes settings.js ask up front); only the settings PIN may. **CSP**: `secureHeaders` in `http.go` sets one Content-Security-Policy (`script-src 'self'`, styles allow inline attributes, `frame-ancestors 'none'`), `nosniff` and `Referrer-Policy: same-origin` on every response; pages must have no inline script bodies, `on*=` handlers or `javascript:` URLs (`TestNoInlineScript`; the two forms' `onsubmit` became a listener in `core.js`).
- **Trusted users**: the flag lets a connection unlocked as that user make LOW-RISK saves with no settings PIN (Settings form, `filterSets`, `presets`). Still the settings PIN, trusted or not: `clearHistory`, any Settings-form field whose `guard` is `router` or `pin` (`trustedMayNotChange` via `config.Changed`, on the normalized value; refused with `guardedErr`, which counts as `errLocked`), `users` (users, maxPinLen), and any change to the settings PIN itself. The server sends `trusted` in `lockState`, as well as `lens` (the PIN lengths users have, so every lock pad follows a PIN change) and `hi` (set only on the answer to the page's own `hi`: `lock.js` forgets its session token only on that one, never on an unsolicited state); web `pin.js` keeps it (`trusted()`, fed by lock.js's `access` event) and `needsPin()` (`lockrules.needsPin`, pure, Node-tested) is what Settings (`renderLock`) and `globalsave.js` ask instead of `S.pinSet && !unlocked()`. This only hides the prompt: when the server refuses (`locked`/`locked: true`), `demandPin()` makes `needsPin` true again until the PIN is entered or Settings close/relock, so Clear history, Users saves and PIN changes (settings.js asks up front when the PIN fields are used) show the normal PIN prompt.
- **Removed (the admin browser)**: the `adminUnlock` message and policy entry, the lock screen's admin-password sign-in, "Forget this browser", "Never auto-lock this browser" (`sode-lock-never`), `userLock {suspend}` / `connUser.suspended`, `exempt` in `lockState`, the "admin" chip/welcome text, and old admin tokens (dropped on load). `lock.js` deletes the old `sode-lock-token`/`sode-lock-never` keys. A wall panel now logs in once as a trusted + persistent user.
- **Frontend**: `lock.js` (overlay, `lockState`/`userUnlockResult` via `onMsg`, Ctrl+L, idle timer; emits `locking` as it comes down, which `settings.js` answers by exiting, `unlocked`, which `log.js` uses to ask again, and `access` with the lock state, which `pin.js` and `settings.js` use; remembers the focused element and restores it), `lockrules.js` (pure, Node-tested), `lock.css`, `users.js` (#165/#168: Settings > Users is a one-line summary ("3 users · main screen locked") and a "Manage users…" button (`#users-manage`, `data-find`, DICT `users-manage`); the editor is its own `pb-modal` with `trapDialog`: one row per user (name, PIN, Trusted, Never log out, Sign out everywhere, Remove), then lock main, lock log, auto-lock minutes, longest PIN, its own Cancel/Save. It asks `usersList`, saves with `users` and closes on success, shows the server's error text, calls `demandPin()` on a locked refusal; it holds no rules. Esc/Cancel with edits warns once, the second try discards; `locking` closes it. Holds no inputs in the Settings form, so the unsaved-changes check never sees it). Modals other than Settings are still closed by `lock.js` clicking their Cancel/Close (a fallback until they listen for `locking`).
- **Lock polish** (feat/lock-polish):
  - **Chip** (`lockchip.js`, built with `el()`): "Logged in as <name>" fixed at the TOP LEFT, below the lost-link banner (`--sode-down-h`); on the phone under the fixed header (`--sode-head-h`, measured in `lock.js`). The bottom-left shortcut tip is never covered. One icon-only lock button (`icon('lock')`, `data-pb-tip` "Lock (Ctrl+L)"); no menu. **Account block** (index.html, inside This device, hidden unless `access` says a user is logged in; found by Settings search via `data-find`, DICT `account`, `account-pin`, `account-logout`): "Logged in as <name>", Change my PIN (bus `changePin`, the dialog lives in `lockchip.js`) and Log out (bus `logout`: ends the session, revokes the token, shows the pad; the explicit way out for a persistent user).
  - **Animation**: the logo's move is the Web Animations API (`moveBrand`, `brandFrames` in `lockrules.js`): one run each, brand at rest when measured, fresh keyframes every time, so it restarts however soon after the last. The way out lasts `OUT_FACTOR` (1.5, `--sode-lock-out` in CSS) times the way in: the brand holds, then fades over the last 45%; the overlay's own transitions use the slow duration when going away; the pad body fades in after half the motion and out at once; the root is hidden after the longest plus 100ms. Reduced motion = no animation (no fade, no shake; the text still shows).
  - **Pad feedback** (`feedback`/`clearFeedback` in `lock.js`, `wrongFeedback` in `lockrules.js`): the dots field itself changes. Correct PIN: it says "Welcome, <name>" (short fade) and the unlock runs after `WELCOME_MS` (600ms; keys are ignored meanwhile). Wrong PIN: it shakes (WAAPI, restarts every time) and says "Incorrect" for `WRONG_MS` (1s), then the dots return; a wait note from the server goes under it, and other refusals (too many wrong PINs, lockout) stay whole in the field until the next key. Text always carries the status.
  - **Scroll**: the page keeps its scroll through lock and unlock (`preventScroll` focus, `data-sode-lock` on `<html>` stops desktop.js's focus-scroll, the position is restored). `shouldFly(rect, scrollY, innerHeight)`: the logo flies only for an unscrolled page whose logo is fully in view; otherwise brand and overlay just fade.
  - **PIN pad**: submits by itself only at the LONGEST length in use (`sendDelay` is null for shorter ones, so a pause after 4 digits never sends 1234 when 12345 exists). The check key (spanning the pad) and Enter send what is typed if a user has that length (`sendable`). The pad stops at `min(longest, maxPinLen)`.
  - **maxPinLen** (`config.MaxPinLen`, `SODE_MAX_PIN_LEN` seeds first start, default 8, 4-12, owned: saved by `users` with `usersReq.maxPinLen`, 0 keeps). `Validate` rejects users whose `len` is above it; an older file without it gets max(8, longest user PIN) in `Normalize`. `CheckUserPinRules(pin, max)`.

  - **Who made it**: Sode takes by a configured user show a small "by <name>" (`byLabel` in `widgets.js`, `actorUser`/`folderActor` in `lockrules.js`) in the route cell (desktop) or route line (phone); never an address; ext/found show nothing; a folder shows it when all its takes share one user.

The page keeps it in sessionStorage (`sode-tab-session`; closing the tab logs out), sends it in `hi` (`hiToken`). No idle lock; Log out and `userLock` revoke it. Persistent users are unchanged. The hand lock screen has a small **Log in as…** (`loginAsOffered`; users exist and no PIN lock): it ends the hand lock and starts the login (`loginFromSoft`), and Cancel/Esc returns to the hand lock; a successful login releases it. The page's lock view is ONE value (`V = {mode: 'page'|'soft'|'login', back}` in `lock.js`, with the pure transitions `softLock`, `softUnlock`, `startLogin`, `cancelLogin`, `lockArrived`, `loginWon` and `viewBody` in `lockrules.js`); a `lockState` ends a login only on a real unlock (`unlocked`) or an enforced lock. `lock.js` emits `handlock {on}` when the hand lock (or any lock overlay) goes up or down, which `transfer.js` uses for the share sheet. The "Logged in as" chip stays up (above the overlay) while the hand lock is up.
- **Hand lock (#158)**: where no PIN lock is on for the page (`!L.enforced`) Ctrl+L, or Settings > This device > Lock screen (`#soft-lock`, bus `softLock`, hidden when `access` says enforced), puts up the lock overlay with its second body (`softBody`): "Press X to unlock" with a churning letter (`churnKey` in `lockrules.js`, the same as the take confirm's, which `keyconfirm.js` now uses too) and an Unlock button for touch screens. It waits out the confirm lockout (`lockout.js`, split from `widgets.js`, which re-exports it) and honours `confirmEnter`. Purely this page's state (`soft` in `lock.js`): no server message, no PIN, a reload clears it. While it is up the capture keydown handler stops every key from reaching the page (`stopImmediatePropagation`; chords like reload and copy are left to the browser, so Ctrl+Z can't undo a take underneath). The idle timer puts it up after `autoLockMinutes` (`softIdleLock`, only where no PIN lock is on). An enforced lock arriving (`lockState`) cancels it. It is a guard against mashing, not security.
- Not done: idle lock is client-side (a persistent user skips it); a non-persistent user's reconnect asks for the PIN again.

## Profiles (#161), guests (#187) and sharing (#169)

A **profile** is a user's own saved This device settings, filter sets and presets, kept on the server so they follow that person to any browser. Third scope **Me**, beside Everyone (`global`) and This browser (`local`). Only exists where users do: no users, or nobody logged in = no Me options, wording or buttons anywhere, and a guest gets this browser's and everyone's values.
- **Config**: `User.Profile` (`config/profile.go`: `Prefs` map of pref name to value string as in `web/prefs.js`, `FilterSets`, `Presets`; `json:"-"` on the user, so it never rides the `hello`). Normalize drops unknown prefs, Validate reuses the preset/filter/name rules, and a whole profile is capped at `MaxProfileBytes` (48 KiB as JSON) so a save fits the 64 KiB socket. `TestPrefTable` compares the Go pref table with `prefs.js`. `SaveUsers` carries a profile over by `Was` (rename keeps it); a removed user's is dropped.

The command log notes whose profile and how many items, never values.

## Communication Log (#72, `/log`)

Every message written to the router, captured at the wire, plus event rows (#139, below). `swp08.Client.OnTx` fires once per message from `transmit` (after ACK/NAK/give-up, with `Tries`) or for messages still queued when a session ends (`dropped`); `sendMsg` logs `unsent` when `Send` refuses. Each `Send` carries a `swp08.Why`. `OnTx` only pushes onto `txq` (never blocks the ACK-gated writer); `logSent` decodes (`swp08.DescribeTx`), appends to `SentLog` (`sentlog.go`: JSONL with its own `seq`, rotated to `.1` at half of `SODE_SENTLOG_MB`) and queues `sentAdd`/`sentPage` (both carry `total`) for connections that asked (`client.sent`). A failed write keeps its seq unused and isn't broadcast (`txLost`), so seqs have no gaps; a damaged file is renamed `.bad-…`, not fatal. `Send` pushes under `c.mu` and the session drains the queue after the writer exits, so every queued message gets a TxEvent. Read-only, no clear, no PIN. **Events (#139)**: kinds `browser` (WebSocket connect/disconnect, `By` = IP), `command` (batch as take/undo/retry, refreshNames, clearHistory, config, filterSets, unlock ok/refused, lock; never a PIN or settings), `link` (router `up`/`down`/`changed`) and `server` (`start`/`stop`). They have `cmd`/`wire`/`dst`/`src` -1 and empty hex (`event()`; the page tells them by `EVENT_KINDS` in `logkinds.js`, not by hex), with `Note` for the detail. `logEvent` only pushes onto `evq`; `logSent` is the single writer of both `txq` and `evq`, so seq, file and live feed agree, and on shutdown it drains both and writes `stop`. `Run` waits for it and `main` waits for `Run` (3s). `logLink` (under `mu`) logs `down` once per outage (again if the error changes) and `up`; `applyConfig` on a router change resets it, logs `changed` and marks uptime down because `SetTarget` never reports down. `problem()` in `log.js` is per kind (commands that weren't ok, link down). The default kinds are Connects, Commands and Router link; a saved list of all six older groups is All.
- **Uptime graph**: `uptime.go` keeps JSONL (`SODE_UPTIME`) of state changes (`up`/`down`/`off`; connecting counts as down) and per-minute counts of bad (not ACKed, or tries > 1) and slow (`AckMs` over `slowAckMs`, 300ms) messages, counted in `logSent` before the append so a failing disk doesn't lose them. No file I/O under `mu`: `State` and `Note` only change memory and `Run` writes (5s), plus `<path>.alive` every minute; `Stop` (after `logSent` is done) writes `off` and the minute being counted. Opening a file whose last state isn't `off` adds `off` at the alive stamp; lines older than `uptimeKeep` (400 days) are dropped, keeping the last state before the cutoff. The `uptime` request (`from`,`to`,`slot`,`id`) is answered by `uptimeReply` with the range cut to `uptimeKeep` and counts already summed per slot, so a long range stays small. `web/uptime.js` (pure, Node-tested) makes the colours: red = no up time, yellow = partly down or bad/slow, grey = no record; one strip, toggles (1h/24h/7d/30d, labelled with their slot length by `presetText`) that set the log's From (`chipOn`; cleared by a hand-typed time or Clear times) and keep the strip rolling back from now; with no times it shows 24h, with times typed by hand those (`rangeFor`). Bars are buttons: `enterSlot` (slot mode, `slotMode`) sets From/To to the slot, forces time newest first and shows the `#log-slot` banner; the strip stays on its `view` window; Back restores times, chip and sort, any other time change just leaves the mode. Not kept across loads, like the range itself; `slotFor` keeps it under 200 slots. The page reads the log back with `logpager.js` (`newPager()`: a pure closure that owns the list, one pending request and the open/Load older/range reads; `log.js` only reads its getters), which keeps asking until a page of *shown* rows is loaded, since the default filter hides most entries. `web/log.html` + `log.js` import `core.js` and `device.js` but not `initTheme`; filter in `localStorage['sode-log-filter']`. Paging is `web/logpager.js` (pure, Node-tested, #141): one request in flight, its reply accepted only if it echoes that `before`; open and Load older keep reading (500 at a time, up to 20 requests) until 100 *shown* rows more, since the default filter hides most entries and pages of hidden ones looked like a stuck button.

## Architecture

- `internal/swp08`: framing (`frame.go`), message builders/parsers (`msg.go`), `Client` (`client.go`): one TCP session with reconnect and a keepalive probe (an interrogate, on connect and after 10s without rx). Up is reported, and `Send` accepts messages, only after the router's first reply. `SetTarget` reconnects without reporting down. A probe with no reply drops the link (~13s); any other unanswered message just triggers a probe. Rx times are monotonic offsets (`lastRx`), ACK-gated writer. Messages sent while disconnected are dropped. Callbacks `OnUp`/`OnMsg`/`OnState`.
- `internal/app`: `App` owns all router state (names, tally, protect, keyed dst → **UI level**) under one mutex. Config is an immutable `runtime` behind an `atomic.Pointer`; `ApplyConfig` saves, swaps and, if router-side fields changed, clears state and calls `SetTarget`. `Run` ticks every 100ms: `flush()` batches changes into broadcasts and finishes name refreshes, `periodic()` re-polls names/dumps.
  - Takes (`take()`): plan → check → register → send → wait → collect, one `takeLevel` per level in the `waiter`. Tests drive takes through `App.sendMsg` with a fake router (`take_test.go`).
  - Check (`checkTally`, #57) interrogates every level and waits up to 1s so `Prev` (which undo restores) comes from the router, not a cache that misses unannounced changes (falls back to the cache). It skips levels reported within `checkFresh` (15s, `seenAt`) and every take of a confirm of `bigBatch` (6)+ (`takeReq.NoCheck`), trading undo accuracy for router load (#91).
  - Router load: one message per ACK, so a take's timeouts count from when its last message was written and ACKed (`Why.Done`, closed by `Client.tx`; `sendTracked`, `leftQueue`, `queueMax`), and `own` keys are registered for `queueMax + ownFor` then shortened to `ownFor`.
  - Late answers: a take the router answers late is claimed (`lateTake`, `lateFor`; a list per route; only for levels the router said nothing about) and its entry amended (`lateWorker`, one `History.Update` per entry, `Entry.Late`, a `recent` message with `update`).
  - Failures (#15, #17): the cache holds only what the router reported, so the next `Prev` is the actual state. `waiter.see` keeps the latest route reported for unconfirmed levels; `whyMissing` writes `Failed` and `Now` (`[ui level, src]`, -1 = nothing) to the entry; a level the router reports on src after all is `already` (#36). `Err` says each level's outcome. Undo of a failed take (`undoItem` in `plans.js`) leaves out levels in `Now` and keeps no-answer levels.
  - A router change cuts takes in flight (#106; `cutTakes`): they fail with "the router changed", and a waiter keeps the `extTracker` it started on.
  - `history.go`: JSONL log with paging; a page never ends inside a group.
- `internal/app/http.go`: `/` static, `/healthz`, `/api/health` (#140: server vs router health for uptime monitors; 200 only while the router is up, else 503; no PIN, no config), `/ws`. One WebSocket per browser, JSON with a `t` field. Client → server: `batch` (all takes of one confirm; at most 8 at once, multi-take batches share a history `group`), `history` (+ `before`, echoed; `takePage` keeps a page only if it's for its current oldest entry), `refreshNames`, `clearHistory`, `config` (+ `pin`/`clearPin`), `filterSets` (+ `sets`, `id`; PIN-guarded like `config`, answered with `filterSetsResult`, then everyone gets a `filterSets` message), `presets`, `unlock` (+ `id` echoed in `unlockResult`), `lock`. What each type needs is the policy table (below); an unlisted type is dropped. Server → client: `hello` snapshot (carries `pinSet`, `version`), `status`, `names`, `namesChecked`, `tally`, `protect`, `unlockResult`, `locked`, `ping` (heartbeat every `wsHeartbeat`, 5s, through the writer goroutine; browsers can't see WebSocket ping frames, #142), history/results. Client IP honors `X-Forwarded-For` (all header lines, nearest untrusted hop; `X-Real-IP` when there is none) only from `trustedProxies`; a hop that isn't an address ends the search at the peer.
- `internal/config`: `Defaults` → `FromEnv` (seed) → `Normalize`/`Validate`; YAML load/save; `LevelMap` does UI↔wire levels.
- `cmd/swp08sim`: fake router; must keep mimicking real Ultrix quirks (e.g. no Connected for no-op connects).

## Verified against the real Ultrix (2026-10-22, 172.17.60.101:8910)

- UI level 1 → wire level 0 (`SODE_LEVEL_WIRE_OFFSET=-1`), display number = wire + 1 (`SODE_NUM_OFFSET=1`).
- Standard name requests (100/102) with 12-char names work. ~2690 sources, 720 destinations.
- Extended tally dump (0x95 → 0x97, 64 per message) works on all 17 levels; source 0xFFFF = nothing routed. Extended connect (0x82) is confirmed by 0x84.
- Routers send Connected only when a crosspoint *changes*; a matching connect gets no reply, so `take()` interrogates (0x81 → 0x83) levels already on the source, and any level still unconfirmed at the 3s timeout gets a 1s interrogate grace; those are reported `already`. The simulator mimics this.
- The router does **not** announce every change: 2026-10-23 KiPro 4 went UDX 04 → UDX 03 with no 0x84 to Sode (the next entry's `prev` showed it). Hence `found` entries and the pre-take check.
- 2026-10-23 18:01:40: the router sent 0x84 for a route Sode didn't make (PIX 03 to DSM 03 and MV08 PIP015), logged as an `ext` burst; source (panel, Companion, other client) unidentified.
- Extended protect dump (0x93 matrix, level, startDst(2) → 0x94 matrix, level, count, firstDst(2), count × 2 bytes): state in bits 4-5 of byte 1, device in the rest. Dest 65 was protected by device 9 on all levels. Single protect change messages (0x8B/0x8D/0x8F) not yet seen live.

- **2026-11-02 (branch `spike/salvo-probe`, `cmd/swp08probe`)**: 51 ordinary extended connects take ~840 ms to land, one destination after another in router-side order (~16 ms per crosspoint); pipelining the writes (20 frames per TCP write) saves under 10%. Group salvos work (contrary to the spec's "XD and Eclipse only"): 120 is answered by 122 echoing its 5 data bytes, 121 by 123 (`00` set, `01` cleared, `02` nothing to do; a clear of an empty group answers `02`), both in ~5-7 ms. Standard layout: 4-bit level, numbers < 1024, group 0-127; the probe used group 127.
- **0x84 after a Go is not reliable**: the spec (SW-P-88 Issue 4b 8.1.5) says a Go sends none, and uninstrumented runs saw 0 (standard-only Go) and 3 (mixed standard + extended). Instrumented runs (probe steps `salvo`, `extsalvo`, interrogating right after the Go) got one ordinary 0x84 per staged crosspoint, in destination/level order, ~3-5 ms apart, from ~100-130 ms after the Go to ~270-340 ms for 48-51 crosspoints. So: measured on the Ultrix 2026-11-02: a group Go announces its crosspoints about 4 ms apart (51 in ~210 ms) against ~16 ms apiece for ordinary connects (51 in ~840 ms); whether the switch itself is simultaneous is unproven (it needs a scope). The router sometimes announces staged crosspoints with 0x84 and sometimes not; Sode must work either way.
- **Extended stage** 248 (`F8 <matrix> <level> <dstH> <dstL> <srcH> <srcL> <group>`) is acknowledged by 250 (`FA` + the same 7 bytes), is held in the group, and a standard Go (121) fires extended-staged crosspoints too (#154 comments). So level 17 and source/destination numbers >= 1024 can ride a salvo; Sode stages with it (below); a Go-clear clears both kinds; extended-staged crosspoints may be announced with an ordinary 0x84 after the Go.

## Presets (#152; first called salvos, renamed in #162)

A **Preset** is a saved set of takes. It is named apart from the router's own salvos (Ross Salvos, the native group salvo of Native salvos below), and the code keeps the two apart: `preset` is the saved set (config `presets`, message `presets`, `Entry.Preset`, localStorage `sode-presets`, CSS `sode__preset*`), `salvo` is only the router feature (`fireMode: native`, `salvoGroup`, `fire.go`, `swp08/salvo.go`, the `salvo*` sent-log kinds). Old data still loads: a `salvos:` key in `config.yaml` (`Config.LegacySalvos`, moved by `Normalize`), `"salvo"` in history lines (`Entry.UnmarshalJSON`), `sode-salvos` and `sode-salvo-pins` in localStorage (`migrateLegacyKeys` in `presetstore.js`), and `salvo` on a `batch` from a page loaded before the rename.

Saved sets of takes, buttons above Recent (`data-presets` in both layouts). `config.Preset` `{name, items: [{src, dsts, levels}]}` is all numbers (internal src/dst, UI levels, `[]` = `defaultLevels`), never names. Caps in `internal/config/presets.go` (30 presets, 100 sources, 100 dsts per source, names unique ignoring case). Global ones are `cfg.presets` (`SavePresets` in `internal/app/presets.go` through `saveShared`, PIN-guarded like filter sets: `presets` message, `presetsResult`, then a `presets` broadcast; an owned field); per-browser ones are `localStorage[sode-presets]`. `web/presetstore.js` is the store and the pure parts (`resolvePreset`, `parseRefs`, validation that mirrors Go, Node-tested against `web/test/preset_cases.json`, meant for the Go tests too), `web/presets.js` the strip and editor dialog (built with `el()`). Firing is plain: `presetPlan` (in `plans.js`, next to `patchPlan`; both build items with `takeItem`) makes a plan with verb `preset` (leaves the patch boxes alone) and `plan.title`/`plan.warnings` (what no longer exists on the router, shown in the confirm and left out; `planSummary` renders any plan's title and warnings), the layout showing opens its normal confirm through the one `presetHost({active, confirm, patch})` each layout registers (`patch()` is the patch boxes as `{src, dsts, levels}`), and `sendTakes` sends one `batch`: one history group, one folder, Undo all. A preset of `bigBatch` (6)+ takes skips the pre-take check (#91). With `fireMode: native` it fires as one SW-P-08 group preset, like any multi-take confirm (Native presets, below).
- **History trigger**: `presetPlan` carries the bare `preset` name, `sendTakes` sends it as a top-level `preset` string on `batch`, the `batch` handler cleans it (`cleanPresetName`: printable runes only, 32 max, not matched against `cfg.Presets` since per-browser presets exist) and sets `takeReq.Preset` (`json:"-"`) on each item; `planPhase` copies it to `Entry.Preset` (`json:"preset,omitempty"`, old JSONL loads). Folders show a "Preset: name" note in `folderTitle`; a single-take preset (no group) shows it via `entryNote`. Quick search also matches the name (every box with text must find it). Retry/redo/undo of a preset take don't carry it; ext rows never have it.
- **Pinning**: `Preset.Pinned` (`*bool`, `pinned`; nil = true, `normalizePresets` fills it; local presets carry their own flag). The strip shows only effective pins (`pinnedPresets`, `effectivePin` in `presetstore.js`): this browser's override `localStorage['sode-preset-pins']` `{lowercase name: bool}` (everyone's presets only; unknown names and non-boolean values ignored) beats the preset's flag. `setLocalPin` is the "local toggle" (a global override equal to the flag is dropped; a local preset changes its own flag); "Pin/Unpin for everyone" in the popup sends the whole list through `globalSaver` (settings PIN, `withGlobalPin`) and clears this browser's override of that name. The editor has a Pinned checkbox (for everyone's presets it sets the flag, not this browser's override). With presets but none pinned the strip shows a "Presets… (Ctrl+G)" button.
- **Popup** (`web/presetpopup.js`, opened by `emit('presetPopup')` so `presets.js` doesn't import it): Ctrl+G on every OS, ⌘G on a Mac, from any box but not with Settings, a modal, the phone sheet or the lock screen up. Search box (`rankPresets`, core.js `search` over names), all presets listed with scope and Pin/Unpin buttons; ↑/↓ or Ctrl+J/K (⌘J/K) move, Enter closes it and calls `fire` (the normal confirm), Esc clears the text then closes. Hidden presets stay fireable. Phone: a "Presets" button at the end of the strip opens it full-screen. Keyboard mode `p` focuses the strip (`emit('presetStrip')`; ←/→ between buttons, Enter fires, Esc back to Source).

## Native salvos (#154)

`fireMode` (`sequential` default | `native`, global, not router-side: no reconnect) and `salvoGroup` (0-127, default 127). Code: `internal/app/fire.go`, builders/parsers `internal/swp08/salvo.go`.
Claims: measured on the Ultrix 2026-11-02: a group Go announces its crosspoints about 4 ms apart (51 in ~210 ms) against ~16 ms apiece for ordinary connects (51 in ~840 ms); whether the switch itself is simultaneous is unproven (it needs a scope). Native mode makes a confirm's routes land closer together; it is not promised to be one frame.
- **When**: `batch` with 2+ items in native mode runs `markStages`, which sets `takeReq.Stage` (wire levels to stage) per item: every level that exists on the router (`ExtSalvoFits`), and a dst+wire level used once in the batch (twice = neither staged). If 2+ items have something to stage it goes `batchNative`, else the batch is sequential as before. **Stage command rule**: `fireSalvo` stages a level that fits the standard layout (`SalvoFits`: matrix and wire level 0-15, numbers 0-1023) with 120, anything else (level 17, numbers >= 1024) with the extended 248; both ride the same Go, so there is no split any more. A dst+wire level used twice is staged in neither (an ordinary connect). Protected and bad takes drop out in `prepare` as ever; if fewer than 2 staged takes are left, all are sequential.
- **Phases**: `take()` is now `prepare` (plan, guard/protects, `checkPhase`: Prev and register) + `complete` (await, outcome, finish, unregister, gap). `batchNative` prepares every take (takeLimit at once; bigBatch NoCheck as today), then `fireSalvo` under `App.fireMu` (one fire at a time, never holding `mu` across waits): Go-clear and wait for its 123 (none = router without group salvos: fall back), stage each native level (120 or 248, `stageChunk` 64 queued at a time) and wait until **every** 122 or 250 has come back, matched by its decoded bytes (`swp08.Staged`; a stage the link gave up on gets no 122, so the Go never fires with one missing), then Go-set (121) and wait for 123. A deferred Go-clear runs after every fire, set or not. Acks reach the fire through `a.fire` (`fireState`, set only while a fire runs; `onRouterMsg` → `onSalvoAck`, dropped otherwise), each command waits `salvoReply` (1s) after its ACK. Then every take runs `sendTake` + `complete`: `sendTake` skips connects for native levels and interrogates them (as it does `same` levels), and the waiter is confirmed by whichever comes first: a 0x84 (if the router announces the Go) or the tally.
- **Waiter rules**: `takeLevel.native` levels get `own` keys exactly like sequential ones (`register`/`ownKeys`), because the router may announce the Go with 0x84 (then it is ours, confirms the level, and is not `already`). `see` sets `already` for them only if `l.same` (the cache said so). A native level a tally confirmed keeps its key until `goAt + salvoAnnounceFor` (2s; the Ultrix's 0x84s end ~340 ms after the Go) in `unregister`, then it expires with nothing logged. A 0x84 for a route the cache already has (the tally came first) still uses its key up (`applyTally` else branch) and `sawOwn` extends the latest matching cause, so follows of a late-announced destination still tie to the take. Also: the Go resets their `seen`/`now` (reports before it were of the old route) and sets `cause.sent`, plus `cause.saw` for takes with a changed level, so router follows still tie to the take. awaited() keeps the confirming tallies out of `found`; late/lateTake work as for sequential takes.
- **Failures**: anything before the Go (no 123 for the first clear, a missing 122, the link refusing) → group cleared, `unNative` (levels back to connects, own keys added) and the whole batch goes sequential, logged as a `salvo` command row with result `fallback`. Once the Go is sent it is **never** resent nor followed by connects: a missing 123 or `02` (someone emptied the group) is logged (`salvo` `error`) and the interrogates say what happened (failed levels as `still on`, `Failed`/`Now` as ever). On every new session `onRouterUp` clears the group under fireMu (`clearStaleSalvo`), only in native mode: sequential mode sends no salvo command at all. A router without group salvos costs each multi-take confirm a 1s wait before falling back.
- **Log**: sent kinds `salvoStage` (120), `salvoStageExt` (248) and `salvoGo` (121, Note `salvo N: set|clear`), shown in the Connects chip group; 122/123/250 are inbound, so they appear only through `salvo` command events: the fire (`N crosspoints set in X ms`, or `fallback`/`error`) and, after the takes finish, the timing (`logSalvoTiming`: `N of M crosspoints confirmed, the last X ms after the Go (a by Connected, b by interrogate)`). The confirm interrogates usually answer before the router's late 0x84s, so that time is when Sode knew, not when the router switched.
- **Simulator**: 120/248/121 with a staged list per group shared by all clients, 122/250/123 after 6 ms in line, no Connected after a Go set by default (followers follow silently), `SIM_SALVO_ANNOUNCE=1` sends one per changed crosspoint from ~110 ms after the Go, 4 ms apart, in dst/level order; `SIM_NO_SALVO=1` ignores all three. `TestNativeFits` runs level 17 and dst/src >= 1024 (mixed 120 + 248, one Go) in all four worlds; `loseExt` in the fake router drops 250s (`TestNativeNoExtStageAck`). Tests: `fire_test.go` (`fakeSalvo` in the fake router; `announce` 0/1/2 = no Connected, all, every other one, `announceAfter` the delay; `TestNativeFire` runs all four worlds).
- The extended stage (248/250) is built and tested against the simulator and fake router, but not yet seen live through Sode, nor the whole path on the Ultrix, whether the switch is simultaneous, whether router follows (PiP after DSM) fire after a Go, and what the router does with a group staged by a session that dropped.
