# Sode — notes for agents

Keyboard-first web patching for one SW-P-08 router (Ross Ultrix). User-facing settings table and protocol summary: README.md.

## Commands

```sh
go test ./...        # all tests (the Dockerfile build runs them too)
go vet ./...
go test ./internal/app -run TestWaiterAlreadyRouted -v   # one test
node --test 'web/test/*.test.mjs'                        # browser-side tests (filter language, histRows, imports)

go run ./cmd/swp08sim                                    # simulator on :8910, see SIM_* in cmd/swp08sim and README
SODE_ROUTER=127.0.0.1:8910 SODE_DEBUG=true go run ./cmd/sode   # :8080; SODE_DEBUG hex-dumps SW-P-08
docker compose --profile sim up --build                  # server + simulator
```

Without `SODE_CONFIG`, config comes from `SODE_*` env and is not persisted. The web UI is embedded with `go:embed` (`web/web.go`): restart after frontend edits.

## Key decisions

- Go, stdlib-first. Only deps: coder/websocket, yaml.v3. Distroless static image, HTTP :8080 (TLS is the user's proxy). Keep it light: no frameworks, no new deps without asking.
- SW-P-08 over TCP to one router, **single matrix**, always **extended** commands (16-bit src/dst). Protects are honored. Auto-reconnect + keepalive. Names come from the router, re-polled (default 60s).
- Levels: wire = level + configurable offset. Internally levels are UI 1..N everywhere (history, `defaultLevels`); `levelNumbering` (`1` / `0` / `va`) only changes display (`Level.Label` from `LevelMap`) and typing (`parseLevels` in `levelview.js`). `levelTypedBase` is a dropped setting kept so old files load (`KnownFields`). No free-text level names (removed at the user's request).
- Config: `/data/config.yaml`, edited in the Settings dialog; `SODE_*` env only seeds the file on first start. Save writes and stays open; Exit/Esc/Back with unsaved server settings warns once, a second try discards.
  - Settings PIN: PBKDF2 hash in `settingsPin` (`json:"-"`, never sent to browsers; `SaveSettings` carries it over). Unlock is per WebSocket connection *for that hash* (changing/removing the PIN relocks everyone) and relocks when Settings closes. `unlock` is handled in line in the read loop so a following `lock` wins. Wrong PINs are counted globally, one check at a time, waits double from 30s after the 5th, `pinMaxTries` (default 10, 0 = never) locks until `-reset-pin` or restart. A non-hash `settingsPin` stops startup. `SaveSettings` runs one at a time (`cfgMu`) and re-checks the lock.
  - Device defaults (#49): `deviceDefaults` (`config.DeviceDefaults`: theme, layout, clock, flip, scrollTop, searchFilters, setStack, nextMode) is what "This device" follows until a browser chooses its own. Not router-side, so saving never reconnects. A browser's value is a localStorage string (`sode-theme`, `sode-layout`, `sode-clock`, `sode-flip`, `sode-scroll-top`, `sode-search-filters`, `sode-set-stack`, `sode-next-mode`); missing/unknown = "Global". `resolve()` in `web/prefs.js` (pure, Node-tested): own value, then global default, then built-in. `device.js` `pref(name)`/`setPref(name, v)` (`''` removes) are the only readers/writers; `applyPrefs` re-applies live and emits `prefs`. The last global defaults are cached in `localStorage['sode-device-defaults']` on every `hello` so index.html's pre-paint script (and log.html's, theme only) follows them; that script is the one classic `web/prepaint.js` (loaded synchronously in each page's `<head>`; the other pages pass `data-only="theme"`) and repeats `resolve()` inline, keep the two in step.
- **Settings search**: the box above `#settings-toc` (end of `settings.js`) searches an index built from the page's fieldsets and their labels (`label[for]`, `.sode__field-label[id]`, `.pb-check`, `[data-find][data-label]` for anything else, e.g. buttons). `web/settingsindex.js` is pure (Node-tested, has its own scorer, not `core.js` `search`): `buildIndex`, `find`, and `DICT`, the words people type, keyed by section slug (legend text, e.g. `this-device`) and by control id; unknown ids are ignored. **A new settings section must add its slug to `DICT`; `settingsindex.test.mjs` fails otherwise.** Add terms for new settings too. Esc in the box clears it first (stopped there), the next Esc leaves Settings; its input events don't reach the form (so the unsaved warning stays). The Communication Log link is in Settings > History; the bottom `.sode__open-log` link only shows while Settings are locked.
- Frontend: vanilla JS ES modules, no build step. Follow patchbay rules exactly (https://github.com/sethdotfm/patchbay llms.txt): pb- classes only, tokens only, no Bootstrap utilities, no border-radius, status always with text. Patchbay is vendored under `web/vendor/patchbay`; copy missing icons from upstream, don't fake them. Vendored version is in `web/vendor/patchbay/VERSION` (v2.1.0; upgrade guide: upstream `transition.md`). Rules from v2: the whole UI scales with `html { font-size: 125% }` (phone 100%), never `zoom`; sizes in rem; numbers use `--pb-font-num` (set to Sans here), `--pb-font-mono` is real mono for code/hex; no per-theme CSS, tokens switch themselves; tooltips are `data-pb-tip` (+ `pb-tip--end`), the script-placed cut-off tip is `.pb-tip`; green buttons are `pb-btn--ok`; icon-only ghost buttons need `pb-btn--icon`; `layout.js` sets `data-pb-layout="phone"` next to `data-layout`.
- Confirm dialog: random churning letter + lockout (default 500ms; Enter optional).
- Version (#95): `Version`/`Stage` in `internal/app/version.go`, sent in `hello`, shown in Settings, noted in README's `**Version:**` line. **Every release bumps both**; `TestVersionNoted` fails if they differ, or (with `SODE_RELEASE_TAG=v1.0`) if the tag differs.

## History, ext and follows

JSONL history plus a shared server-side recent/undo list. Routes made elsewhere are `ext` entries (`ext.go`, split into `ext_burst.go`, `ext_ownership.go`, `ext_follows.go`):
- Connected messages none of our takes sent, plus `found` entries (#57): a tally (resync or interrogate) differing from a *known* cached value that isn't a take in flight or one that just gave up (`awaited`, `late` keys for 5s). Found entries are never follows, are grouped apart from announced ones, and show as `found`.
- `own` holds each take's (dst, wire level, src) for `ownFor`; keys are used up by the router's answer, so the same route made elsewhere right after still logs. Changes are collected into bursts (end after 500ms quiet or 3s total), logged one entry per dst+src; a burst over several dsts shares a `group`.
- **Follows** (#53): an `ext` change of the same src to another dst within 500ms of one of *our* takes (`waiter.cause` → `a.causes`). Of several that fit, the one whose last confirm came latest wins (`followed`). Panel changes are never followed. Followers of a take in a multi-take confirm aren't tied to a destination: they carry `followGroup` and `histRows` lists them as `f.followers` (a Followers row at the bottom of the folder, not in `f.entries`, so Undo all leaves them; desktop keyboard stop `w<group>`). Otherwise the follow is written with `follow` = the take's ID, ungrouped, and `histRows` attaches it as `e.follows` unless filters hide the take. Undo plans carry follows as `plan.extra` (one per dst, the oldest), sent only if the confirm's box is ticked. A burst that might follow a take still in flight waits for it (`extAwaitsTake`), only once its connects went out (`cause.sent`). An undo's confirm flags levels where dst no longer has the undone take's source (`changedSince`; skips `Failed` levels and entries without `Failed`).
- Repeated same-dst/same-levels `ext` entries within 30s merge into one row (newest, oldest's `prev`, `merged` count, `chain`); any other entry on that dst, even hidden, breaks the chain. `stackSteps` in `widgets.js` shows a stack as a timeline; older steps have Restore (`restorePlan`, `plan.at`).
- `histRows` then applies this browser's Recent filter (`filterstore.js`, `localStorage['sode-filter']`: kinds plus `src`/`dst` expressions). Folders keep every entry in `f.entries` (Undo all covers the whole confirm) and visible ones in `f.shown`.
- Stacked sets (#131): set buttons toggle (`toggleSet`). One set is `sode-filter-active` as ever. Two or more are a stack, `sode-filter-stack` `[{scope,name}]`, with no active set; `filter` is the first one's, each set's saved filter judges an entry by `stackAllows` (`filter.js`, pure) and pref `setStack` says whether all must allow (`and`) or any may (`or`; a set's excludes and kinds count only inside it). `useSets` is the one builder (missing sets drop out, one left is that set, none is All); `setActive` the one writer, which also drops the stack's cached matchers. `setFilter` is the edit path and leaves a stack. `snapshot`/`restore` put set or stack back (share-link Undo). The dialog shows "A + B", edits the first, and turns off Save as and the share link while stacked.
- Filter language: `web/filter.js`, pure, no imports; the server's `hiddenDsts` uses it too and is evaluated only in browsers. Filter sets come from the built-in All, `cfg.filterSets` and `localStorage['sode-filter-sets']`; active one is `sode-filter-active` `{scope, name, base}`; `followGlobal()` on hello applies a changed global set unless the browser edited it. Names unique per scope, ignoring case.
- Quick search (`setSearch`, `[data-search]` boxes): not kept, doesn't merge rows, reads back in 500-entry pages (`history` takes `n`, server caps at 500). Ignores the filter unless `sode-search-filters` is `on`. `web/filters.js`: the dialog, share links (`?f=` base64url JSON, applied and stripped in `main.js`), empty-state note.

- **Redo** (#153): every history row and folder has one Retry/Redo button ("take this line again", `againPlan` in `plans.js`; `againButton` in `widgets.js`). Failed takes retry (linked to their entry, a folder with failures retries just those); every other row redoes: src to dst on its levels as a plain new take, including undo, ext/found and follow rows. Skipped only with no real source or no existing level (`canRedo`). Frontend only. Retry is an outlined text button; Redo is a ghost button with the `redo-2` icon, so it doesn't read as Undo's twin. Verb wording lives in `VERBS` (`plans.js`); only a `patch` resets the boxes (`VERBS[verb].resets`; `salvo` is a verb too). The confirm shows "Already there" (`alreadyThere`, from the tally) when dst already has the source on every level. Desktop keyboard mode: `r` does whatever the button says.

## Shared saves and owned fields

- Filter sets, salvos and grid panels save through one path: `saveShared` (`app/shared.go`: takes `cfgMu`, `guardSave` re-checks the settings PIN inside it (the policy table checked it on arrival; the main lock does not cover settings), `update` mutates a copy then Normalize+Validate+save, optional broadcast of one small message, not a hello) and `replyOp(c, kind, id, n, noun, err)` (logs the command as `kind`, answers `<kind>Result` echoing `id`, sets `locked`). New "saved apart from Settings" features use both. The name rules (count, empty, 32 runes, unique ignoring case) are `validateNames` in `config/names.go`.
- **Owned fields**: Config fields saved outside the Settings form carry the tag `owned:"true"` (filterSets, salvos, grids, gridConfirm, settingsPin, deviceDefaults, users, locks, autoLockMinutes). A Settings save (`saveSettings`) does `cur.KeepOwned(live)` (reflection, `config/owned.go`), so a stale or huge browser copy can never change them; only the PIN dialog and `keepDefaults` handle the PIN and device defaults after that. `TestOwnedOrForm` fails if a new Config field is neither tagged nor in its `formFields` list, so adding a field forces the choice. The Settings dialog also strips owned lists from its `config` message (the socket read limit is `wsReadLimit`, 64 KiB; `TestMessageSizes`, `TestSettingsIgnoresOwned`).

## Grid (#150, `/grid/<link>`, `/settings/grids`)

**Files (`config/gridfiles.go`)**: each panel is its own `grids/<link>.yml` in a `grids` directory next to the config file (`GridsDir`, `/data/grids/` in Docker): one `Grid` `{link, name, cols, rows, confirm default|on|off, levels (UI levels, empty = defaultLevels), cells[{x,y,w,h,kind,ref,label}]}`. The file name must be exactly `<link>.yml` and the link a slug (`ValidLink`: lowercase letters, digits, single dashes, 40 max, so no traversal; every path goes through `gridPath`). Without `SODE_CONFIG` panels are in memory only. `Config.Grids` is a runtime field (`yaml:"-"`, `json:"grids"` so `hello` still carries it), filled at startup by `Config.LoadGrids` and kept in step by `update` (`SyncGrids` writes changed panels, removes gone ones, atomic temp+fsync+rename, before config.yaml is saved). `gridConfirm` (default true; panels on "default", `confirmFor` in `web/gridgeom.js`) stays in config.yaml. **A damaged, invalid or misnamed panel file stops startup, like a bad config.yaml, naming the file.** Migration: a config.yaml that still has `grids:` (read into `LegacyGrids`, so `KnownFields` accepts it) is moved once into files (a file that already exists wins) and config.yaml is rewritten without it. Caps: one panel at most 32 KiB as JSON, all together 48 KiB, 20 panels, so `gridSave` and the `grids` message stay under the 64 KiB read limit (`TestGridCaps`). Cell kinds: `src`, `dst` (decimal router numbers, not displayed numbers), `salvo` (a salvo's name), `confirm` (no ref, at most one per grid) and `""` (a spacer: no ref, kept so a layout survives a reload); bounds and overlap apply to all. **Messages** (all PIN-guarded like `filterSets`, answered `gridsResult` `{ok, err, locked, id}`, logged as the `grids` command): `gridSave` `{grid, was?, id}` (create or replace by link; `was` is the old link of a rename, whose file is deleted and whose new link must be free), `gridDelete` `{link, id}`, `gridConfirm` `{on, id}`. On success everyone first gets `{t:'grids', grids:[all, sorted by link], gridConfirm}` (not a hello) and then the sender its result. There is no whole-list `grids` save message. Both pages are plain routes (`/grid/<link>` serves `grid.html`, `/settings/grids` serves `settings-grids.html`) and the server no longer serves the embedded files under those prefixes, so both pages use `<base href="../">` and root-relative URLs; `core.js` builds the WebSocket URL from `new URL('ws', document.baseURI)` (so the main page, `/log` and the grid pages all work, also behind a proxy prefix). Cell kinds: `src`, `dst`, `salvo` (ref = a salvo name), `confirm` (no ref, at most one per panel) and `''`, a spacer (empty slot, saved; cells are the only truth, a square no cell covers is empty too). `grid.js` takes its link from the last path segment, reads the grid from `S.cfg.grids`, builds buttons once and updates lit/selected/now/protected text in place on `tally` (so a tap isn't lost to a redraw); takes go through `patchPlan`/`salvoPlan`/`planBlocked`/`sendTakes`, with `keyconfirm.js` (the churning letter, shared with `desktop.js`) or at once, protected destinations listed in `#grid-prot`. **Confirm cell semantics** (state in `gridstate.js`, pure): on a panel with a confirm cell a destination tap lights it (several), a source tap only selects it (one at a time, "Selected", tap again to unselect) and the Confirm cell is disabled, saying what is missing, until a source is selected and a destination lit; pressing it sends at once with no churning letter (it is the confirmation; an all-protected route is blocked), then clears the source and keeps the destinations lit. Without a confirm cell a source tap takes at once (per-panel `confirm` on shows the churning letter). A salvo cell fires `salvoPlan(salvoNamed(ref), panel levels)` under the panel's confirm mode, disabled with "Salvo not found" when the name doesn't resolve (a salvo kept in one browser only exists there). `gridedit.js` edits drafts in memory (`was` = the link as last saved, `edited` per grid), saves one panel via `globalSaver`, shows the server's error text, and keeps only `validLink` for the live outline; geometry is `gridgeom.js` (pure, Node-tested). Grid levels past the router's count are kept but unused, like `levelColors`.

## Users and locks (#151)

Optional and off by default (no users, no locks = nothing changes). `cfg.Users` `[{name, pin hash (json:"-"), len}]` (`config/users.go`, <=12, unique names ignoring case, PINs 4-12 digits and unique across users), `cfg.Locks{main,grid,log}`, `cfg.AutoLockMinutes`. A lock needs >=1 user and a settings PIN (`Validate`; `-reset-pin` turns locks off). All three are saved only by the `users` message (`SaveUsers`), which needs a settings PIN to exist and the connection settings-unlocked; `saveSettings` carries them over, like `settingsPin`. They are not grouped in one struct: they are top-level config keys (YAML and JSON) that browsers read, and an `Access` struct would change both.
- **Policy table** (`internal/app/policy.go`): ONE map from every client-to-server message type to what it needs, checked once by `admit` before the read loop's `switch` runs, and closed: a type not in the table is dropped. `TestPolicyCoversEveryMessage` parses `http.go` and fails if a `case` is missing from the table (or the table lists a type the loop doesn't handle). Needs: `open` (`hi`, `userUnlock`, `userLock`, `adminUnlock`, `unlock`, `lock`, `history`; each has a comment saying why), `needTake` (`batch`: the main lock, plus the grid lock from a page that said `grid`, as a claimed page type can only add a lock), `needMain` (`refreshNames`; `clearHistory` also `needAdmin`), `needLog` (`sent`, `uptime`; admitting `sent` sets `c.sent` in the same step under `mu`, so a lock can't slip in before the feed starts), `needAdmin` (`config`, `filterSets`, `salvos`, `gridSave`, `gridDelete`, `gridConfirm`, `users`: the settings PIN unlocked when one is set, **and not the main lock**: the settings PIN is the admin credential, and a locked wall panel or the `/settings/grids` editor, which has no lock screen, must still be able to save with it; `guardSave` repeats the PIN check under `cfgMu`). A refusal logs a `locked` command and answers the same way everywhere: `lockState` for a page lock (so the page shows its lock screen), the `locked` message for a settings PIN, and for a type with a result a failure echoing the id (`<op>Result` with `locked`; a refused `batch` gets a failed `takeResult` per item, so the page says "Not sent").
- **What the locks cover**: the main and log locks cover *actions and log reads*, not data. `hello`, names, tally, recent history and history reads keep streaming to a locked browser by design (the lock screen hides the page, it isn't a secret). Main lock: `batch`, `refreshNames`, `clearHistory`. Log lock: reading the sent log and uptime graph. Settings saves: the settings PIN alone. The page declares its type with `hi` (`{page, token}`, sent on every new socket by `lock.js`; default `main`); `/healthz` and `/api/health` stay open. History `Client`, `Why.By` and event `By` use `c.who()` (user name, else IP).
- **Access state** (`users.go`): `client.u` is a `connUser` (page, token under `mu`; the unlocked `*config.User` in one `atomic.Pointer`, so `who()` needs no lock). `pageAllowed(c, gate)` is true when the gate's lock is off or the connection is an unlocked user who still exists with the same PIN hash (a removed user or changed PIN relocks) or holds a valid admin token. `settingsUnlocked(c)` is the settings PIN. `...Locked` always means "caller holds `mu`". `syncAccess(c)` sends the lock state and, as its explicit side effect, stops the sent feed for a connection no longer allowed it.
- **PIN pools** (`pin.go`): `pinPool{state, wait, maxTries, what}` and ONE method, `tryPin(pool, from, check)`, which takes and releases `mu` itself (the hash check runs with it free). Two pools: `a.pin` (settings PIN and admin password; `checkAdmin` is the shared check behind `Unlock` and `AdminUnlock`): waits double from 30s after the 5th wrong try, up to an hour, and `pinMaxTries` locks it for good; `a.userPin` (user PINs, `userUnlock`): the same waits capped at 5 minutes, no permanent lock (a stranger must not lock operators out). A success or lockout in one never touches the other. PIN only, no name; a PIN of a length no user has is just a wrong try (the page's `sendDelay` only sends lengths some user has, and waits 500ms when a longer one exists).
- **Admin tokens** (`tokens.go`, `adminUnlock` = settings PIN from the lock screen): random 32 bytes, stored as sha256 in memory and in `tokens.json` beside the config (0600), loaded once in `New` (never under `mu`). Each is tied to the settings PIN hash it was issued against; `tokenStore.ok` fails when that no longer matches the live hash, and `issue` drops tokens of any other PIN. The browser keeps it in `localStorage['sode-lock-token']`.
- **Frontend**: `lock.js` (overlay, `lockState`/`userUnlockResult`/`adminUnlockResult` via `onMsg`, Ctrl+L, idle timer; emits `locking` as it comes down, which `settings.js` answers by exiting, and `unlocked`, which `log.js` uses to ask again; remembers the focused element and restores it), `lockrules.js` (pure, Node-tested), `lock.css`, `users.js` (the settings section; it holds no rules, it shows the server's error text; excluded from the unsaved-changes check, saved on its own). Modals other than Settings are still closed by `lock.js` clicking their Cancel/Close (a fallback until they listen for `locking`).
- Not done: idle lock is client-side; unlock is per connection, so a reconnect asks again.

## Communication Log (#72, `/log`)

Every message written to the router, captured at the wire, plus event rows (#139, below). `swp08.Client.OnTx` fires once per message from `transmit` (after ACK/NAK/give-up, with `Tries`) or for messages still queued when a session ends (`dropped`); `sendMsg` logs `unsent` when `Send` refuses. Each `Send` carries a `swp08.Why`. `OnTx` only pushes onto `txq` (never blocks the ACK-gated writer); `logSent` decodes (`swp08.DescribeTx`), appends to `SentLog` (`sentlog.go`: JSONL with its own `seq`, rotated to `.1` at half of `SODE_SENTLOG_MB`) and queues `sentAdd`/`sentPage` (both carry `total`) for connections that asked (`client.sent`). A failed write keeps its seq unused and isn't broadcast (`txLost`), so seqs have no gaps; a damaged file is renamed `.bad-…`, not fatal. `Send` pushes under `c.mu` and the session drains the queue after the writer exits, so every queued message gets a TxEvent. Read-only, no clear, no PIN. **Events (#139)**: kinds `browser` (WebSocket connect/disconnect, `By` = IP), `command` (batch as take/undo/retry, refreshNames, clearHistory, config, filterSets, grids, unlock ok/refused, lock; never a PIN or settings), `link` (router `up`/`down`/`changed`) and `server` (`start`/`stop`). They have `cmd`/`wire`/`dst`/`src` -1 and empty hex (`event()`; the page tells them by `EVENT_KINDS` in `logkinds.js`, not by hex), with `Note` for the detail. `logEvent` only pushes onto `evq`; `logSent` is the single writer of both `txq` and `evq`, so seq, file and live feed agree, and on shutdown it drains both and writes `stop`. `Run` waits for it and `main` waits for `Run` (3s). `logLink` (under `mu`) logs `down` once per outage (again if the error changes) and `up`; `applyConfig` on a router change resets it, logs `changed` and marks uptime down because `SetTarget` never reports down. `problem()` in `log.js` is per kind (commands that weren't ok, link down). The default kinds are Connects, Commands and Router link; a saved list of all six older groups is All.
- **Uptime graph**: `uptime.go` keeps JSONL (`SODE_UPTIME`) of state changes (`up`/`down`/`off`; connecting counts as down) and per-minute counts of bad (not ACKed, or tries > 1) and slow (`AckMs` over `slowAckMs`, 300ms) messages, counted in `logSent` before the append so a failing disk doesn't lose them. No file I/O under `mu`: `State` and `Note` only change memory and `Run` writes (5s), plus `<path>.alive` every minute; `Stop` (after `logSent` is done) writes `off` and the minute being counted. Opening a file whose last state isn't `off` adds `off` at the alive stamp; lines older than `uptimeKeep` (400 days) are dropped, keeping the last state before the cutoff. The `uptime` request (`from`,`to`,`slot`,`id`) is answered by `uptimeReply` with the range cut to `uptimeKeep` and counts already summed per slot, so a long range stays small. `web/uptime.js` (pure, Node-tested) makes the colours: red = no up time, yellow = partly down or bad/slow, grey = no record; one strip, toggles (1h/24h/7d/30d, labelled with their slot length by `presetText`) that set the log's From (`chipOn`; cleared by a hand-typed time or Clear times) and keep the strip rolling back from now; with no times it shows 24h, with times typed by hand those (`rangeFor`). Bars are buttons: `enterSlot` (slot mode, `slotMode`) sets From/To to the slot, forces time newest first and shows the `#log-slot` banner; the strip stays on its `view` window; Back restores times, chip and sort, any other time change just leaves the mode. Not kept across loads, like the range itself; `slotFor` keeps it under 200 slots. The page reads the log back with `logpager.js` (`newPager()`: a pure closure that owns the list, one pending request and the open/Load older/range reads; `log.js` only reads its getters), which keeps asking until a page of *shown* rows is loaded, since the default filter hides most entries. `web/log.html` + `log.js` import `core.js` and `device.js` but not `initTheme`; filter in `localStorage['sode-log-filter']`. Paging is `web/logpager.js` (pure, Node-tested, #141): one request in flight, its reply accepted only if it echoes that `before`; open and Load older keep reading (500 at a time, up to 20 requests) until 100 *shown* rows more, since the default filter hides most entries and pages of hidden ones looked like a stuck button.

## Architecture

- `internal/swp08`: framing (`frame.go`), message builders/parsers (`msg.go`), `Client` (`client.go`): one TCP session with reconnect and a keepalive probe (an interrogate, on connect and after 10s without rx). Up is reported, and `Send` accepts messages, only after the router's first reply. `SetTarget` reconnects without reporting down. A probe with no reply drops the link (~13s); any other unanswered message just triggers a probe. Rx times are monotonic offsets (`lastRx`), ACK-gated writer. Messages sent while disconnected are dropped. Callbacks `OnUp`/`OnMsg`/`OnState`.
- `internal/app`: `App` owns all router state (names, tally, protect, keyed dst → **UI level**) under one mutex. Config is an immutable `runtime` behind an `atomic.Pointer`; `ApplyConfig` saves, swaps and, if router-side fields changed, clears state and calls `SetTarget`. `Run` ticks every 100ms: `flush()` batches changes into broadcasts and finishes name refreshes, `periodic()` re-polls names/dumps.
  - Takes (`take()`): plan → check → register → send → wait → collect, one `takeLevel` per level in the `waiter`. Tests drive takes through `App.sendMsg` with a fake router (`take_test.go`).
  - Check (`checkTally`, #57) interrogates every level and waits up to 1s so `Prev` (which undo restores) comes from the router, not a cache that misses unannounced changes (falls back to the cache). It skips levels reported within `checkFresh` (15s, `seenAt`) and every take of a confirm of `bigBatch` (6)+ (`takeReq.NoCheck`), trading undo accuracy for router load (#91).
  - Router load: one message per ACK, so a take's timeouts count from when its last message was written and ACKed (`Why.Done`, closed by `Client.tx`; `sendTracked`, `leftQueue`, `queueMax`), and `own` keys are registered for `queueMax + ownFor` then shortened to `ownFor`.
  - Late answers: a take the router answers late is claimed (`lateTake`, `lateFor`; a list per route; only for levels the router said nothing about) and its entry amended (`lateWorker`, one `History.Update` per entry, `Entry.Late`, a `recent` message with `update`).
  - Failures (#15, #17): the cache holds only what the router reported, so the next `Prev` is the actual state. `waiter.see` keeps the latest route reported for unconfirmed levels; `whyMissing` writes `Failed` and `Now` (`[ui level, src]`, -1 = nothing) to the entry; a level the router reports on src after all is `already` (#36). `Err` says each level's outcome. Undo of a failed take (`undoItem` in `plans.js`) leaves out levels in `Now` and keeps no-answer levels.
  - A router change cuts takes in flight (#106; `cutTakes`): they fail with "the router changed", and a waiter keeps the `extTracker` it started on.
  - `history.go`: JSONL log with paging; a page never ends inside a group.
- `internal/app/http.go`: `/` static, `/healthz`, `/api/health` (#140: server vs router health for uptime monitors; 200 only while the router is up, else 503; no PIN, no config), `/ws`. One WebSocket per browser, JSON with a `t` field. Client → server: `batch` (all takes of one confirm; at most 8 at once, multi-take batches share a history `group`), `history` (+ `before`, echoed; `takePage` keeps a page only if it's for its current oldest entry), `refreshNames`, `clearHistory`, `config` (+ `pin`/`clearPin`), `filterSets` (+ `sets`, `id`; PIN-guarded like `config`, answered with `filterSetsResult`, then everyone gets a `filterSets` message), `salvos`, `gridSave`, `gridDelete`, `gridConfirm` (see Shared saves and Grid), `unlock` (+ `id` echoed in `unlockResult`), `lock`. What each type needs is the policy table (below); an unlisted type is dropped. Server → client: `hello` snapshot (carries `pinSet`, `version`), `status`, `names`, `namesChecked`, `tally`, `protect`, `unlockResult`, `locked`, `ping` (heartbeat every `wsHeartbeat`, 5s, through the writer goroutine; browsers can't see WebSocket ping frames, #142), history/results. Client IP honors `X-Forwarded-For` (all header lines, nearest untrusted hop; `X-Real-IP` when there is none) only from `trustedProxies`; a hop that isn't an address ends the search at the peer.
- `internal/config`: `Defaults` → `FromEnv` (seed) → `Normalize`/`Validate`; YAML load/save; `LevelMap` does UI↔wire levels.
- `cmd/swp08sim`: fake router; must keep mimicking real Ultrix quirks (e.g. no Connected for no-op connects).

## Web layout

`main.js` wires modules then calls `connect()`. `core.js` is the state/socket/bus core (state `S`, WebSocket, `on`/`onFirst`/`emit`/`onMsg`, `el`, fuzzy `search`, status helpers); it imports nothing but `tooltip.js`, and the rest sit on it with no import cycles (`test/imports.test.mjs` checks that and that every import exists). Shared helpers: `globalsave.js` `globalSaver` (the PIN-guarded "save for everyone" flow of filter sets, salvos and the grid editor: PIN row, request, answer, relock; `change`/`cancel`/`close`/`busy`), `keyconfirm.js` `keyConfirm` (the churning-letter confirm of the desktop and grid pages; each page wires its own keys to `.key(e)`), `trapDialog` in `widgets.js`, `nameProblem` in `core.js`, `owned.js` (`OWNED_KEYS`: the server-owned config lists, which the Settings form never sends back). Others: `store.js` (never-throwing localStorage `readStr`/`writeStr`/`readJSON`/`writeJSON`: use these, no hand-written try/catch), `levelview.js`, `levels.js` (pure parser), `routes.js`, `device.js`, `filterstore.js`, `history.js` (`histRows`, quick search, pager, `putEntry`), `plans.js` (plan builders, `planBlocked`/`planSummary`, `sendTakes`, results and banners), `widgets.js` (shared `levelBox`, `combobox`, `undoButton`/`retryButton`/`disclosure`, `arrivals`, `feeding`, `lockout`), `pin.js` (settings PIN unlock, one `unlocked()` flag per connection), `settings.js` (shared; builds `#settings-toc`), `filters.js`, `filter.js`. Modules reach into `handle()` through events (`helloCfg`, `helloData`, `wsclose`, `onMsg('recent' | 'takeResult' | 'filterSets' …, fn)`), so a page only gets those if it imports the module. Tests import everything through `web/test/all.mjs`.
- Socket freshness (#142): `core.js` keeps `ws.lastRx` (set on open and on every message, so a test's stub socket needs it). A 1s check per socket drops an OPEN one silent for 15s, and `wsSend` refuses one silent for 7s; either way `drop(ws)` reports the loss at once (its own close event can be long in coming) and the page reconnects. Because `wsSend` does it, every sender is covered; `sendTakes` shows "Not sent" when it returns false.

- Source ends in a row (#138): `srcEnd` in `routes.js` decides if a source is pickable (routed, with an `onPick`); `srcRow`, `currentlyNodes` and `stackSteps` all go through it. Desktop history rows fill a box with `useEnd` (opposite box next, as the row's own boxes do); Receiving's `pickSrc` goes to Levels.
- **Build DOM with `el()`, never `innerHTML`**: names come from the router.
- `planBlocked` returns `{block, prot}` without touching the plan; pass `prot` on to `planSummary`.
- Failed-take banner (`failureBanner`, `refreshResult`): one line per distinct outcome, follows the takes' history entries (`takeResult` carries `entry`), shrinks then turns into a confirmation as takes are confirmed late or retried.
- `desktop.js` and `mobile.js` are the two layouts (`layout.js` picks: auto on narrow touch screens, per-browser override; `index.html` applies the same rule before first paint). Phone: one input stepping Source → Destination → Levels, patch summary pinned at the top, match list floating over it, number pad for Levels.
- Desktop keyboard mode: Esc with every box empty (or Esc on a Recent button) focuses `#history` and sets `keysOn`, cleared by any click (`onListKey`: s/d/f boxes, j/k rows, J next group, K latest take, h/l or Shift+Enter/Enter close/open, u/r, `,` settings, `/` Filters, Shift+S/Shift+D Filter by boxes, `?` shortcut list, also Ctrl+? anywhere). Folders open as the cursor enters and close as it leaves (`autoOpen`); a small `.sode__key-note` shows each empty box's key.
- Keys: Ctrl+Z (and ⌘Z on a Mac) undoes the last Sode take, except that the OS text-undo key leaves a box with text to undo its typing. Ctrl+, opens Settings. Modifier rule: Control = Sode commands and match-list moves (Ctrl+J/K) on every OS; Option/Alt = only the theme toggle (Alt+Shift+T); ⌘ left to the OS except ⌘Z, ⌘J/K and ⌘Enter in the Destination box; every check excludes the other two modifiers. Key labels are lowercase with ⇧ where Shift is needed (⇧j).
- Ctrl+S/D/F fill a patch box from the last take (`useLast`, `lastTake()` in `plans.js`: this browser's last patch recorded by `sendTakes`, else the newest Sode take in history); destinations are added to those present; focus moves to the opposite box only if empty, otherwise Levels. Each box shows a "Last:" chip. Destination-before-Source is per browser unless following the global default (`flipped()`/`setFlip()`, `data-flip` on `<html>`).
- **Next chips** (`nextTake` in `plans.js`): beside each "Last:" chip, and Ctrl+Shift+S/D, fill Source/Destination with the last take's numbers one higher (every destination shifted). Pref `nextMode` (device default `number` | `fuzzy`): fuzzy searches the name's text without its counter, trailing digits and single letters (`nameStem`: "Cam 3" → "Cam", "Prmpt A" → "Prmpt", #149) and takes the first higher match in router order (`nextOf`). A side with no next is null/empty and its chip and key do nothing. On desktop the chip is a small "Next" that opens (CSS only) to the value on hover, focus or while Shift is held (`data-shift` on `<html>`, set in `desktop.js`), hiding the Last chip meanwhile; the phone shows it in full.
- Destination box `+`, Ctrl+Enter, ⌘Enter add another destination (#93): the match becomes a chip (bubble on the phone) and the typed search stays with its list open minus already-added ones. Enter with leftover text and chips is refused as unmatched text (Esc clears); Tab takes its best match (desktop).

## Verified against the real Ultrix (2026-10-22, 172.17.60.101:8910)

- UI level 1 → wire level 0 (`SODE_LEVEL_WIRE_OFFSET=-1`), display number = wire + 1 (`SODE_NUM_OFFSET=1`).
- Standard name requests (100/102) with 12-char names work. ~2690 sources, 720 destinations.
- Extended tally dump (0x95 → 0x97, 64 per message) works on all 17 levels; source 0xFFFF = nothing routed. Extended connect (0x82) is confirmed by 0x84.
- Routers send Connected only when a crosspoint *changes*; a matching connect gets no reply, so `take()` interrogates (0x81 → 0x83) levels already on the source, and any level still unconfirmed at the 3s timeout gets a 1s interrogate grace; those are reported `already`. The simulator mimics this.
- The router does **not** announce every change: 2026-10-23 KiPro 4 went UDX 04 → UDX 03 with no 0x84 to Sode (the next entry's `prev` showed it). Hence `found` entries and the pre-take check.
- 2026-10-23 18:01:40: the router sent 0x84 for a route Sode didn't make (PIX 03 to DSM 03 and MV08 PIP015), logged as an `ext` burst; source (panel, Companion, other client) unidentified.
- Extended protect dump (0x93 matrix, level, startDst(2) → 0x94 matrix, level, count, firstDst(2), count × 2 bytes): state in bits 4-5 of byte 1, device in the rest. Dest 65 was protected by device 9 on all levels. Single protect change messages (0x8B/0x8D/0x8F) not yet seen live.

## Salvos (#152)

Saved sets of takes, buttons above Recent (`data-salvos` in both layouts). `config.Salvo` `{name, items: [{src, dsts, levels}]}` is all numbers (internal src/dst, UI levels, `[]` = `defaultLevels`), never names. Caps in `internal/config/salvos.go` (30 salvos, 100 sources, 100 dsts per source, names unique ignoring case). Global ones are `cfg.salvos` (`SaveSalvos` in `internal/app/salvos.go` through `saveShared`, PIN-guarded like filter sets: `salvos` message, `salvosResult`, then a `salvos` broadcast; an owned field); per-browser ones are `localStorage[sode-salvos]`. `web/salvostore.js` is the store and the pure parts (`resolveSalvo`, `parseRefs`, validation that mirrors Go, Node-tested against `web/test/salvo_cases.json`, meant for the Go tests too), `web/salvos.js` the strip and editor dialog (built with `el()`). Firing is plain: `salvoPlan` (in `plans.js`, next to `patchPlan`; both build items with `takeItem`) makes a plan with verb `salvo` (leaves the patch boxes alone) and `plan.title`/`plan.warnings` (what no longer exists on the router, shown in the confirm and left out; `planSummary` renders any plan's title and warnings), the layout showing opens its normal confirm through the one `salvoHost({active, confirm, patch})` each layout registers (`patch()` is the patch boxes as `{src, dsts, levels}`), and `sendTakes` sends one `batch`: one history group, one folder, Undo all. A salvo of `bigBatch` (6)+ takes skips the pre-take check (#91). No SW-P-08 salvo commands (120-125) and no fire mode.
