Notes for AI agents working in this repo. Only the non-obvious is here; code and git history hold the rest.

Sode: keyboard-first web patching for one SW-P-08 router (Ross Ultrix). Settings table and protocol summary are in README.md.

## Key decisions

- Go, stdlib-first. Deps only coder/websocket and yaml.v3; no new deps or frameworks without asking. Distroless image, HTTP :8080 (TLS is the user's proxy).
- SW-P-08 over TCP to one router, single matrix, always extended commands (16-bit src/dst). Protects honored. Auto-reconnect and keepalive. Names come from the router, re-polled (default 60s).
- Levels: wire = level + offset. Internally levels are UI 1..N everywhere. levelNumbering (1, 0, va) only changes display (Level.Label) and typing (parseLevels in levelview.js). levelTypedBase is dropped but kept so old files load. No free-text level names (user asked for removal).
- Config lives in /data/config.yaml, edited in Settings. SODE_* env only seeds the file on first start. Save stays open; leaving with unsaved server settings warns once, a second try discards.
- Settings PIN: PBKDF2 hash in settingsPin (json:"-", never sent to browsers, SaveSettings carries it over). Unlock is per connection and per hash, relocks when Settings closes or the PIN changes. unlock is handled inline in the read loop so a following lock wins. Wrong PINs counted globally, one check at a time, waits double from 30s after the 5th; pinMaxTries (default 10, 0 = never) locks until -reset-pin or restart. A non-hash settingsPin stops startup. SaveSettings is serialized by cfgMu and re-checks the lock.
- Device defaults (#49): deviceDefaults (theme, layout, clock, flip, scrollTop, searchFilters, setStack, nextMode) is what This device follows until a browser picks its own. Not router-side, no reconnect. Browser values are localStorage strings (sode-theme, sode-layout, sode-clock, sode-flip, sode-scroll-top, sode-search-filters, sode-set-stack, sode-next-mode); missing or unknown means Global. resolve() in web/prefs.js (pure) picks own, then global, then built-in. device.js pref/setPref ('' removes) are the only readers and writers. Global defaults are cached in localStorage sode-device-defaults on every hello for web/prepaint.js (sync in each head; other pages pass data-only="theme"), which repeats resolve() inline: keep them in step.
- Settings search: settingsindex.js (pure, own scorer) indexes fieldsets and labels (label[for], .sode__field-label[id], .pb-check, [data-find][data-label] for buttons etc). DICT maps section slugs (legend text) and control ids to search words. A new settings section must add its slug to DICT or settingsindex.test.mjs fails; add terms for new settings too. Esc in the box clears it, the next Esc leaves Settings. Its input events must not reach the form.
- Frontend: vanilla ES modules, no build. Follow patchbay rules exactly (https://github.com/sethdotfm/patchbay llms.txt): pb- classes only, tokens only, no Bootstrap utilities, no border-radius, status always with text. Vendored in web/vendor/patchbay (VERSION file, v2.1.0); copy missing icons from upstream, never fake them. UI scales with html font-size 125% (phone 100%), never zoom; sizes in rem; numbers use --pb-font-num, --pb-font-mono is for code/hex; no per-theme CSS; tooltips are data-pb-tip (+ pb-tip--end); green buttons pb-btn--ok; icon-only ghost buttons need pb-btn--icon; layout.js sets data-pb-layout="phone".
- Build DOM with el(), never innerHTML: names come from the router.
- Users never ride the hello (it reaches locked pages): hello() blanks cfg.users. Names come in lockState.names (only when unlocked, S.userNames), PIN lengths in lockState.lens, the Users editor asks usersList. Keep new user fields out of anything sent before unlock.
- Confirm dialog: churning random letter plus lockout (default 500ms, Enter optional).
- Version (#95): Version and Stage in internal/app/version.go, sent in hello as BuildLabel(), shown in Settings, noted in README's Version line. Every release bumps both and adds a CHANGELOG.md section (#147). TestVersionNoted fails on mismatch, or with SODE_RELEASE_TAG if the tag differs or the heading says unreleased. See RELEASING.md. Only promote.yml may push the latest image tag.

## History, ext and follows

JSONL history plus a shared server recent/undo list. Routes made elsewhere are ext entries (ext*.go).
- Ext: Connected messages none of our takes sent, plus found entries (#57): a tally differing from a known cached value that isn't a take in flight or one that just gave up (awaited, late keys for 5s). Found entries are never follows, are grouped apart.
- own holds each take's (dst, wire level, src); the router's answer uses a key up, so the same route made elsewhere right after still logs. Changes gather into bursts (500ms quiet or 3s total), one entry per dst+src; a burst over several dsts shares a group.
- Follows (#53): an ext change of the same src to another dst within 500ms of one of our takes (waiter.cause, a.causes). Of several, the latest last confirm wins. Panel changes are never followed. In a multi-take confirm followers carry followGroup and histRows lists them as f.followers (not in f.entries, so Undo all leaves them; keyboard stop w<group>). Otherwise follow = the take's ID, ungrouped, shown as e.follows unless filters hide the take. Undo plans carry follows as plan.extra, sent only if the confirm's box is ticked. A burst that might follow a take in flight waits for it (extAwaitsTake) once its connects went out (cause.sent). An undo confirm flags levels where dst no longer has the undone take's source (changedSince).
- Same-dst same-levels ext entries within 30s merge (merged count, chain); any other entry on that dst breaks the chain. stackSteps shows a stack as a timeline with Restore (restorePlan).
- histRows applies this browser's filter (filterstore.js, sode-filter). Folders keep all entries in f.entries, visible ones in f.shown.
- Stacked sets (#131): set buttons toggle. One set is sode-filter-active. Two or more are a stack, sode-filter-stack [{scope,name}], no active set. stackAllows (filter.js) judges per set; pref setStack: and or or. useSets is the one builder, setActive the one writer, setFilter the edit path (leaves the stack), snapshot/restore for share-link Undo. The dialog shows "A + B", edits the first, disables Save as and share while stacked.
- Filter language: web/filter.js, pure, no imports; the server's hiddenDsts uses it too. Sets come from built-in All, cfg.filterSets, localStorage sode-filter-sets; active is sode-filter-active {scope,name,base}; followGlobal() on hello applies a changed global set unless the browser edited it. Names unique per scope ignoring case.
- Quick search: not kept, doesn't merge rows, reads 500-entry pages (server caps at 500). Ignores the filter unless sode-search-filters is on.
- Redo (#153): every row and folder has one Retry/Redo button (againPlan in plans.js, againButton in widgets.js). Failed takes retry (a folder retries just failures); everything else redoes src to dst on its levels as a new take, including undo, ext, found, follow rows. Skipped with no real source or level (canRedo). Frontend only. Undo/Redo/Retry are outlined pb-btn--sm; Undo has undo-2, Redo redo-2, Retry text only; phone swipe Undo hides the icon in CSS. Verb wording in VERBS (plans.js); only patch resets the boxes. Confirm shows Already there (alreadyThere) when dst has the source on every level. Keyboard r does what the button says.
- Desktop Recent sits apart from the patch boxes by a thin divider (end of history.css); the phone has none.

New saved-apart features use both. Name rules: validateNames in config/names.go (count, empty, 32 runes, unique ignoring case).

- Grid is parked on branch archive/grids (#150); old grids: and gridConfirm: keys load and are ignored.

## Users and locks (#151)

Off by default. cfg.Users [{name, pin hash (json:"-"), len, trusted, persistent}] (max 12, unique names ignoring case, PINs 4-12 digits unique across users), cfg.Locks{main,log}, cfg.AutoLockMinutes. A lock needs a user and a settings PIN (Validate; -reset-pin turns locks off). The user list and maxPinLen are saved only by the users message (SaveUsers), which needs the connection settings-unlocked (a trusted user is not enough); saveSettings carries it over. Locks and auto-lock are ordinary Settings fields tagged guard:"pin"; a config message without a locks or autoLockMinutes key keeps live values (a missing key must never read as every lock off). Web GUARDED in lockrules.js mirrors the tag.
- Policy table (internal/app/policy.go): one closed map from every client-to-server type to its need, checked once by admit before the read loop switch; unlisted types are dropped. TestPolicyCoversEveryMessage parses http.go and fails on a mismatch. Needs: open (hi, userUnlock, userLock, userSetPin, unlock, lock, history), needTake (batch: main lock), needMain (refreshNames; clearHistory also needAdmin), needLog (sent, uptime), needAdmin (users, clearHistory: settings PIN when set, and not the main lock, so a locked wall panel can still save with the PIN), needTrusted (config, filterSets, presets: settings PIN, or a connection unlocked as a user who still exists with the same hash and is Trusted now in live config). config becomes needAdmin when it carries pin or clearPin. guardSave repeats the check under cfgMu. A refusal logs a locked command and answers lockState (page lock), locked (settings PIN), or a failed <op>Result echoing id (batch gets a failed takeResult per item).
- Locks cover actions and log reads, not data: hello, names, tally, history keep streaming to locked browsers. Main lock: batch, refreshNames, clearHistory. Log lock: sent log and uptime. Pages declare type with hi {page, token}; /healthz and /api/health stay open. History Client, Why.By and event By use c.who() (user name, else IP).
- Access state (users.go): client.u is a connUser (page, token under mu, unlocked *config.User in an atomic.Pointer). pageAllowed: lock off, or an unlocked user who still exists with the same hash. ...Locked means caller holds mu. syncAccess(c) sends lock state and stops the sent feed for connections no longer allowed.
- PIN pools (pin.go): one method tryPin(pool, from, check). a.pin (settings): doubling waits from 30s after the 5th wrong try up to an hour, pinMaxTries locks for good, resets on success. a.userPin (userUnlock): same waits capped at 5 minutes, no permanent lock, a right PIN does not reset the count (else a holder of one PIN could guess the rest), forgotten after an hour clean. Pools never touch each other. PIN only, no name; a length no user has is just a wrong try.
- Persistent sessions (tokens.go, user flag persistent): userUnlock for a persistent user issues a token (issueSession, no disk I/O under mu): 32 random bytes base64url, only sha256 kept, in memory and tokens.json beside config (0600, temp file, fsync, rename). Record {user, pin hash, at}; tokenStore.user re-reads the live user on each use, so a changed PIN, removed or renamed user or unticked Persistent kills it. Max 8 per user and kind. Browser keeps it in localStorage sode-session and sends it in hi; a wrong one is ignored. userLock always revokes the connection's token and relocks other connections holding it. Non-persistent users get the idle timer and PIN on reconnect. Old admin-token files load as nothing; a damaged file is forgotten.
  - Catch-up (#159): catchUpSessions (end of applyConfig and UserSetPin) gives every connection unlocked as a persistent user without a good token one, as {t:"session",token}. issueSession is idempotent and drops its token if the connection locked or got another meanwhile.
  - localStorage rather than a cookie: hi already carries the token over the WebSocket, so no HTTP endpoint, cookie flags or CSRF. A cookie could be HttpOnly, but the page never uses innerHTML, the token only acts as that user, and the server caps and revokes.
- Hardening: tokenStore.prune(cfg) deletes every record invalid against live config, run at the end of a.update and in New, so untick/retick, rename A to B to A, or PIN changed and restored never revive a token. Tokens die after tokenMaxAge (90 days) unused; hi or an open connection (touchSessions hourly) renews. userSignOutAll {name,id} (needAdmin) deletes a user's tokens and relocks them. UserUnlock clears the connection's token. A trusted-only Settings save may not change router, trustedProxies or pinMaxTries (trustedMayNotChange; guardedErr counts as errLocked so the page asks for the PIN; guardedEdited in lockrules.js asks up front). CSP: secureHeaders in http.go sets one policy (script-src 'self', frame-ancestors 'none'), nosniff and Referrer-Policy same-origin; pages must have no inline scripts, on*= handlers or javascript: URLs (TestNoInlineScript).
- Trusted users make low-risk saves without the settings PIN (Settings form, filterSets, presets). ## Communication Log (#72, /log)

Every message written to the router, captured at the wire, plus event rows (#139). swp08.Client.OnTx fires once per message from transmit (after ACK, NAK or give-up, with Tries) or for messages still queued when a session ends; sendMsg logs unsent when Send refuses. Each Send carries a swp08.Why. OnTx only pushes onto txq (never blocks the ACK-gated writer); logSent decodes, appends to SentLog (sentlog.go: JSONL with own seq, rotated to .1 at half SODE_SENTLOG_MB) and queues sentAdd/sentPage for connections that asked. A failed write keeps its seq unused and isn't broadcast, so seqs have no gaps; a damaged file is renamed .bad-..., not fatal. Read-only, no clear, no PIN.
- Events: kinds browser (connect/disconnect, By = IP), command (batch, refreshNames, clearHistory, config, filterSets, unlock, lock; never a PIN or settings), link (up, down, changed) and server (start, stop). They have cmd/wire/dst/src -1 and empty hex (event(); the page uses EVENT_KINDS in logkinds.js), detail in Note. logEvent pushes onto evq; logSent is the single writer of txq and evq so seq, file and feed agree; on shutdown it drains both and writes stop (Run waits for it, main waits for Run, 3s). logLink (under mu) logs down once per outage (again if the error changes) and up; a router change resets it, logs changed and marks uptime down because SetTarget never reports down. Default kinds: Connects, Commands, Router link.
- Uptime graph: uptime.go keeps JSONL (SODE_UPTIME) of state changes (up, down, off; connecting counts as down) and per-minute counts of bad (not ACKed or tries > 1) and slow (AckMs over 300) messages, counted in logSent before the append. No file I/O under mu: State and Note change memory only, Run writes (5s) plus <path>.alive each minute; Stop writes off. A file whose last state isn't off gets off at the alive stamp; lines older than uptimeKeep (400 days) drop, keeping the last state before the cutoff. The uptime request {from,to,slot,id} is answered by uptimeReply with counts summed per slot. uptime.js (pure): red = no up time, yellow = partly down or bad or slow, grey = no record; toggles 1h/24h/7d/30d set the log's From (chipOn; cleared by hand-typed times or Clear times); bars are buttons: enterSlot sets From/To, forces newest first, shows #log-slot; Back restores. slotFor keeps it under 200 slots.
- Page: log.js imports core.js and device.js but not initTheme; filter in sode-log-filter. logpager.js (newPager, pure, #141) owns the list and one pending request (reply accepted only if it echoes that before); it keeps reading (500 at a time, up to 20 requests) until 100 shown rows more, since the default filter hides most entries.

## Architecture

- internal/swp08: frame.go, msg.go, client.go: one TCP session with reconnect and a keepalive probe (an interrogate, on connect and after 10s without rx). Up is reported, and Send accepts, only after the router's first reply. SetTarget reconnects without reporting down. A probe with no reply drops the link (~13s); other unanswered messages just trigger a probe. Rx times are monotonic offsets, writer is ACK-gated. Messages sent while disconnected are dropped. Callbacks OnUp, OnMsg, OnState.
- internal/app: App owns all router state (names, tally, protect, keyed dst to UI level) under one mutex. Config is an immutable runtime behind an atomic.Pointer; ApplyConfig saves, swaps and, if router-side fields changed, clears state and calls SetTarget. Run ticks every 100ms: flush() batches broadcasts and finishes name refreshes, periodic() re-polls.
  - Takes: take() = prepare + complete: plan, check, register, send, wait, collect, one takeLevel per level in the waiter. Tests drive takes through App.sendMsg with a fake router (take_test.go).
  - Check (checkTally, #57) interrogates every level and waits up to 1s so Prev (what undo restores) comes from the router, not a cache that misses unannounced changes (falls back to cache). Skips levels reported within checkFresh (15s) and all takes of a confirm of bigBatch (6)+ (NoCheck, #91), trading undo accuracy for router load.
  - Router load: one message per ACK, so timeouts count from when a take's last message was ACKed (Why.Done, sendTracked, leftQueue, queueMax); own keys register for queueMax + ownFor then shorten to ownFor.
  - Late answers: a take the router answers late is claimed (lateTake, lateFor; only levels the router said nothing about) and its entry amended (lateWorker, Entry.Late, a recent message with update).
  - Failures (#15, #17): the cache holds only what the router reported, so the next Prev is real state. waiter.see keeps the latest route for unconfirmed levels; whyMissing writes Failed and Now ([ui level, src], -1 = nothing); a level the router reports on src after all is already (#36). Undo of a failed take leaves out levels in Now and keeps no-answer levels (undoItem).
  - A router change cuts takes in flight (#106, cutTakes): they fail with "the router changed"; a waiter keeps the extTracker it started on.

## Verified against the real Ultrix (2026-10-22, 172.17.60.101:8910)

- UI level 1 = wire 0 (SODE_LEVEL_WIRE_OFFSET=-1), display number = wire + 1 (SODE_NUM_OFFSET=1).
- Standard name requests (100/102) with 12-char names work. About 2690 sources, 720 destinations.
- Extended tally dump (0x95 to 0x97, 64 per message) works on all 17 levels; source 0xFFFF = nothing routed. Extended connect (0x82) is confirmed by 0x84.
- Routers send Connected only when a crosspoint changes; a matching connect gets no reply, so take() interrogates (0x81 to 0x83) levels already on the source, and levels unconfirmed at the 3s timeout get a 1s interrogate grace; those are reported already. The simulator mimics this.
- The router does not announce every change: 2026-10-23 KiPro 4 went UDX 04 to UDX 03 with no 0x84 (the next entry's prev showed it), hence found entries and the pre-take check. Also 2026-10-23 18:01:40 a 0x84 arrived for a route Sode didn't make (PIX 03 to DSM 03 and MV08 PIP015), logged as an ext burst, source unknown.
- Extended protect dump (0x93 matrix, level, startDst(2) to 0x94 matrix, level, count, firstDst(2), count x 2 bytes): state in bits 4-5 of byte 1, device in the rest. Dest 65 was protected by device 9 on all levels. Single protect change messages (0x8B/0x8D/0x8F) not seen live.
- 2026-11-02 (branch spike/salvo-probe, cmd/swp08probe): 51 ordinary extended connects take about 840 ms (~16 ms each, one dst after another); pipelining saves under 10%. Group salvos work despite the spec saying XD and Eclipse only: 120 is answered by 122 echoing its 5 data bytes, 121 by 123 (00 set, 01 cleared, 02 nothing to do; clearing an empty group answers 02), in 5-7 ms. Standard layout: 4-bit level, numbers under 1024, group 0-127; probe used 127.
- 0x84 after a Go is unreliable: the spec (SW-P-88 Issue 4b 8.1.5) says none, uninstrumented runs saw 0 and 3, instrumented runs got one 0x84 per staged crosspoint ~3-5 ms apart, from ~100-130 ms after the Go to ~270-340 ms for 48-51 crosspoints. So a Go announces crosspoints about 4 ms apart (51 in ~210 ms) against ~16 ms for ordinary connects; whether the switch itself is simultaneous is unproven (needs a scope). Sode must work either way.
- Extended stage 248 (F8 matrix level dstH dstL srcH srcL group) is acked by 250 (FA + same 7 bytes), is held in the group, and a standard Go (121) fires extended-staged crosspoints too (#154). So level 17 and numbers >= 1024 can ride a salvo; a Go-clear clears both kinds; they may be announced with an ordinary 0x84 after the Go.

## Native salvos (#154)

fireMode (sequential default, or native; global; no reconnect) and salvoGroup (0-127, default 127). Code: app/fire.go, swp08/salvo.go. Native makes a confirm's routes land closer together (see measurements above); not promised to be one frame.
- When: a batch of 2+ items in native mode runs markStages, setting takeReq.Stage (wire levels) per item: every level that exists on the router (ExtSalvoFits) and a dst+wire level used once in the batch (used twice = neither staged, an ordinary connect). If 2+ items have something to stage it goes batchNative, else sequential. Stage command rule: SalvoFits levels (matrix and wire level 0-15, numbers 0-1023) use 120, anything else (level 17, numbers >= 1024) uses extended 248; both ride the same Go. Protected and bad takes drop out in prepare; fewer than 2 staged takes left means all sequential.
- Phases: batchNative prepares every take (bigBatch NoCheck as usual), then fireSalvo under App.fireMu (one fire at a time, never holding mu across waits): Go-clear and wait for 123 (none = no group salvos, fall back), stage each native level (stageChunk 64 queued at a time) and wait for every 122 or 250 matched by decoded bytes (swp08.Staged; a stage the link gave up on gets no ack, so the Go never fires with one missing), then Go-set (121) and wait for 123. A deferred Go-clear runs after every fire. Acks arrive through a.fire (fireState, set only during a fire; onRouterMsg to onSalvoAck, dropped otherwise); each command waits salvoReply (1s) after its ACK. Then each take runs sendTake + complete: sendTake skips connects for native levels and interrogates them, and the waiter confirms on whichever comes first, a 0x84 or the tally.
- Waiter rules: takeLevel.native levels get own keys like sequential ones, because the router may announce the Go (then it is ours, confirms the level, isn't already). see sets already for them only if l.same. A native level confirmed by tally keeps its key until goAt + salvoAnnounceFor (2s) in unregister, then expires silently. A 0x84 for a route the cache already has still uses its key (applyTally else branch) and sawOwn extends the latest matching cause, so follows of a late-announced destination still tie to the take. The Go resets their seen/now and sets cause.sent, plus cause.saw for takes with a changed level. awaited() keeps confirming tallies out of found.
- Failures: anything before the Go (no first 123, a missing ack, the link refusing) clears the group, unNative turns levels back to connects (adding own keys) and the whole batch goes sequential, logged as a salvo command with result fallback. Once the Go is sent it is never resent or followed by connects: a missing 123 or a 02 is logged (salvo error) and the interrogates say what happened (still on, Failed/Now). On every new session onRouterUp clears the group under fireMu (clearStaleSalvo), native mode only; sequential mode sends no salvo command at all. A router without group salvos costs each multi-take confirm a 1s wait before fallback.
- Log: sent kinds salvoStage (120), salvoStageExt (248), salvoGo (121, Note "salvo N: set|clear"), in the Connects group. 122/123/250 are inbound, so they appear only via salvo command events: the fire ("N crosspoints set in X ms", fallback, error) and, after takes finish, logSalvoTiming ("N of M crosspoints confirmed, the last X ms after the Go (a by Connected, b by interrogate)"). Confirm interrogates usually answer before the router's late 0x84s, so that time is when Sode knew, not when the router switched.
- Simulator: 120/248/121 with a staged list per group shared by all clients, 122/250/123 after 6 ms, no Connected after a Go by default; SIM_SALVO_ANNOUNCE=1 sends one per changed crosspoint from ~110 ms after the Go, 4 ms apart in dst/level order; SIM_NO_SALVO=1 ignores all three. Tests: fire_test.go (fakeSalvo; announce 0/1/2 = none, all, every other; announceAfter delay; TestNativeFire runs all four worlds), TestNativeFits (level 17 and numbers >= 1024, mixed 120 and 248, one Go), TestNativeNoExtStageAck (loseExt drops 250s).
- Not yet seen live through Sode: extended stage, the whole path on the Ultrix, whether the switch is simultaneous, whether router follows (PiP after DSM) fire after a Go, what the router does with a group staged by a session that dropped.
