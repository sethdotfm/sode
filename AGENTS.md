# AGENTS.md

Guidance for AI coding agents working in this repo. Details that the code or git history already show are left out; what is here is the non-obvious part.

# Sode — notes for agents

Keyboard-first web patching for one SW-P-08 router (Ross Ultrix). User-facing settings table and protocol summary: README.md.

## Commands

```sh
go test ./...        # all tests (the Dockerfile build runs them too)
go vet ./...
go test ./internal/app -run TestWaiterAlreadyRouted -v   # one test
node --test 'web/test/*.test.mjs'                        # browser-side tests (filter language, histRows, imports)

go run ./cmd/swp08sim                                    # simulator on :8910, see SIM_* in cmd/swp08sim and README
SODE_ROUTER=127.0.0.1:8910 SODE_DEBUG=true go run ./cmd/sode   # :8080; SODE_DEBUG hex-dumps SW-P-08
docker compose --profile sim up --build                  # server + simulator
```

Without `SODE_CONFIG`, config comes from `SODE_*` env and is not persisted. The web UI is embedded with `go:embed` (`web/web.go`): restart after frontend edits.

## Key decisions

- Go, stdlib-first. Only deps: coder/websocket, yaml.v3. Distroless static image, HTTP :8080 (TLS is the user's proxy). Keep it light: no frameworks, no new deps without asking.
- SW-P-08 over TCP to one router, **single matrix**, always **extended** commands (16-bit src/dst). Protects are honored. Auto-reconnect + keepalive. Names come from the router, re-polled (default 60s).
- Levels: wire = level + configurable offset. Internally levels are UI 1..N everywhere (history, `defaultLevels`); `levelNumbering` (`1` / `0` / `va`) only changes display (`Level.Label` from `LevelMap`) and typing (`parseLevels` in `levelview.js`). `levelTypedBase` is a dropped setting kept so old files load (`KnownFields`). No free-text level names (removed at the user's request).
- Config: `/data/config.yaml`, edited in the Settings dialog; `SODE_*` env only seeds the file on first start. Save writes and stays open; Exit/Esc/Back with unsaved server settings warns once, a second try discards.
  - Settings PIN: PBKDF2 hash in `settingsPin` (`json:"-"`, never sent to browsers; `SaveSettings` carries it over). Unlock is per WebSocket connection *for that hash* (changing/removing the PIN relocks everyone) and relocks when Settings closes. `unlock` is handled in line in the read loop so a following `lock` wins. Wrong PINs are counted globally, one check at a time, waits double from 30s after the 5th, `pinMaxTries` (default 10, 0 = never) locks until `-reset-pin` or restart. A non-hash `settingsPin` stops startup. `SaveSettings` runs one at a time (`cfgMu`) and re-checks the lock.
  - Device defaults (#49): `deviceDefaults` (`config.DeviceDefaults`: theme, layout, clock, flip, scrollTop, searchFilters, setStack, nextMode) is what "This device" follows until a browser chooses its own. Not router-side (no reconnect). A browser's value is a localStorage string (`sode-theme`, `sode-layout`, `sode-clock`, `sode-flip`, `sode-scroll-top`, `sode-search-filters`, `sode-set-stack`, `sode-next-mode`); missing/unknown = "Global". `resolve()` in `web/prefs.js` (pure, Node-tested): own value, then global default, then built-in. `device.js` `pref(name)`/`setPref(name, v)` (`''` removes) are the only readers/writers; `applyPrefs` re-applies live and emits `prefs`. The last global defaults are cached in `localStorage['sode-device-defaults']` on every `hello` so the pre-paint script follows them; that is the classic `web/prepaint.js` (loaded synchronously in each page's `<head>`; other pages pass `data-only="theme"`) and it repeats `resolve()` inline: keep the two in step.
- **Settings search**: the box above `#settings-toc` (end of `settings.js`) searches an index built from the page's fieldsets and labels (`label[for]`, `.sode__field-label[id]`, `.pb-check`, `[data-find][data-label]` for anything else, e.g. buttons). `web/settingsindex.js` is pure (Node-tested, own scorer): `buildIndex`, `find`, and `DICT`, the words people type, keyed by section slug (legend text, e.g. `this-device`) and by control id. **A new settings section must add its slug to `DICT`; `settingsindex.test.mjs` fails otherwise.** Add terms for new settings too. Esc in the box clears it first, the next Esc leaves Settings; its input events don't reach the form (so the unsaved warning stays). The Communication Log link is in Settings > History; the bottom `.sode__open-log` link only shows while Settings are locked.
- Frontend: vanilla JS ES modules, no build step. Follow patchbay rules exactly (https://github.com/sethdotfm/patchbay llms.txt): pb- classes only, tokens only, no Bootstrap utilities, no border-radius, status always with text. Patchbay is vendored under `web/vendor/patchbay` (version in `VERSION`, v2.1.0; upgrade guide: upstream `transition.md`); copy missing icons from upstream, don't fake them. Rules from v2: the whole UI scales with `html { font-size: 125% }` (phone 100%), never `zoom`; sizes in rem; numbers use `--pb-font-num` (Sans here), `--pb-font-mono` is real mono for code/hex; no per-theme CSS; tooltips are `data-pb-tip` (+ `pb-tip--end`), the script-placed cut-off tip is `.pb-tip`; green buttons are `pb-btn--ok`; icon-only ghost buttons need `pb-btn--icon`; `layout.js` sets `data-pb-layout="phone"` next to `data-layout`.
- Users never ride the `hello` (it goes to locked pages too): `hello()` blanks `cfg.users`. Names come in `lockState.names` (only when the page isn't locked; `S.userNames`), PIN lengths in `lockState.lens` for everyone, and the Users editor asks `usersList` (needAdmin, reply `usersListResult`). Keep a new user field out of anything sent before unlock.
- Confirm dialog: random churning letter + lockout (default 500ms; Enter optional).
- Version (#95): `Version`/`Stage` in `internal/app/version.go` (`MAJOR.MINOR.PATCH`), sent in `hello` as `BuildLabel()` (with the short `Commit` the Dockerfile injects), shown in Settings, noted in README's `**Version:**` line. **Every release bumps both** and gives `CHANGELOG.md` a section (#147); `TestVersionNoted` fails if they differ, or (with `SODE_RELEASE_TAG=v1.5.0` / `v1.5.0-rc.1`) if the tag differs or the heading still says unreleased. Release flow and image tags: `RELEASING.md`. Nothing may push `latest` except `promote.yml` (never an rc or `edge`).

## History, ext and follows

JSONL history plus a shared server-side recent/undo list. Routes made elsewhere are `ext` entries (`ext.go`, `ext_burst.go`, `ext_ownership.go`, `ext_follows.go`):
- Connected messages none of our takes sent, plus `found` entries (#57): a tally (resync or interrogate) differing from a *known* cached value that isn't a take in flight or one that just gave up (`awaited`, `late` keys for 5s). Found entries are never follows, are grouped apart, and show as `found`.
- `own` holds each take's (dst, wire level, src) for `ownFor`; keys are used up by the router's answer, so the same route made elsewhere right after still logs. Changes are collected into bursts (end after 500ms quiet or 3s total), logged one entry per dst+src; a burst over several dsts shares a `group`.
- **Follows** (#53): an `ext` change of the same src to another dst within 500ms of one of *our* takes (`waiter.cause` → `a.causes`). Of several that fit, the one whose last confirm came latest wins (`followed`). Panel changes are never followed. Followers of a take in a multi-take confirm carry `followGroup` and `histRows` lists them as `f.followers` (a Followers row at the bottom of the folder, not in `f.entries`, so Undo all leaves them; desktop keyboard stop `w<group>`). Otherwise the follow is written with `follow` = the take's ID, ungrouped, and `histRows` attaches it as `e.follows` unless filters hide the take. Undo plans carry follows as `plan.extra` (one per dst, the oldest), sent only if the confirm's box is ticked. A burst that might follow a take still in flight waits for it (`extAwaitsTake`), only once its connects went out (`cause.sent`). An undo's confirm flags levels where dst no longer has the undone take's source (`changedSince`; skips `Failed` levels and entries without `Failed`).
- Repeated same-dst/same-levels `ext` entries within 30s merge into one row (newest, oldest's `prev`, `merged` count, `chain`); any other entry on that dst, even hidden, breaks the chain. `stackSteps` in `widgets.js` shows a stack as a timeline; older steps have Restore (`restorePlan`, `plan.at`).
- `histRows` then applies this browser's Recent filter (`filterstore.js`, `localStorage['sode-filter']`: kinds plus `src`/`dst` expressions). Folders keep every entry in `f.entries` (Undo all covers the whole confirm) and visible ones in `f.shown`.
- Stacked sets (#131): set buttons toggle (`toggleSet`). One set is `sode-filter-active`. Two or more are a stack, `sode-filter-stack` `[{scope,name}]`, with no active set; `filter` is the first one's, each set's saved filter judges an entry by `stackAllows` (`filter.js`, pure) and pref `setStack` says whether all must allow (`and`) or any may (`or`; a set's excludes and kinds count only inside it). `useSets` is the one builder (missing sets drop out); `setActive` the one writer (also drops cached matchers). `setFilter` is the edit path and leaves a stack. `snapshot`/`restore` put set or stack back (share-link Undo). The dialog shows "A + B", edits the first, and turns off Save as and the share link while stacked.
- Filter language: `web/filter.js`, pure, no imports; the server's `hiddenDsts` uses it too and is evaluated only in browsers. Filter sets come from the built-in All, `cfg.filterSets` and `localStorage['sode-filter-sets']`; active one is `sode-filter-active` `{scope, name, base}`; `followGlobal()` on hello applies a changed global set unless the browser edited it. Names unique per scope, ignoring case.
- Quick search (`setSearch`, `[data-search]` boxes): not kept, doesn't merge rows, reads back in 500-entry pages (`history` takes `n`, server caps at 500). Ignores the filter unless `sode-search-filters` is `on`. `web/filters.js`: the dialog, share links, empty-state note.
- **Redo** (#153): every history row and folder has one Retry/Redo button (`againPlan` in `plans.js`; `againButton` in `widgets.js`). Failed takes retry (a folder with failures retries just those); every other row redoes src to dst on its levels as a plain new take, including undo, ext/found and follow rows. Skipped only with no real source or no existing level (`canRedo`). Frontend only. Undo, Redo and Retry are outlined `pb-btn--sm`; Undo carries `undo-2` and Redo `redo-2`, Retry is text only. The phone's swipe-reveal Undo (`sode-m__undo`) hides the icon in CSS. Verb wording lives in `VERBS` (`plans.js`); only a `patch` resets the boxes (`VERBS[verb].resets`). The confirm shows "Already there" (`alreadyThere`) when dst already has the source on every level. Desktop keyboard mode: `r` does whatever the button says.

Desktop Recent is set apart from the patch boxes and Presets by a thin divider (`#patch-view > .sode__history`, end of `web/history.css`); the phone has none.

## Shared saves and owned fields

- Filter sets and presets save through one path: `saveShared` (`app/shared.go`: takes `cfgMu`, `guardSave(c, true)` re-checks the settings PIN or a trusted user inside it, `update` mutates a copy then Normalize+Validate+save, optional broadcast of one small message, not a hello) and `replyOp(c, kind, id, n, noun, err)` (logs the command as `kind`, answers `<kind>Result` echoing `id`, sets `locked`). New "saved apart from Settings" features use both. Name rules (count, empty, 32 runes, unique ignoring case): `validateNames` in `config/names.go`.
- **Owned fields**: Config fields saved outside the Settings form carry `owned:"true"` (filterSets, presets, settingsPin, deviceDefaults, users). `saveSettings` does `cur.KeepOwned(live)` (reflection, `config/owned.go`), so a stale browser copy can never change them; only the PIN dialog and `keepDefaults` handle the PIN and device defaults after that. A field the form saves carries `guard:"router|pin|open"`: `router` (reconnects; `applyConfig` asks `config.Changed(old, c, "router")`), `pin` (only the settings PIN may change it) or `open`. `TestEveryFieldChooses` fails if a new Config field has neither tag. The Settings dialog also strips owned lists from its `config` message (`OWNED_KEYS` in `owned.js`; socket read limit `wsReadLimit`, 64 KiB; `TestMessageSizes`, `TestSettingsIgnoresOwned`).
- Blocks whose inputs are saved apart from the Settings form carry `data-apart` (This device, lock, Users, `#config-file`): the unsaved-changes check skips them. `emit('settingsClose', {discard: true})` closes Settings discarding the form.

Grid (full-page button panels at `/grid/<link>`) is parked on branch `archive/grids` (issue #150); `grids:` and `gridConfirm:` in an old config.yaml still load and are ignored.

## Users and locks (#151)

Optional and off by default. `cfg.Users` `[{name, pin hash (json:"-"), len, trusted, persistent}]` (`config/users.go`, <=12, unique names ignoring case, PINs 4-12 digits and unique across users), `cfg.Locks{main,log}`, `cfg.AutoLockMinutes`. A lock needs >=1 user and a settings PIN (`Validate`; `-reset-pin` turns locks off). The user list (and `maxPinLen`) is saved only by the `users` message (`SaveUsers`), which needs a settings PIN and the connection settings-unlocked (a trusted user is NOT enough); `saveSettings` carries it over. **Locks and auto-lock are ordinary Settings fields** (Settings > Access) tagged `guard:"pin"` (`trustedMayNotChange`, `guardedErr`); a `config` message WITHOUT a `locks` / `autoLockMinutes` key keeps the live values (`configMsg` records presence; a missing key must never read as every lock off). Web `GUARDED` in `lockrules.js` mirrors the tag.
- **Policy table** (`internal/app/policy.go`): ONE map from every client-to-server message type to what it needs, checked once by `admit` before the read loop's `switch`, and closed: an unlisted type is dropped. `TestPolicyCoversEveryMessage` parses `http.go` and fails if a `case` is missing (or the table lists a type the loop doesn't handle). The file header comment lists one line per type. Needs: `open` (`hi`, `userUnlock`, `userLock`, `userSetPin`, `unlock`, `lock`, `history`; each has a comment saying why), `needTake` (`batch`: main lock), `needMain` (`refreshNames`; `clearHistory` also `needAdmin`), `needLog` (`sent`, `uptime`; admitting `sent` sets `c.sent` in the same step under `mu`), `needAdmin` (`users`, `clearHistory`: the settings PIN unlocked when one is set, **and not the main lock**, so a locked wall panel can still save with the PIN), `needTrusted` (`config`, `filterSets`, `presets`: settings PIN unlocked, OR the connection unlocked as a user who still exists with the same PIN hash AND is `Trusted` *now* in the live config (`trustedLocked`)). `config` is `needAdmin` instead when it carries `pin` or `clearPin` (`rule.strict`, `rule.forMsg`). `guardSave(c, trusted)` repeats the check under `cfgMu` (`saveSettings` passes `trusted=false` when pin/clearPin are set). A refusal logs a `locked` command and answers the same way everywhere: `lockState` for a page lock, `locked` for a settings PIN, and for a type with a result a failure echoing the id (`<op>Result` with `locked`; a refused `batch` gets a failed `takeResult` per item).
- **What the locks cover**: *actions and log reads*, not data. `hello`, names, tally, recent history and history reads keep streaming to a locked browser by design. Main lock: `batch`, `refreshNames`, `clearHistory`. Log lock: sent log and uptime graph. The page declares its type with `hi` (`{page, token}`, sent on every new socket by `lock.js`; default `main`); `/healthz` and `/api/health` stay open. History `Client`, `Why.By` and event `By` use `c.who()` (user name, else IP).
- **Access state** (`users.go`): `client.u` is a `connUser` (page, session token under `mu`; the unlocked `*config.User` in one `atomic.Pointer`). `pageAllowed(c, gate)`: the gate's lock is off or the connection is an unlocked user who still exists with the same PIN hash. `settingsUnlocked(c)` is the settings PIN; `trustedLocked(c)` is PIN or trusted user. `...Locked` means "caller holds `mu`". `syncAccess(c)` sends the lock state (`user`, `trusted`, `persistent`, from the live config) and stops the sent feed for a connection no longer allowed it.
- **PIN pools** (`pin.go`): `pinPool{state, wait, maxTries, resetOnOK, forget, what}` and ONE method, `tryPin(pool, from, check)` (takes and releases `mu` itself). `a.pin` (settings PIN): waits double from 30s after the 5th wrong try, up to an hour, `pinMaxTries` locks it for good, starts over on a right PIN. `a.userPin` (`userUnlock`): same waits capped at 5 minutes, no permanent lock, a right PIN does NOT reset the count (a holder of one valid PIN could otherwise guess the rest); forgotten after an hour with no wrong PIN. A success or lockout in one never touches the other. PIN only, no name; a PIN of a length no user has is just a wrong try.
- **Persistent sessions** (`tokens.go`, user flag `persistent`, "Never log out"): `userUnlock` for a persistent user also issues a token (`issueSession`, after the unlock; no disk I/O under `mu`): 32 bytes crypto/rand, base64url; only its sha256 is kept, in memory and `tokens.json` beside the config (0600; temp file in the same dir, fsync, rename, dir sync; loaded once in `New`). A record is `{user, pin hash, at}`; `tokenStore.user(t, cfg)` re-reads the live user on every use, so a changed PIN, removed/renamed user or unticked Persistent kills it at once. At most `perUserTokens` (8) per user and kind, oldest dropped. The result is `userUnlockResult.token`; the browser keeps it in `localStorage['sode-session']` and sends it in `hi`; a valid one brings the connection up unlocked with no PIN (a wrong one is ignored). `lockState` carries `persistent`, so the idle timer skips that session; the server stays the authority. `userLock` ALWAYS revokes the connection's token (and relocks other connections holding it), so Lock, Log out and Ctrl+L can't be undone by a reload. Non-persistent users: idle timer, reconnect asks for the PIN again. Old `tokens.json` of admin tokens loads as nothing; a damaged file is forgotten.
  - **Catching up (#159)**: `catchUpSessions` (end of `applyConfig` and `UserSetPin`, off `mu`) gives every connection unlocked as a persistent user with no good token one, sent as `{t:"session", token}`; `lock.js` keeps it while logged in. `issueSession` is idempotent and drops its token if the connection was locked, or given a good one by a racing call, while the file was written.
  - **localStorage, not a cookie**: the WebSocket `hi` already carries the token, so no HTTP endpoint, cookie flags or CSRF thinking is needed. Trade-off: a cookie could be HttpOnly; but the page builds all router-supplied text with `el()` (no `innerHTML`), the token only works as that user, and a server-side cap and revoke exist. As strong as the browser profile either way.
- **Hardening**: revocation is durable: `tokenStore.prune(cfg)` deletes every record invalid against the live config, run at the end of `a.update` and in `New`; untick/re-tick Persistent, rename A->B->A or a PIN changed and restored never revive a token. Tokens die after `tokenMaxAge` (90 days) unused; a `hi` with the token, or its connection still open (`touchSessions`, hourly from `periodic`; `tokenStore.touch` rewrites only when over a day old) renews it. `userSignOutAll {name, id}` (`needAdmin`, `SignOutAll`, button per user in Settings > Users) deletes a user's tokens and relocks their connections. `UserUnlock` clears the connection's token. A trusted-only Settings save may not change `router`, `trustedProxies` or `pinMaxTries` (`trustedMayNotChange`; `guardedErr` counts as `errLocked`, so the page asks for the PIN; `guardedEdited` in `lockrules.js` makes settings.js ask up front). **CSP**: `secureHeaders` in `http.go` sets one Content-Security-Policy (`script-src 'self'`, inline style attributes allowed, `frame-ancestors 'none'`), `nosniff` and `Referrer-Policy: same-origin` on every response; pages must have no inline script bodies, `on*=` handlers or `javascript:` URLs (`TestNoInlineScript`).
- **Trusted users**: the flag lets a connection unlocked as that user make LOW-RISK saves with no settings PIN (Settings form, `filterSets`, `presets`). Always the settings PIN: `clearHistory`, Settings fields whose `guard` is `router` or `pin`, `users` (users, maxPinLen), any change to the settings PIN. The server sends `trusted`, `lens` (PIN lengths users have, so every pad follows a PIN change) and `hi` (set only on the answer to the page's own `hi`; `lock.js` forgets its token only on that one) in `lockState`; `pin.js` keeps `trusted()` (fed by lock.js's `access` event) and `needsPin()` (`lockrules.needsPin`, pure) is what Settings (`renderLock`) and `globalsave.js` ask instead of `S.pinSet && !unlocked()`. This only hides the prompt: when the server refuses, `demandPin()` makes `needsPin` true again until the PIN is entered or Settings close/relock.
- **Removed (the admin browser)**: `adminUnlock`, admin-password sign-in, "Forget this browser", "Never auto-lock this browser" (`sode-lock-never`), `userLock {suspend}`, `exempt` in `lockState`, the "admin" chip text, old admin tokens. `lock.js` deletes the old `sode-lock-token`/`sode-lock-never` keys. A wall panel logs in once as a trusted + persistent user.
- **Frontend**: `lock.js` (overlay, `lockState`/`userUnlockResult` via `onMsg`, Ctrl+L, idle timer; emits `locking` as it comes down (settings.js answers by exiting), `unlocked` (log.js asks again) and `access` (pin.js, settings.js); remembers and restores the focused element), `lockrules.js` (pure, Node-tested), `lock.css`, `users.js` (#165/#168: Settings > Users is a one-line summary and a "Manage users…" button (`#users-manage`, `data-find`, DICT `users-manage`); the editor is its own `pb-modal` with `trapDialog`: one row per user (name, PIN, Trusted, Never log out, Sign out everywhere, Remove), then lock main/log, auto-lock minutes, longest PIN, own Cancel/Save. Asks `usersList`, saves with `users` and closes on success, shows the server's error text, calls `demandPin()` on a locked refusal; holds no rules. Esc/Cancel with edits warns once; `locking` closes it; it holds no inputs in the Settings form). Modals other than Settings are closed by `lock.js` clicking their Cancel/Close.
- **Lock polish**:
  - **Chip** (`lockchip.js`, built with `el()`): "Logged in as <name>" fixed top left below the lost-link banner (`--sode-down-h`); on the phone under the fixed header (`--sode-head-h`, measured in `lock.js`). One icon-only lock button (`data-pb-tip` "Lock (Ctrl+L)"); no menu. **Account block** (index.html, in This device, hidden unless `access` says a user is logged in; `data-find`, DICT `account`, `account-pin`, `account-logout`): Change my PIN (bus `changePin`, dialog in `lockchip.js`) and Log out (bus `logout`: ends the session, revokes the token, shows the pad).
  - **Phone**: no lock button in the chip (CSS hides it, and the whole cell until a lock screen shows its closed lock: `.is-hand`); the lock screen's brand text wraps. A phone locks by idle, the hand lock in Settings, or logging out.
  - **Chip glide**: the chip's left/top transition exists only while `data-sode-lock` is set; its top follows the lost-link banner (`--sode-down-h`), which must jump, not float.
  - **Animation**: the logo's move is the Web Animations API (`moveBrand`, `brandFrames` in `lockrules.js`): one run each, brand at rest when measured, fresh keyframes every time. The way out lasts `OUT_FACTOR` (1.5, `--sode-lock-out`) times the way in; the pad body fades in after half the motion and out at once; the root is hidden after the longest plus 100ms. Reduced motion = no animation (the text still shows). `shouldFly(rect, scrollY, innerHeight)`: the logo flies only for an unscrolled page whose logo is fully in view; otherwise brand and overlay just fade.
  - **Pad feedback** (`feedback`/`clearFeedback` in `lock.js`, `wrongFeedback` in `lockrules.js`): correct PIN says "Welcome, <name>" and the unlock runs after `WELCOME_MS` (600ms; keys ignored meanwhile). Wrong PIN shakes (WAAPI) and says "Incorrect" for `WRONG_MS` (1s); a wait note from the server goes under it; other refusals stay in the field until the next key. Text always carries the status.
  - **Scroll**: the page keeps its scroll through lock and unlock (`preventScroll` focus, `data-sode-lock` on `<html>` stops desktop.js's focus-scroll, position restored).
  - **PIN pad**: submits by itself only at the LONGEST length in use (`sendDelay` is null for shorter ones, so a pause after 4 digits never sends 1234 when 12345 exists). The check key and Enter send what is typed if a user has that length (`sendable`). The pad stops at `min(longest, maxPinLen)`.
  - **maxPinLen** (`config.MaxPinLen`, `SODE_MAX_PIN_LEN` seeds, default 8, 4-12, owned: saved by `users` with `usersReq.maxPinLen`, 0 keeps). `Validate` rejects users whose `len` is above it; an older file gets max(8, longest user PIN) in `Normalize`. `CheckUserPinRules(pin, max)`.
  - **userSetPin** `{old, new, id}` -> `userSetPinResult`: policy `open`, but the handler requires the connection unlocked as a user; `old` is a try in the user PIN pool; `new` follows the PIN rules and uniqueness; saved with `update` without the settings PIN; this connection stays unlocked, the user's other connections relock (their tokens die with the old hash).
  - **Who made it**: Sode takes by a configured user show a small "by <name>" (`byLabel` in `widgets.js`, `actorUser`/`folderActor` in `lockrules.js`); never an address; ext/found show nothing; a folder shows it when all its takes share one user.
- **Tab login (no lock on)**: with users but no lock, Settings > This device shows Log in (`account-login`, bus `login`): the PIN pad with Cancel/Esc. `userUnlock` carries `tab: true`; the server (`issueSessionTab`) issues a token marked `tab` for a non-persistent user, only where the page's lock is off, same caps/prune/revocation (`valid`: a Tab token is valid only while its user is NOT persistent, for `tabTokenMaxAge` (48h, an open tab renews it); a persistent token only while persistent; `Hi` ignores a tab token once the page is locked). The page keeps it in sessionStorage (`sode-tab-session`), sends it in `hi` (`hiToken`). No idle lock; Log out and `userLock` revoke it. The hand lock screen has a small **Log in as…** (`loginAsOffered`): it ends the hand lock and starts the login (`loginFromSoft`); Cancel/Esc returns to it; success releases it. The page's lock view is ONE value (`V = {mode: 'page'|'soft'|'login', back}` in `lock.js`, pure transitions `softLock`, `softUnlock`, `startLogin`, `cancelLogin`, `lockArrived`, `loginWon`, `viewBody` in `lockrules.js`); a `lockState` ends a login only on a real unlock or an enforced lock. `lock.js` emits `handlock {on}` when any lock overlay goes up or down (`transfer.js` uses it). **Chip motion**: `<html>` carries `data-sode-lock` while any lock overlay is up (chip z-index above the overlay) and `data-sode-lock-on`, set and cleared exactly with the overlay's `is-on`, driving the chip's geometry so its slide starts and ends with the border (`--sode-lock-motion` in, `--sode-lock-out` out; 0ms under reduced motion). Its lock button shows `lock-open` when unlocked and `lock` once a lock is up (`chip.setLocked`); the button is hidden under the hand lock, where `.sode-lock__who-ico` shows a non-interactive closed lock.
- **Hand lock (#158)**: where no PIN lock is on for the page (`!L.enforced`) Ctrl+L, or Settings > This device > Lock screen (`#soft-lock`, bus `softLock`), puts up the overlay with its second body (`softBody`; bottom row **Log in as…** and, when logged in, **Log out**, which ends the session but keeps the hand lock): "Press X to unlock" with a churning letter (`churnKey` in `lockrules.js`, shared with `keyconfirm.js`) and an Unlock button for touch. The idle timer puts it up after `autoLockMinutes` (`softIdleLock`, only where no PIN lock is on). An enforced lock arriving cancels it. A guard against mashing, not security.
- Not done: idle lock is client-side (a persistent user skips it); a non-persistent user's reconnect asks for the PIN again.

## Profiles (#161), guests (#187) and sharing (#169)

A **profile** is a user's own saved This device settings, filter sets and presets, kept on the server so they follow that person to any browser. Third scope **Me**, beside Everyone (`global`) and This browser (`local`). Only exists where users do: no users, or nobody logged in = no Me options, wording or buttons, and a guest gets this browser's and everyone's values.
- **Config**: `User.Profile` (`config/profile.go`: `Prefs` map of pref name to value string as in `web/prefs.js`, `FilterSets`, `Presets`; `json:"-"`, never rides the `hello`). ## Communication Log (#72, `/log`)

Every message written to the router, captured at the wire, plus event rows (#139). `swp08.Client.OnTx` fires once per message from `transmit` (after ACK/NAK/give-up, with `Tries`) or for messages still queued when a session ends (`dropped`); `sendMsg` logs `unsent` when `Send` refuses. Each `Send` carries a `swp08.Why`. `OnTx` only pushes onto `txq` (never blocks the ACK-gated writer); `logSent` decodes (`swp08.DescribeTx`), appends to `SentLog` (`sentlog.go`: JSONL with its own `seq`, rotated to `.1` at half of `SODE_SENTLOG_MB`) and queues `sentAdd`/`sentPage` (both carry `total`) for connections that asked (`client.sent`). A failed write keeps its seq unused and isn't broadcast (`txLost`), so seqs have no gaps; a damaged file is renamed `.bad-…`, not fatal. `Send` pushes under `c.mu` and the session drains the queue after the writer exits, so every queued message gets a TxEvent. Read-only, no clear, no PIN.
- **Events (#139)**: kinds `browser` (WebSocket connect/disconnect, `By` = IP), `command` (batch as take/undo/retry, refreshNames, clearHistory, config, filterSets, unlock ok/refused, lock; never a PIN or settings), `link` (router `up`/`down`/`changed`) and `server` (`start`/`stop`). They have `cmd`/`wire`/`dst`/`src` -1 and empty hex (`event()`; the page tells them by `EVENT_KINDS` in `logkinds.js`), with `Note` for detail. `logEvent` only pushes onto `evq`; `logSent` is the single writer of both `txq` and `evq`, so seq, file and live feed agree; on shutdown it drains both and writes `stop`. `Run` waits for it and `main` waits for `Run` (3s). `logLink` (under `mu`) logs `down` once per outage (again if the error changes) and `up`; `applyConfig` on a router change resets it, logs `changed` and marks uptime down because `SetTarget` never reports down. `problem()` in `log.js` is per kind. Default kinds are Connects, Commands and Router link; a saved list of all six older groups is All.
- **Uptime graph**: `uptime.go` keeps JSONL (`SODE_UPTIME`) of state changes (`up`/`down`/`off`; connecting counts as down) and per-minute counts of bad (not ACKed, or tries > 1) and slow (`AckMs` over `slowAckMs`, 300ms) messages, counted in `logSent` before the append. No file I/O under `mu`: `State` and `Note` only change memory and `Run` writes (5s), plus `<path>.alive` every minute; `Stop` (after `logSent` is done) writes `off` and the minute being counted. Opening a file whose last state isn't `off` adds `off` at the alive stamp; lines older than `uptimeKeep` (400 days) are dropped, keeping the last state before the cutoff. The `uptime` request (`from`,`to`,`slot`,`id`) is answered by `uptimeReply` with the range cut to `uptimeKeep` and counts summed per slot. `web/uptime.js` (pure, Node-tested) makes the colours: red = no up time, yellow = partly down or bad/slow, grey = no record; one strip, toggles (1h/24h/7d/30d, labelled with slot length by `presetText`) that set the log's From (`chipOn`; cleared by a hand-typed time or Clear times); with no times it shows 24h, with times typed by hand those (`rangeFor`). Bars are buttons: `enterSlot` (`slotMode`) sets From/To to the slot, forces newest first and shows the `#log-slot` banner; Back restores times, chip and sort, any other time change just leaves the mode. Not kept across loads; `slotFor` keeps it under 200 slots.
- **Page**: `web/log.html` + `log.js` import `core.js` and `device.js` but not `initTheme`; filter in `localStorage['sode-log-filter']`. `web/logpager.js` (`newPager()`, pure, Node-tested, #141) owns the list, one pending request (reply accepted only if it echoes that `before`) and the open/Load older/range reads: it keeps reading (500 at a time, up to 20 requests) until 100 *shown* rows more, since the default filter hides most entries.

## Architecture

- `internal/swp08`: framing (`frame.go`), message builders/parsers (`msg.go`), `Client` (`client.go`): one TCP session with reconnect and a keepalive probe (an interrogate, on connect and after 10s without rx). Up is reported, and `Send` accepts messages, only after the router's first reply. `SetTarget` reconnects without reporting down. A probe with no reply drops the link (~13s); any other unanswered message just triggers a probe. Rx times are monotonic offsets (`lastRx`), ACK-gated writer. Messages sent while disconnected are dropped. Callbacks `OnUp`/`OnMsg`/`OnState`.
- `internal/app`: `App` owns all router state (names, tally, protect, keyed dst → **UI level**) under one mutex. Config is an immutable `runtime` behind an `atomic.Pointer`; `ApplyConfig` saves, swaps and, if router-side fields changed, clears state and calls `SetTarget`. `Run` ticks every 100ms: `flush()` batches changes into broadcasts and finishes name refreshes, `periodic()` re-polls names/dumps.
  - Takes (`take()` = `prepare` + `complete`): plan → check → register → send → wait → collect, one `takeLevel` per level in the `waiter`. Tests drive takes through `App.sendMsg` with a fake router (`take_test.go`).
  - Check (`checkTally`, #57) interrogates every level and waits up to 1s so `Prev` (which undo restores) comes from the router, not a cache that misses unannounced changes (falls back to the cache). It skips levels reported within `checkFresh` (15s, `seenAt`) and every take of a confirm of `bigBatch` (6)+ (`takeReq.NoCheck`), trading undo accuracy for router load (#91).
  - Router load: one message per ACK, so a take's timeouts count from when its last message was written and ACKed (`Why.Done`, closed by `Client.tx`; `sendTracked`, `leftQueue`, `queueMax`), and `own` keys are registered for `queueMax + ownFor` then shortened to `ownFor`.
  - Late answers: a take the router answers late is claimed (`lateTake`, `lateFor`; only for levels the router said nothing about) and its entry amended (`lateWorker`, one `History.Update` per entry, `Entry.Late`, a `recent` message with `update`).
  - Failures (#15, #17): the cache holds only what the router reported, so the next `Prev` is the actual state. `waiter.see` keeps the latest route reported for unconfirmed levels; `whyMissing` writes `Failed` and `Now` (`[ui level, src]`, -1 = nothing) to the entry; a level the router reports on src after all is `already` (#36). `Err` says each level's outcome. Undo of a failed take (`undoItem` in `plans.js`) leaves out levels in `Now` and keeps no-answer levels.
  - A router change cuts takes in flight (#106; `cutTakes`): they fail with "the router changed", and a waiter keeps the `extTracker` it started on.
  - `history.go`: JSONL log with paging; a page never ends inside a group.
- `internal/app/http.go`: `/` static, `/healthz`, `/api/health` (#140: server vs router health for uptime monitors; 200 only while the router is up, else 503; no PIN, no config), `/ws`. One WebSocket per browser, JSON with a `t` field. Client → server: `batch` (all takes of one confirm; at most 8 at once, multi-take batches share a history `group`), `history` (+ `before`, echoed, `n`; `takePage` keeps a page only if it's for its current oldest entry), and the rest per the policy table. Server → client: `hello` snapshot (carries `pinSet`, `version`), `status`, `names`, `namesChecked`, `tally`, `protect`, `unlockResult`, `locked`, `ping` (heartbeat every `wsHeartbeat`, 5s, through the writer goroutine; browsers can't see WebSocket ping frames, #142), history/results. Client IP honors `X-Forwarded-For` (all header lines, nearest untrusted hop; `X-Real-IP` when none) only from `trustedProxies`; a hop that isn't an address ends the search at the peer.
- `internal/config`: `Defaults` → `FromEnv` (seed) → `Normalize`/`Validate`; YAML load/save; `LevelMap` does UI↔wire levels.
- `cmd/swp08sim`: fake router; must keep mimicking real Ultrix quirks (e.g. no Connected for no-op connects).

## Verified against the real Ultrix (2026-10-22, 172.17.60.101:8910)

- UI level 1 → wire level 0 (`SODE_LEVEL_WIRE_OFFSET=-1`), display number = wire + 1 (`SODE_NUM_OFFSET=1`).
- Standard name requests (100/102) with 12-char names work. ~2690 sources, 720 destinations.
- Extended tally dump (0x95 → 0x97, 64 per message) works on all 17 levels; source 0xFFFF = nothing routed. Extended connect (0x82) is confirmed by 0x84.
- Routers send Connected only when a crosspoint *changes*; a matching connect gets no reply, so `take()` interrogates (0x81 → 0x83) levels already on the source, and any level still unconfirmed at the 3s timeout gets a 1s interrogate grace; those are reported `already`. The simulator mimics this.
- The router does **not** announce every change: 2026-10-23 KiPro 4 went UDX 04 → UDX 03 with no 0x84 to Sode (the next entry's `prev` showed it). Hence `found` entries and the pre-take check. Also 2026-10-23 18:01:40 the router sent 0x84 for a route Sode didn't make (PIX 03 to DSM 03 and MV08 PIP015), logged as an `ext` burst; source unidentified.
- Extended protect dump (0x93 matrix, level, startDst(2) → 0x94 matrix, level, count, firstDst(2), count × 2 bytes): state in bits 4-5 of byte 1, device in the rest. Dest 65 was protected by device 9 on all levels. Single protect change messages (0x8B/0x8D/0x8F) not yet seen live.
- **2026-11-02 (branch `spike/salvo-probe`, `cmd/swp08probe`)**: 51 ordinary extended connects take ~840 ms to land, one destination after another (~16 ms per crosspoint); pipelining writes saves under 10%. Group salvos work (contrary to the spec's "XD and Eclipse only"): 120 is answered by 122 echoing its 5 data bytes, 121 by 123 (`00` set, `01` cleared, `02` nothing to do; a clear of an empty group answers `02`), both in ~5-7 ms. Standard layout: 4-bit level, numbers < 1024, group 0-127; the probe used group 127.
- **0x84 after a Go is not reliable**: the spec (SW-P-88 Issue 4b 8.1.5) says a Go sends none, and uninstrumented runs saw 0 (standard-only Go) and 3 (mixed). Instrumented runs got one ordinary 0x84 per staged crosspoint, in destination/level order, ~3-5 ms apart, from ~100-130 ms after the Go to ~270-340 ms for 48-51 crosspoints. So a group Go announces its crosspoints about 4 ms apart (51 in ~210 ms) against ~16 ms apiece for ordinary connects; whether the switch itself is simultaneous is unproven (it needs a scope). Sode must work whether or not the router announces.
- **Extended stage** 248 (`F8 <matrix> <level> <dstH> <dstL> <srcH> <srcL> <group>`) is acknowledged by 250 (`FA` + the same 7 bytes), is held in the group, and a standard Go (121) fires extended-staged crosspoints too (#154). So level 17 and numbers >= 1024 can ride a salvo; a Go-clear clears both kinds; extended-staged crosspoints may be announced with an ordinary 0x84 after the Go.

## Presets (#152; first called salvos, renamed in #162)

A **Preset** is a saved set of takes. It is named apart from the router's own salvos, and the code keeps the two apart: `preset` is the saved set (config `presets`, message `presets`, `Entry.Preset`, localStorage `sode-presets`, CSS `sode__preset*`), `salvo` is only the router feature (`fireMode: native`, `salvoGroup`, `fire.go`, `swp08/salvo.go`, the `salvo*` sent-log kinds). Old data still loads: a `salvos:` key in `config.yaml` (`Config.LegacySalvos`, moved by `Normalize`), `"salvo"` in history lines (`Entry.UnmarshalJSON`), `sode-salvos` and `sode-salvo-pins` in localStorage (`migrateLegacyKeys` in `presetstore.js`), and `salvo` on a `batch` from a page loaded before the rename.

`config.Preset` `{name, items: [{src, dsts, levels}]}` is all numbers (internal src/dst, UI levels, `[]` = `defaultLevels`), never names. Caps in `internal/config/presets.go` (30 presets, 100 sources, 100 dsts per source, names unique ignoring case). ## Native salvos (#154)

`fireMode` (`sequential` default | `native`, global, no reconnect) and `salvoGroup` (0-127, default 127). Code: `internal/app/fire.go`, builders/parsers `internal/swp08/salvo.go`. Native mode makes a confirm's routes land closer together (see the measurements above); it is not promised to be one frame.
- **When**: `batch` with 2+ items in native mode runs `markStages`, which sets `takeReq.Stage` (wire levels to stage) per item: every level that exists on the router (`ExtSalvoFits`), and a dst+wire level used once in the batch (twice = neither staged, an ordinary connect). If 2+ items have something to stage it goes `batchNative`, else sequential. **Stage command rule**: `fireSalvo` stages a level that fits the standard layout (`SalvoFits`: matrix and wire level 0-15, numbers 0-1023) with 120, anything else (level 17, numbers >= 1024) with the extended 248; both ride the same Go. Protected and bad takes drop out in `prepare` as ever; if fewer than 2 staged takes are left, all are sequential.
- **Phases**: `batchNative` prepares every take (takeLimit at once; bigBatch NoCheck as today), then `fireSalvo` under `App.fireMu` (one fire at a time, never holding `mu` across waits): Go-clear and wait for its 123 (none = router without group salvos: fall back), stage each native level (`stageChunk` 64 queued at a time) and wait until **every** 122 or 250 has come back, matched by decoded bytes (`swp08.Staged`; a stage the link gave up on gets no ack, so the Go never fires with one missing), then Go-set (121) and wait for 123. A deferred Go-clear runs after every fire. Acks reach the fire through `a.fire` (`fireState`, set only while a fire runs; `onRouterMsg` → `onSalvoAck`, dropped otherwise), each command waits `salvoReply` (1s) after its ACK. Then every take runs `sendTake` + `complete`: `sendTake` skips connects for native levels and interrogates them (as for `same` levels), and the waiter is confirmed by whichever comes first: a 0x84 (if announced) or the tally.
- **Waiter rules**: `takeLevel.native` levels get `own` keys exactly like sequential ones (`register`/`ownKeys`), because the router may announce the Go with 0x84 (then it is ours, confirms the level, and is not `already`). `see` sets `already` for them only if `l.same`. A native level a tally confirmed keeps its key until `goAt + salvoAnnounceFor` (2s) in `unregister`, then it expires with nothing logged. A 0x84 for a route the cache already has still uses its key up (`applyTally` else branch) and `sawOwn` extends the latest matching cause, so follows of a late-announced destination still tie to the take. The Go resets their `seen`/`now` (reports before it were of the old route) and sets `cause.sent`, plus `cause.saw` for takes with a changed level. `awaited()` keeps the confirming tallies out of `found`; late/lateTake work as for sequential takes.
- **Failures**: anything before the Go (no 123 for the first clear, a missing 122, the link refusing) → group cleared, `unNative` (levels back to connects, own keys added) and the whole batch goes sequential, logged as a `salvo` command row with result `fallback`. Once the Go is sent it is **never** resent nor followed by connects: a missing 123 or `02` is logged (`salvo` `error`) and the interrogates say what happened (failed levels as `still on`, `Failed`/`Now` as ever). On every new session `onRouterUp` clears the group under fireMu (`clearStaleSalvo`), only in native mode: sequential mode sends no salvo command at all. A router without group salvos costs each multi-take confirm a 1s wait before falling back.
- **Log**: sent kinds `salvoStage` (120), `salvoStageExt` (248) and `salvoGo` (121, Note `salvo N: set|clear`), shown in the Connects chip group; 122/123/250 are inbound, so they appear only through `salvo` command events: the fire (`N crosspoints set in X ms`, or `fallback`/`error`) and, after the takes finish, the timing (`logSalvoTiming`: `N of M crosspoints confirmed, the last X ms after the Go (a by Connected, b by interrogate)`). The confirm interrogates usually answer before the router's late 0x84s, so that time is when Sode knew, not when the router switched.
- **Simulator**: 120/248/121 with a staged list per group shared by all clients, 122/250/123 after 6 ms in line, no Connected after a Go set by default, `SIM_SALVO_ANNOUNCE=1` sends one per changed crosspoint from ~110 ms after the Go, 4 ms apart, in dst/level order; `SIM_NO_SALVO=1` ignores all three. `TestNativeFits` runs level 17 and dst/src >= 1024 (mixed 120 + 248, one Go) in all four worlds; `loseExt` in the fake router drops 250s (`TestNativeNoExtStageAck`). `fire_test.go`: `fakeSalvo` in the fake router; `announce` 0/1/2 = no Connected, all, every other one, `announceAfter` the delay; `TestNativeFire` runs all four worlds.
- Not yet seen live through Sode: the extended stage (248/250), the whole path on the Ultrix, whether the switch is simultaneous, whether router follows (PiP after DSM) fire after a Go, and what the router does with a group staged by a session that dropped.
