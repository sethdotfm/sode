# A panel's type is fixed when the panel is made

A panel is a Buttons panel or a Grid panel. The person who makes it chooses the type, and the panel keeps it. The panel file stores it as `type` (`buttons` or `grid`), and a file with no `type` loads as a Buttons panel, so files from before Grid panels load unchanged. The server refuses a change of `type`, and a body with no `type` keeps the stored one, so an older client cannot change it. The API returns `type` so that other programs know which body to expect. For its sources and its destinations, a Grid panel stores membership apart from per-item settings. Membership is "all, in router order" (less any hidden items) or an ordered list of router numbers; only a reorder or an explicit add makes an "all" edge a list. A new Grid panel starts as two empty lists (2026-11-17, owner's alpha notes), as a new Buttons panel starts with no buttons. Pins and artwork are per item, keyed by router number, so a pin does not stop an "all" edge from following the router. An edge pins any number of items (2026-11-17, owner; an earlier limit of 8 is gone, and files from then load unchanged). The page draws as pinned only what fits in half the room, and that band of pins scrolls on its own. A Grid panel has no cells and no Pages. The server refuses a Grid panel body with a non-empty `cells` or `pages`, so a client can send a read back unchanged. Push and Checkpoint sets refuse a target of the other type.

Considered: a type for each Page, so that one panel mixes buttons and a grid. This puts two plans and two key models on one page, and Push, Templates and the Pages bar would each need a rule for the mix. Also a convert action. Buttons to Grid is easy (collect the Source and Destination cells), but Grid to Buttons has no good answer for 2500 sources and the cell layout, so a convert action would work in one direction only. A copy with the other type can come later if people ask for it.
