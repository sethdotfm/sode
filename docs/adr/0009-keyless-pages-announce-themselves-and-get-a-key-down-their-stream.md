# A keyless panel page announces itself, and an Assign sends its key down that stream

A panel page with no working key is invisible to Sode: it never opened a key's stream, so nobody can find it from the panels page, and fixing it means walking to the device or sending a new link. So every panel page with no working key (none yet, a spent setup link, or a key that answered 401) holds an open stream, `GET /api/v1/panels/{id}/instances/keyless`, with no Authorization header. It carries the panel's id or short name, the device name the page holds and whether its key was ended. Sode records the address it sees with `clientIP`, the same address the auth path checks. A Trusted user then sees it in Assign to and assigns it like any instance; the key goes down that stream as its last line, as for a keyed page.

The stream grants nothing. No key, session, user or panel data rides it, and it answers the same whether or not the panel exists, so it is no way to find panels. Nothing comes down it but beats until a Trusted user (or the Advanced Settings PIN) assigns it. A key goes only to the newest stream of the entry, since unauthenticated streams that share an address and name are not known to be one device. It goes only when the device's address is inside the target client's allowed networks; an empty list allows any address, as it does for the key itself, so a check there adds nothing. A target that acts as a user sends no key: the device shows its own sign-in, which runs over the page's socket and Lock, so the idle clock and the held Lock cover it as they cover any other sign-in.

Entries live in memory only, for 24 hours, at most 1000, the oldest dropped; a restart forgets them, as it forgets every instance. A page with no name is listed under the last name a stream from its address carried, else the address. There is no rate limit: Sode is an internal tool, and an announcement that is refused would make a device unfixable.

Considered: a keyless page asking for its key by polling a REST route, which needs a secret to tell its answer from another device's and so gets back to delivering one. Also a pairing code shown on the device and typed by the engineer, which is the walk to the device this removes.
