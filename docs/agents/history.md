# History, ext and External follow

JSONL history plus a shared server recent/undo list. Routes made elsewhere are ext entries (ext*.go).
- Router: `App.record` gives every entry `router` (the router UID) and `routerTitle` (the title at that time). Thus an entry still names its router after a rename or delete. Without SODE_CONFIG the UID is new on each start, so do not match an entry's `router` against the running router's UID.
- Step in: a take made while stepped in has `browserOf` (the original user, or the address) beside `client` (the stepped-in user). Filters and `actorUser` read `client` only; `byText` shows "by Bo (browser of Ana)". docs/agents/users-locks.md.
- Ext: Connected messages that none of our takes sent, plus found entries (#57). A found entry is a tally that differs from a known cached value. It is not a take in flight or one that recently gave up (awaited, late keys for 5s). Found entries are never an External follow and are grouped apart.
- own holds each take's (dst, router level, src); the router's answer uses a key up, so the same route made elsewhere right after still logs. Changes gather into bursts (500ms quiet or 3s total), one entry per dst+src; a burst over several dsts shares a group.
- External follow (#53): an ext change of the same src to another dst within 500ms of one of our takes (waiter.cause, `u.ext.causes`). Each router has its own burst, own keys and causes, so an External follow never crosses routers. flushExt and flushProtExt write the burst of each router, and each entry names its router. An External route entry on the upstream end of a tie line gets `also`, the destinations downstream that it also changes (`noteAlso`, tievia.go). Of several, the latest last confirm wins. Changes at a router panel are never followed. In a multi-take confirm followers carry followGroup and histRows lists them as f.followers (not in f.entries, so Undo all leaves them; keyboard stop w<group>). Otherwise follow = the take's ID, ungrouped, shown as e.follows unless filters hide the take. Undo plans carry the External follow as plan.extra, sent only if the confirm's box is ticked. A burst waits for a take in flight (extAwaitsTake) when it is possible that the burst is the External follow of that take. It waits after the take's connects went out (cause.sent). An undo confirm flags levels where dst no longer has the undone take's source (changedSince).
- Stacked rows (mergeRuns, below): histRows merges changes to one dst on the same levels. Each comes at most stackGapMs() (pref stackGap, history.js) after the one before. stackGap is a This browser pref like setStack: 0 (off), 10, 30 (default), 60, 120 or 300 seconds, kept as text in `sode-stack-gap` and `browserDefaults.stackGap`. 0 never stacks. This is the gap between neighbours, not the whole span, so a monitor punched all day stays one row. Any instance stacks: Sode takes from any browser, panel or API client, and ext entries (merged count, chain). A failed take, an undo or Restore, a Group, a follow, a hidden entry or any other entry on that dst ends the row. Found and announced entries do not mix. No search merges. Frontend only: no wire field, and the only persisted value is the pref. The row shows the oldest prev (stackBefore, stackFrom) "to" the newest src, ids `#oldest–#newest` and a count on the disclosure. stackSteps shows each change as a timeline with Restore (restorePlan). Add from History picks the newest, which is the row's end state.
- histRows applies this browser's filter (filterstore.js, sode-filter). Groups keep all entries in f.entries, visible ones in f.shown.
- Stacked sets (#131): set buttons toggle. One set is sode-filter-active. Two or more are a stack, sode-filter-stack [{scope,id}], no active set. A Me set's ref also holds its user. stackAllows (filter.js) judges per set; pref setStack: and or or. useSets is the one builder, setActive the one writer, setFilter the edit path (leaves the stack), snapshot/restore for the Filters dialog's Cancel. The dialog shows "A + B", edits the first, disables Save as while stacked.
- Filter language: web/filter.js, pure, no imports; the server's hiddenDsts uses it too. A filter set (config.FilterSet `router`) and hiddenDsts (`hiddenDstsRouter`) carry an optional router UID. Blank is the one router. With a router, compileFilter's number and range terms match only an entry on that router. The matcher gets the entry's router as its third argument. filterAllows passes the entry's router, else the hello's routerUid. routerTermsProblem is the rule for a second router: a set with no router allows only name, exact and regex terms. The Filters dialog's editor (filtereditor.js) calls it through `filterProblem` with the hello's router count. With a second router, a number term there is an error and the filter is not stored. Sets come from built-in All (id `All`), cfg.filterSets, Profile.filterSets and localStorage sode-filter-sets {id,name,f}. Each set has a hidden id, as a preset has (config.FilterSet `id`). Normalize gives a blank or repeated id a new one, and WithFilterSetExtras gives a set sent without an id the saved id of its name. The page makes This browser ids and a new set's id (newPresetId). The active set, a stack, bookmarks and Palette picks name a set by scope and id, so a rename moves nothing. Active is sode-filter-active {scope,id,base}; followGlobal() on hello applies a changed global set unless the browser edited it. Names unique per scope ignoring case.
- Quick search: not kept, does not merge rows, reads 500-entry pages (server caps at 500). Ignores the filter unless sode-search-filters is on.
- Loaded entries stay bounded (history.js `trimHist`). Clearing a search drops S.hist back to the newest 200, whole Groups. So does a live take that brings it past 1000 (`HIST_CAP`) while no search runs and no pager shows past 200. `histMore` is then true, so Load more reads the rest again. The desktop page redraws History once per frame for a burst of `recent` messages (desktop.js).
- Redo (#153): every row and Group has one Retry/Redo button (againPlan in plans.js, againButton in widgets.js). Failed takes retry (a Group retries only failures). Everything else redoes src to dst on its levels as a new take, including undo, ext, found, follow rows. Skipped with no real source or level (canRedo). Frontend only. Undo/Redo/Retry are outlined pb-btn--sm; Undo has undo-2, Redo redo-2, Retry text only; phone swipe Undo hides the icon in CSS. Verb wording in VERBS (plans.js); only patch resets the boxes. Confirm shows Already there (alreadyThere) when dst has the source on every level. Keyboard r does what the button says.
- Desktop History sits apart from the patch boxes by a thin divider (end of history.css); the phone has none.
- Row kinds: rowView (historyrows.js) gives each row one descriptor: take, Group, and protects.js's PROTECT_ENTRY and PROTECT_GROUP. Desktop and phone draw from it the route (lead chip, src, dst, notes), disclosure word, detail heading, actions and empty Undo text. They have no kind checks of their own. Keyboard u and r use the row's actions. A tie take can fail after a hop changed its tie line. Its row then gets the note "TIE 3 changed, B.42 not" (`partialNote`). A hop with `late` (the router confirmed it after the take gave up) reads "TIE 3 changed late" and also offers Put back. `actions.putBack` has one Put back button for each such hop entry (`putBacks`). Its plan is the Undo of the hop entry with verb `putback` and `putBack` on each item. The hop entry keeps its own `prev`. The entry of the destination keeps `hops` with the Prev of each hop, for the Undo of a tie take later. A status is words only (statusText in statustext.js, tone in `data-tone`); a Group still on its way says `2/32 done…`.
- Tie takes (docs/tielines-design.md, History): tiehistoryrules.js is pure. A hop entry (`tie`, isHop) is part of the route asked for. buildRows gives each destination entry (`origin`) its `hopEntries`. A Group that has a destination entry loaded never shows a hop entry as a row. A take on its way shows its hops by their own ends. groupRowEntries and groupPartial count the destination entries only. soloTies finds a whole Group with one destination entry and no Protect entry. That entry is a take row alone (`tieSolo`), so it stacks. stackVia adds the tie ids to the stack key. Thus a tie row stacks only with a row through the same tie lines. It never stacks with a route on one router. The open row shows what each tie line carried before (hopRows in widgets.js, from hopsBefore). The phone opens it as "Hops". The take row of a tie take offers Put back from its hop entries. It offers Retry when it failed. Its Redo (againPlan, `tieAgainItem` in plans.js) is a route from `origin` with `ties` and `last`. `ties` are the tie ids of its hops. Thus the confirm opens the picker on it (see Undo and Redo of tie takes below). Its Undo is of the destination entry only. Undo all of a tie Group leaves out the hop entries (groupUndoPlan). Filters and quick search match the typed ends (typedEnds), never a hop entry. The source is `origin`, on its own router (the third argument of srcOk). Router-prefixed number terms (`B.12`) are not in the filter language yet.
- Protect entries (protect.go): `protect` is `set` or `clear`, `src` is -1 and `levels` is every level. `still` names the levels Sode still holds after a failure. They never stack (`stacks` in history.js) and have no Redo. Their Undo is the other one (PROTECT_ENTRY in protects.js), offered only while it is Sode's own. Ctrl+Z (`undoLast`, Step back below) skips a `set`, so it never frees a Protect, and counts a `clear`: its Undo sets the Protect again. The row draws the chip alone where the source box is, with no arrow. The API's History Undo, Redo and Retry answer 409 for them, and `/history/groups/last` skips their Groups.
- A tie take with a Protect (tieprotect.go) has the Protect entry in the Group of the take. The Group's summary, Undo all and Retry leave Protect entries out (`!e.protect` in historyrows.js GROUP and plans.js). So Undo all undoes the routes, and the Protect stays. A failed Protect entry counts as a failure in the Group's status.
- Protect Groups: the page always sends one `protectSet` or `protectClear` with `protect.dsts` ([{dst, undo}]), one destination too, and reads `results` (docs/agents/server.md). Rows that another Sode user holds ask one Approval, at every size. protectMany checks all of them under protMu before it sends, so `group` (`p…`) and `groupN` count only the entries written. Free Sode's Protects is one Group too. The API sets one destination at a time, with no Group. histRows shows a Group of Protect entries with the chip and "N destinations" (PROTECT_GROUP). Its Undo all is one many-destination plan of each entry that protectUndoable allows, with `skipped` for the rest. protectUndoable reads newestProtects, worked out once for each draw. Ctrl+Z on a Free Protect Group undoes the Group. Ctrl+Shift+Z never redoes a Protect, since a Protect has no Redo.
- Runs: buildRows makes uniform rows with `shows`. mergeRuns (historyruns.js) makes both stacked rows (lane dst; rows of other destinations between do not end it) and folded rows (one lane: neighbours only). Folding joins Sode's own Protect rows with the same protectFoldKey (direction, `client`, `browserOf`; no undo, no ext). Each is at most stackGapMs() before the one above (foldRow, protectFoldOpts). A folded row keeps its oldest row's Group id, or `fold-<id>` when that is one entry, so an open row stays open, and has `folded`. It says "(N actions)" only when N is not its count of destinations (foldedNote). No search folds. Frontend only, as stacked rows are.
- Chips: every Protect and Router lock chip is `protectChip` in protects.js, in all views and in History. It has an icon and words, with patchbay's status square off (`sode__hold-chip`). `entryChip` (protectrules.js) picks a History entry's icon and words: shield, shield-off for any Free, shield-ban for a Router lock.
- External Protect entries (protext.go): a Protect or Router lock that another system set or freed. They are ext entries with `protect` `set` or `clear`, `holdKind` (`protect` or `routerLock`) and `device`. One entry for each destination, device, kind and direction in a burst (extQuiet, extMax). The entries of one kind, direction and `found` in a burst share a Group (`xp…` or `fp…`) when there are two or more. `found` marks a change seen at a re-read (0x8B, 0x94); a 0x8D or 0x8F is a plain External. The first state the router reports for a level (`routerState.protSeen`) is the baseline, as for routes. So a start or a router change writes nothing. A reconnect that shows a change writes Found entries. Sode's own changes are skipped: a hold with Sode's device that appears, and a hold that goes while Sode frees it (a protWait). The device is the one Sode has for that router. Another system that frees Sode's Protect gets an entry. They have no Undo or Redo. Filters treat them as ext. Quick search matches their chip words against the Source term (for example `"Router lock"` or `/protect/i`). The Communication Log has only the router messages, as for External routes.
- Undone mark (#737, undone.js; GLOSSARY.md Undone): a record that a later undo put a take back, not what the destination has now. Frontend only. buildRows reads the `undo` and `retry` ids of all loaded entries (undoIndex). Thus a filter that hides the undo row still marks the take. The undo row stays as it is ("undo of #N"). The mark uses the levels the take confirmed (takeLevels), or all its levels when it confirmed none. An undo of a failed take leaves out the levels that the router answered for (untouchedLevels in plans.js). A take whose undo confirmed every one of them gets `e.undone` (state `undone`, text "Undone", by, levels), a neutral pb-badge (undoneBadge) and the note "undone by #M". Some levels failed: "Partly undone", and the note names the levels that went back. All levels failed: no mark. A Retry counts toward the undo row it repeats (a Retry of a Retry too), so a confirmed Retry moves Partly undone to Undone. Redo never changes an earlier row. A stacked row is marked when the undo id is any entry of its chain (stackRow). A Group has `f.undone`: "Undone" when every route in f.entries is, "3 of 5 undone" when only some are. External followers are not in f.entries and do not count. Hop entries and the Protect entry of a tie take do not count either. An undone tie row also gets `tiesKept` and the note "tie lines left as they are", unless an undo row put back one of its hop entries. Quick search loads its own pages, so a result can hold the take without its undo and then shows no mark. This limit is accepted. Step back (below) uses the same marks.
- Step back (#764, stepback.js): Ctrl+Z (Cmd+Z on a Mac) runs `undoLast` in desktophistory.js. It undoes the newest take that this browser sent. Each press goes one take further back. `backStep` passes over an undo, a Retry of a failed undo (undoRoot), a Protect `set` and an ext entry. It also passes over a take from another browser, panel or API client. A take whose Undone mark (undone.js) is Undone is passed over too, but Partly undone is still a step. A take whose Undo plan is empty (planEmpty) is passed over, not shown as "Nothing to undo". This is the panel Undo cell's rule (panelundo.go). A Group is one step without its entries that are already undone. Ctrl+Shift+Z (Cmd+Shift+Z, `redoLast`) redoes the newest take that Ctrl+Z undid, with the row's Redo or Retry plan (`againPlan`). Each press goes one further forward. Both open the usual Confirm. Two `sessionStorage` lists hold entry keys, so a reload keeps them and a new tab starts empty. A key (`entryKey`) is the History id and the entry's `time`, `"12@2026-…"`. The time is in the key because ids start again at 0 after a History Clear and after a restart with no history file. `sode-own-takes` holds the key of each takeResult and Protect result row's `entry`, read from S.hist, since the server sends the entry before the result. `sode-redo-steps` holds one key list for each take that Ctrl+Z undid, newest last. `historyCleared` empties both (forgetSteps). The plan of each key carries `step`: `back` with `stepIds`, or `forward`. sendTakes changes the redo list only when the plan goes out (`nextRedo`). Back adds a step and forward removes the newest. Any other take clears the list, as in an editor. An undo, a redo, a retry or a Protect leaves it. A take that Ctrl+Z undid is passed over while its undo entry is not loaded, so a fast second press goes on back. `forwardStep` drops a step whose entries are not loaded or whose undo failed on every level. No wire or JSONL field. A hop entry is never a step (isHop): the step of a tie take is its destination entry. A tie take that the picker sends itself (tieflow.js `send` with direct) calls noteSent. The `results[].entry` of its answer go to noteOwn, as for a take through sendTakes.
- Undo and Redo of tie takes (#808; docs/tielines-design.md, Undo; tieundorules.js is pure, tieundo.js asks). desktop.js openConfirm and the phone's openSheet first call guardTieUndo. Take an undo plan with the destination entry of a tie take that worked (`origin`, ok). It asks the server with the message `tieUndo` (`entries`). The answer is `tieUndoResult` (`checks`, internal/app/tieundo.go). Then it calls back with `tieChecked`. Verdict `same`: the plain Undo. `putBack`: the plan gets `extra` with the Undo of each hop entry tagged putBack and a `label` ("Also put TIE 3 back to CAM 9. Affected destinations: …"). The box is off until ticked (Space). A hop entry that is not loaded makes it `changed`. `changed`: nothing goes, and the banner says why with a "Choose tie lines for CAM 9" button (`data-tie-undo-pick`). The button opens the picker for the source from before (pickerPlan, verb undo). Row Undo, Undo all and Ctrl+Z all pass this guard. Ctrl+Shift+Z on a tie take uses the row's Redo plan, so it opens the picker. lastState (tiepickrules.js) chooses the path through the old tie lines only if it is usable and costs no more than the cheapest. Each choice of an old tie line has the badge "Used last time" (usedLast).
