# Panels

Sode Panels: saved 4x8 grid pages on `/panels`, `/panels/editor` and `/panels/<id>`, driven over `/api/v1` only. The design and what was built are in docs/panels-design.md; this note holds what bites. Names that are stored or sent are in docs/persisted-names.md, routes in docs/api.md and `internal/app/openapi.yaml`.

## Storage

All beside the config, under `/data` in the image.

- `panels/<id>.yaml`: one file per panel. `<id>.art/<art id>` holds its artwork and `<id>.checkpoints` its Push checkpoints (at most 10). `panelStore` (`panelstore.go`) owns all three. The artwork cap is by total bytes (`panelArtTotal`, 64 MB, `artBytes`), not by count. `copyArt` (Push and Copy) copies what fits and returns the ids that did not fit. Every write goes through `writeLocked`, which moves `Rev`.
- `panelsets/`: Checkpoint sets, `everyone.yaml` and `me-<hex of user>.yaml`.
- `templates/me/` and `templates/everyone/`: templates, apart from the panel files.
- `artdefaults.yaml` and `artdefaults.art/`: Default artwork (`artDefaultStore`, `artdefaults.go`; routes in `artdefaultsapi.go`). Images are keyed by content (`d-` ids), so setting one image twice stores it once, and a write deletes images no default names. The 64 MB cap covers all of them together. Uploads and copies both go through `checkArtBytes`.
- `icons.yaml` and `icons/`: the Icon library (`iconLib`, `iconlib.go`; routes in `iconlibapi.go`). Ids are random, not by content, so two names for one file stay two icons; files are `<id>.png` or `<id>.svg`.
  - `freeName` turns a clash into "Name 2" and is the one place that settles names. A rename runs it against the other icons, so a case-only rename keeps its name.
  - Delete leaves cells with their `lib:<id>` (they draw nothing) and does not rewrite panel files. `/icon-library/{icon}/uses` counts them for the Confirm. It counts cells only; a Default artwork that names the icon is not counted.
  - Push, Copy and templates keep `lib:<id>` untouched (`copyArt` walks `Art` only, `dropArtwork` drops `a-` ids only). A Default artwork stores the reference after it checks that the icon exists, never a `d-` copy. So the 64 MB caps never see library bytes. `iconlibmove_test.go` covers these and a panel body moved to an install without the icon.
  - The upload is JSON with the file base64 in `data`, so the PIN is in the body. `iconBodyMax` sizes the read from the 2 MB cap.
  - `rescan` reads `icons/drop-in/` (`iconlibdrop.go`) at start (`New`) and on `POST /icon-library/rescan`. `checkLibBytes` is the upload's check, and `dropName` keeps in step with `libNameOf`. Sode removes a file after it adds it, so a second rescan never adds it again, and skipped files stay. Reads go through an `os.Root` after an `Lstat`, so a link never leads out; a linked `drop-in` is refused whole.
- `panelwatch.yaml`: who watches what, as watch keys. A watch key is a panel id, or `<id>/<device lowercased>` for one instance (`watchKey` in `panelmon.go`). Keep per-instance watches keyed by the device name, since #293 makes named instances first class. Never part of a panel file, and the API only sends the caller's own `watching` and `watchingInstances`.
- `yamlDir` (`yamldir.go`) is the mutex, directory, id retry, atomic write and name sort that the panel, template and Checkpoint set stores share. File names and skip rules stay in each store. Sets keep several records per file, so they use only part of it.
- A file whose id, name or directory disagrees with its content is skipped, not repaired.
- Pages (ADR 0007, `panelpagelist.go`): `Panel.Pages`, `Template.Pages` and `panelLayout.Pages`. `LegacyCells` (`cells`) is read only, and Sode never writes it. `normalPages`, run by `normalize` and `Template.migrate`, makes it one enabled Page. That Page is named after the record id's hex digits (stable across restarts until the first save). Pages win when a file has both, as one an older Sode saved would. `checkPages` runs in `validatePanel` and `Template.clean`. It fits cells with `fitCells` and refuses a list with no enabled Page. It calls `checkPageTargets` (a malformed Go to Page `page` is 400, a missing target is kept) and `checkShowParts`. A PUT body with `cells` and no `pages` changes Page 1 only; a body with both is 400. Anything that walks a panel's cells uses `allCells(p.Pages)` (Default artwork, Icon library uses).
  - In the page, `pageCells` (`web/panelpages.js`) is what `cellsIn` reads, Page 1 unless given an index. The editor keeps the Page list beside the grid (see Editor Pages below). `saveBody` and `saveTemplateBody` send `pages`, built by `storedPages` from the editor's live Page list (the focused Page's grid folded in). Every Page is fitted to the grid's size.

## Keys

- A panel that acts as an API client has an `apiClients` entry with `panel` set to the panel id. It is made and removed with its panel and does not count toward the 12-client limit. A Trusted user can make one, with Rights no wider than their own (`Rights.Within`, ADR 0006). The cap is checked only when a save sets Rights to something new, so a panel an administrator widened keeps saving.
- Its keys are key-store entries, one per named instance, and the key name is the instance's device name (`panelkey.go`). A link is always made for a name (400 `bad_request` without one). A link made for a held name rotates only that instance, and `DELETE /panels/{id}/key?instance=` revokes only that instance. `replaceInstance` does the end-and-make under one lock. Past `panelKeyMax` (20, keys and pending setup links together), it refuses and changes nothing. `GET /panels/{id}/keys` lists them with `online` from the monitor (`deviceOnline`, matched by name ignoring case) and never a secret. A key made before instances existed is named `Link` and is an instance like any other. Ending an instance forgets only its device (`forgetDevice`). Network limits are the client's `networks`, a CIDR list of at most 16. The auth path checks them, so every route and the setup exchange are covered.
- A setup link is a `keys.json` record with `"setup": true`, named for its instance. It lasts one hour and works once, and the page trades it at `/api/v1/panels/{id}/setup` for a key with the same name. It ends with that instance's key (rotate, revoke, a newer link for the name), not with the other instances'.
- The Share modal opens on the tab that fits the panel (`firstShareTab`). That is Link with key for an API or Both panel, and People for a Session or Public panel. A Session or Public panel's Link with key tab is muted (`keyTabMuted`) (`muted` on the tab item, `aria-disabled`) and readable. It says that a link to a Session panel asks for a sign-in, or that a Public panel needs no key. It offers no key action. The editor's saved note per mode is `actsSavedNote` and the Public warning `PUBLIC_WARNING`, both in `panelsrules.js` so node tests read them. A change of the Authentication mode in the editor saves the panel immediately (`ed.save()`), since it makes or removes the client. A refusal (`trusted_required`, `outside_rights`) puts the choice back and shows under the field.
- `acts` is `session`, `api`, `both` or `public`. `api`, `both` and `public` own a client and keys the same way. Test with `actsHasClient` (Go) and `hasClient` (`panelsrules.js`), never `=== 'api'`. The exception is a rule that really is "only with a key" (the panel page's refusal of a keyless open, the hidden Copy link, the link row's hint). `both` falls back to Session mode in `panelrun.js` by doing nothing: its only `acts` check is the `api` refusal. Switching `api` to `both` or back keeps the client and its keys; `session` ends them. A switch that makes or ends the client waits for the Confirm. Call `guardActs` (`actsguard.js`) from any new place that changes `acts`. Never use `setFields` or a PUT on its own. The Confirm box (`confirmbox.js`) is the one Rotate and Revoke use.
- A panel has an optional `slug` (unique, `validPanelSlug`). `panelStore` checks uniqueness under its lock. `GET /panels/{id}` and the setup route turn a slug into the id (`panelIDOf`); every other route accepts the id only. Build links with `linkFor` (`web/panellink.js`), never by hand. Panel keys and setup tokens are 128 bits and the fragment drops their `sode_` prefix (`fullKey` and `fullSetup` put it back).
- Links made on a page opened as localhost are useless on a phone. So `web/sharehost.js` asks one time for the address that other devices use (`localStorage` `sode-share-host`). `linkBase()` swaps it into every link and QR code; `linkFor` itself stays pure.
- The panel page reads `#key=` (API mode), a stored `sode-panel-key-<id>`, then asks for a Public key, then starts a session key (Session mode). A key never rides a query string. The page stores a `#key=` that opened the panel under that name and drops it from the address (`keepLinkKey` in `panelsetup.js`, `withoutKey` in `panelkeyrules.js`). It does this only after the open succeeded, never for a Public key, and only if `localStorage` reads it back. Otherwise the key stays in the address. A stored key from either path is forgotten on a 401. A test that opens a keyed link and then a plain one in the same browser must drop the stored key first (`TestChromePanelBothMode`).
- Public keys (`panelpublic.go`, ADR 0008): `POST /panels/{id}/public` is unauthenticated, so its keys live in `App.public`, never in `keyStore`. So there is no disk write per request, and nothing in `GET /keys`, the instance cap or `keys-ended.json`.
  - They last 15 minutes each, at most 64 per panel. Past that, the address that asks loses its own oldest key first (`publicRec.addr`), and the key's streams end. They have their own shape (`sode_pub.` and 43 characters, `isPublicShape`).
  - A dropped one (expired, pushed out, the panel left Public) is remembered in `publicKeys.ended` (4096 hashes) and reads as ended, uncounted. An unknown one reads as `key_revoked` too, so a page that slept asks again. But it counts toward the failed-key throttle if `App.started` is more than a TTL ago. Before that, it is possible that it is a key that a restart forgot.
  - No ask counts toward the failed-key throttle. Every keyless open of any panel asks, and a count of those would lock out an office behind one address. Instead `publicAskMax` (128 asks per address per minute, or the API rate limit if lower) counts every ask whatever the id. Not Public, no panel and outside the client's networks all get the same 200 `{"public": false}`. So no run of asks tells which ids exist, and the browser logs no error on a keyless open.
  - `endPublicKeys` runs when a save leaves `public` and on delete; expiry ends them in `expireKeys` with no log row each. Every Public key is named `Public`, so a call with no `X-Sode-Instance` is logged under the caller's address (`apiKey.public` in `panelHeaders`), not the key name.
  - In the page, `askPublic` returns '' only for Sode's `{"public": false}` and throws on anything else. So a lockout or a lost link during a renewal reads as lost contact, and the next call asks again. Only the first ask at open (`askPublicAtOpen`) falls back to a session.
- Page lock on a Public panel: no PIN pad, only the idle letter Lock (docs/panels-design.md). This is page-only. `panelrun.js` emits `publicPanel` {on}, and `lock.js` rereads the last `lockState` through `pinFreeView`. It never emits it from the editor's live test, and emits off again when the page stops or a live update leaves Public. The server's `lockState` for the panel page stays locked with no names. So do not lift the pad by letting the connection in on the server (`TestPageLockLeavesThePublicKeyAndSendsNoNames`, `TestChromePublicPanel`).

## Browser session key

A Session-mode page trades its signed-in session for a user key over the socket: message `sessionKey`, answer `sessionKeyResult` (`internal/app/sessionkey.go`, `web/sessionkey.js`, rules in `sessionkeyrules.js`). The key is memory only, ends with the session, and `sessionFetch` adds the Bearer header. A refused `sessionKeyResult` reaches `onSessionKey` watchers as step `refused` with the server's reason as a third argument. Without it, a page waits for a key forever and shows nothing (the editor's old blank page). Use `sessionFetch` for every `/api/v1` call from a Sode page; never build the header by hand.

Ended keys (the throttle lockout a stale tab caused): Sode answers a key that worked and then ended with 401 `key_revoked` (`key_expired` past its expiry). It never counts it toward the ten failed keys per address. `refuseEnded` in `apiauth.go` does this, with its own cap of 120 a minute and one `endedKeyUsed` row per address per minute. The key store remembers the last 1024 ended keys by hash in `keys-ended.json` (`noteEndedMu`). Every drop path records them, except for setup links and session keys. A session key has its own shape, `sode_ses.` and 43 base64url characters (`isSessionShape`), so an unknown one reads as ended even after a memory-only restart. 256 bits make an uncounted guess harmless. A session holds up to 16 keys (`sessionKeyMax`), one per tab. Tabs share a session token, and a key per session made them end each other's on every renewal.

In the page, `sessionFetch` renews one time on `key_revoked`, `key_expired` or an older Sode's `invalid_key`. The first call that sees the key refused asks for a fresh one, if the page is still signed in. The others wait for it. If signed out, they wait for the sign-in and send nothing. If the server refuses a fresh key before it ever worked, the module ends for good. Every later call gets that answer without the network, and `onSessionKey` watchers hear step `ended`.

After a 429, `guardFetch` (`sessionkeyrules.js`) holds the next call until Retry-After has passed. Given `final`, it replays a final answer without the network. The panel page wraps its link key in it. On a stop, `panelrun.js` clears its timers, the update check and the keepalive (`keep.stop()`). `TestChromeEndedKeysStopWithoutLockingTheAddress` covers two tabs on one session, a forgotten key and a revoked link. For a JSON answer, wrap it in `jsonCall(fetcher, { failed, down })` (`sessionkey.js`). It throws an Error with `status`, `code` and the server's message. A page with a URL key passes its own fetcher. Details are in docs/agents/users-locks.md.

## Seams

- REST: `panelsApp`, `userKey`, `makePanel`, `apiSend` and `apiSendRaw` in `panelsapi_test.go` run the real handlers against a fake router. Use them for any new route test.
- Web rules modules are pure and tested without a DOM: `panelmodel.js` (view, stage, Take), `panelrules.js`, `panelupdate.js`, `panelwatchrules.js`, `panelkeyrules.js`, `panelsrules.js`, `panelpushrules.js`, `gridmodel.js`, `editorrules.js`, `findrules.js` and `arttoolrules.js`. Put new logic there and keep the DOM modules thin.
- Panel types (ADR 0011): `panelrun.js` hands a body the adapter `ctx`. The body is `buttonsBody` (`panelbuttons.js`) or `gridBody` (`gridpanelrun.js`). Grid notes are in Grid panels below.
- Browser harness: docs/agents/browser-checks.md. Chrome checks use the real Handler and a built simulator, never `panelsApp`.

## Grid panels

ADR 0011 and the Grid panels section of docs/panels-design.md say what a Grid panel does. This section holds the seams and what bites. Grid modules are `web/gridpanel*.js`, and each pure one has a node test of the same name.

### Server

- `panelgrid.go` holds `GridEdge{Members, Hide, Items}`, `GridItem{Pinned, Art, ArtB, HideText}` and `GridMembers` (`"all"` or a list of integers, in JSON and YAML). A decoded list is never nil, so `!All && List == nil` means `members` was missing, which is 400. An empty list `[]` round-trips.
- `checkGridEdge`: `hide` only with `all`, numbers from 0 to `dstNumberMax`, no repeats in members or `hide`, any number pinned. Item keys are plain decimal ("007" is refused). Items for non-members stay, and no Rights filter runs on save.
- `Panel.Type`, `Sources` and `Destinations` are in `panelKnown`. `normalize` returns early for a Grid panel (`Pages` is `[]`). `validatePanel` calls `checkGrid` and skips `checkPages`. A Grid panel has no `rows` or `cols`, so openapi allows 0.
- `apiPanelUpdate`: an empty body type keeps the stored one, and a different one is 409 `conflict`. The legacy `cells` to Page 1 branch runs for a Buttons panel only, since a Grid panel has no Page to take it.
- Push and Checkpoint layouts carry `type`, `sources` and `destinations`. `apiPanelPush` refuses the other type before its loop, and `applyLocked` refuses it for sets and restores (Push, Rev and live update below).
- The panel read's ETag moves when an edge's Default artwork changes (`panelArtDefaults` reads the edges). `TestGridDefaultArtworkChangeMovesTheETag` covers it.
- Tests: `panelgrid_test.go`, `panelgridedge_test.go`, `panelgridart_test.go`, `panelgridpush_test.go` and `panelgridpushart_test.go`. `makeGridPanel(t, a, key, name)` makes the fixture.

### Page structure

- `panelrun.js` keeps keys, sharing, polls, keepalive and live update for both types. After the read it builds `ctx` and calls `(isGridPanel(panel) ? gridBody : buttonsBody)(ctx, panel)`.
  - `ctx` is `{ ui, art, embedded, page, id, call, callJSON, post(path, body), poll, ready(), instance(), touched() }`. `post` adds one Idempotency-Key for each call.
  - A body answers `render`, `data({ tally, prot, nm, pr, first })`, `apply(p)`, `pending`, `renamed(changed)` and `stop`. `nm` is null when the names were not read again. The watcher calls `body.rights?.(p.rights)` on every panel read, since a Rights change does not move `rev`. The Buttons body has no `rights`.
- Fixtures for node tests are in `web/test/gridpanelfixture.mjs` (`namesReply`, `tallyReply` with routes as `[dst, level, src]`, `gridPanel`).
- `gridpaneledges.js`: `gridAxes(panel, namesReply)` is `edgeOrder` (pins first, then members, less `hide`) followed by `shown` (items in `GET /names` and inside `panel.rights`). Keep that wrapper when you change `edgeOrder`, since an explicit list with a gone item relies on it. Never apply a Filter inside `gridAxes`, or a filtered-out panel source reads as an "other" source.
- The run keeps two sets of axes. `full` is `gridAxes`, used for picks, other sources and the Diagonal's `srcs` and `dsts`. `axes` is `full` less what a Filter hides, and the view, the cursor and `shownDsts` use it. `arrange(panel, namesReply, { find, picks, cur, axes })` (`gridpanelarrange.js`) is the one step behind `rebuild()`, which a live update, a names poll, a Rights change and the search keys all call. State that must live through a live update goes through it. Test it in `gridpanellive.test.mjs`.
- `rebuild` skips work when `JSON.stringify([full, axes])` is unchanged. `apply` clears that key, so a live update always rebuilds, and the rebuild ends a Drawn line in progress.

### The view

- `gridpanelview.js` draws only what shows, on both axes, and moves nodes from item to item as the grid scrolls. The window maths is in `gridpanelwindow.js`. Its indices are display order, never router numbers. A node holds no state of its own. Paint picks, gone items, Find matches, the cursor and marks from the `view` that `g.paint` gets, in `paintXp` (crosspoints) or `paintSrc` and `paintDst` (names). Both a move and a paint call those.
- A name node keeps one Text child that `setText` changes, and a destination name is `[Text, prot, other, art]`. Do not use `textContent =` or append children on a scroll, or the no-rebuild MutationObserver check sees a childList change. Keep the art row last.
- Spare nodes stay in the DOM with `hidden`, and keep their old `data-picked` and `data-s`. A check that counts nodes counts them, and a "none left" selector needs `:not([hidden])`.
- The layers share one CSS grid cell. The body scrolls. The top and side bands are sticky and hold the names and pinned crosspoints. The corner holds what is pinned on both axes and `g.head`, the Destinations word. The search boxes are in the deck, on the panel page and in the editor's live test alike. A pointer move over `g.head` does not move the cursor.
- Pinned bands (`band` in the view, `itemOf` and `slotOf` in `gridpanelwindow.js`): each edge has `{ pins, slots, at, f }`. The window maths, the pools, `--sode-i`/`--sode-j` and `--sode-rows`/`--sode-cols` are in slots: the band's `slots`, then the items past the pins. The cursor, `ax`, `srcAt`/`dstAt` and every seam the run calls are in items; convert at the seam. A band with more pins than slots scrolls on its own. `gridpanelpins.js` gives it a scroller with a little bigscroll bar. Its offset in pins is `at`, plus `f`, the part of a pin (0 to 1). The band's pools sit in `bandBox` boxes. The outer `.sode-gridpanel__clip` clips at the band's edges while it scrolls (`data-band-x`/`data-band-y` on the field). `bandVars` moves the inner `.sode-gridpanel__shift` by `-f` pins with a transform. So a px of band scroll writes one transform and restyles no pin. A custom property on the layers restyled every pin under them (1.8 s of style per 900 px). While the band can move on, its pools also draw slot `slots`, the part pin at the far end (`extra`). A band pool's nodes are keyed and placed by pin index (`srcIn`/`dstIn`, `slotIn`), not `itemOf`, and `bandVars` moves its box by `-(at + f)` pins. So a whole new `at` gives one row or column's node to the pin that came in, and the rest stay. `reserve` sizes the band pools for the part pin. A wheel step of 40 px or more glides over 140 ms (`by` in `gridpanelpins.js`), as the grid's wheel does. Smaller steps (a trackpad) go at once. Selectors reach a pinned crosspoint or name as a descendant of its layer, not a child. The wheel over a band goes to it (`wheelBand`); `reveal`, `glide` and `jump` move the band to a pin it does not show. The phone has no band bars, so there `pins` equals `slots` and the extra pins scroll with the rest.
- CSS places nodes with `--sode-i` and `--sode-j`. Sizes are `--sode-xp`, `--sode-name-w` and `--sode-name-h` in rem, and the view measures them in px on each resize. `--sode-patch-field` is the field colour token. `scrollbar-width: auto` on `.sode-gridpanel__scroll` lets the `::-webkit-scrollbar` rules apply. `--sode-scroll-h` and `--sode-scroll-w` are the bar sizes; no script reads them. The view's non-passive `wheel` listener calls the pure `wheelAcross` (`gridpanelwindow.js`), with the bar box from the metrics and `offsetHeight`. There is no `border-radius` (rules.test), so the pie is round through `clip-path`.
- Look sizes are rem. The Grid page's root is 112.5% (base.css), so a crosspoint is 72 px and the corner 202 by 108 px. A staged crosspoint carries `data-s="staged"`. Each one runs `sode-panel-pulse` itself, because a Grid panel turns the grid's animation off (Gotchas below). So do the cursor ring and the armed Take. `joinPulse(node)` (`gridpanelview.js`) sets each new pulse animation's `startTime` to 0 in one microtask, so all of them count from the timeline's time zero. Call it after the class or attribute that starts the animation is set. A ring hidden by `display: none` restarts when shown, so `placeCursor` calls it again.
- The cursor (`gridpanelcursor.js`) holds display indices, with -1 on a bar. Its node `.sode-gridpanel__cursor` is a child of the field, not of the overlay. So on a bar or a pinned item it can draw above the sticky bands. `data-band` lifts it. The view moves it by transform. `TestChromeGridPanelCursor` checks that a pointer move changes nothing else on the page.
- `g.hit`, `g.reveal`, `g.node`, `g.onDraw`, `g.cellAt` and `g.page` are the view's seams for keys, jumps and Find. A pointer move calls `onPoint`, and a key clears the run's `ptr`, so a scroll re-places the cursor only after a pointer move.

### Staging, confirm and Undo

- `gridpanelstage.js` is pure. State is `{ mode, staged: [{dst, level, src}], busy, error, undoId }`. Every press path calls `stageRoutes(st, pairs, levels)`, which gives `{ st, send, confirm }`. In Take mode a press whose staged set comes out the same (`sameStage`) keeps the stage and returns `confirm: true`, so a second press is Take. That covers one crosspoint, a Diagonal or a line, on the same or fewer levels. `no-levels` comes before it and `cap` after it. `unstageRoute(st, {src, dst})` drops one route on every level (Alt-click and Delete or Backspace, `unstage` in `gridpanelkeys.js`). The cap error is `{ code: 'cap', add, have }` (`STAGE_MAX` is 128). `restage(st, panel)` is what an apply does to the stage.
- A new press path calls `leaveUndo` before it stages, and skips `keepLive` while `st.undoId` is set (`onPress` does both). A press runs `keepLive` first, and `openConfirm` runs it again.
- `createStage` sets `st.ask` false only for `mode: takeOnly`. `openConfirm` is the one place that decides. The pure `bannerStep` (`gridpanelhead.js`) sets the banner's order. An error outranks a result that went well, and errors of one group join. `say` keeps the held-back keys. It writes each shown message to the `.sode-gridpanel__said` live region. With `ask` false and not Instant mode, it calls `send`. The result note then names what was left out (`plan.left`). `planOf(routes, names, tally)` adds each item's `now` (`currentlyOf`), which `gridSummary` draws under Currently. `.sode__plan-before` is in base.css, since the panel page does not load history.css.
- `gridConfirm` wraps `keyConfirm` and `gridSummary`. The verb comes from `plan.verb` (`take` or `undo`). An Undo plan has `undoId`, and the replace ask has `replace: n` and `next`. `send({ routes, undoId? })` posts to `/panels/{id}/undo` when `undoId` is set, else to `api/v1/takes`.
- The confirm's markup ids are fixed (`#confirm` and its parts in `panel.html`, the same as `keyconfirm.js`). The editor's live test makes its own copy for each run (`panelmount.js`), since `keyConfirm` adds listeners it never removes. `lockout.js` reads `S.cfg`, so the configured lockout applies only after the panel socket's hello (500 ms before it). Instant mode holds nothing staged: `stageRoutes` returns `send` for every press, so only an Undo waits on its confirm (`confirmRoutes`, `cancelConfirm`).
- `.sode__plan-item`, its parts and `.sode__keys` are in `base.css`, since the panel page needs them.
- The Take button `#panel-take` is made by the run and appended to `#panel-levels`. It is `pb-btn pb-btn--danger`, the main page's Take, and shows on every layout in Take mode and never in an embedded run. It has no animation of its own while it is not armed; armed, it glows between `--pb-status-error` and `--pb-danger-hover`. Clear (`#panel-clear`) and the chip (`gridpanelnote.js`, words from `pickNote` in `gridpanelphone.js`, no help words) are made beside it. Clear runs `clearAction` (`gridpanelkeys.js`), the same choice as Esc.
- The run makes the header parts (`gridpanelheadview.js`) on the panel page only. `gridHead` also makes the deck (`.sode-gridpanel__deck`): it moves the header and `#panel-levels` into it with two `pb-divider--vertical` rules and the search slot (`finds`). On the desktop layout the header is a flex row over the whole deck. The Levels box and the slot are `display: contents`, so their parts are cells of the deck's grid areas (`gridpanel.css`). The phone layout keeps the page's flow. The Levels box is `ui.levels` (`pageUi`). The deck's first row is `.sode-gridpanel__headrow`: the header and the Server and Router status, with the Live Editor's status slot (`.sode-gridpanel__slot`) between them. Kiosk mode hides the row on the desktop layout. Settings (a link to `./#settings`), Kiosk, Full screen and Full width go in `.sode-gridpanel__tools`, after the title. On the panel page (no `ui.back`) the order is Settings, the Panels link, Edit, Copy, a rule and Full screen. The Panels link goes in `.sode-gridpanel__home`, which is `ui.tools`. The desktop layout moves the group out of the header into the header row. `ui.toolsShown(kiosk)` tells `panelfull.js` where the Panels link goes, so the buttons show with the Title bar setting off. ## Undo cell

- `panelundo.go`: `GET` and `POST /panels/{id}/undo`, scope `take` only, so a panel key undoes without `history` (`config.PanelClientScopes` must not gain it). `panelUndoTarget` walks History newest first (at most `undoScan` entries, each a file read). An entry with `undo` set counts as an undo of its target only when it is `ok`. A refused or failed undo leaves the take, and a Late Result flips `ok`. It picks the first entry whose `panelId` and `instance` (case ignored) are the caller's own, with its Group. It reads the Group again from that entry, so another take's interleaved entries never split it. GET answers the take's newest entry as `id`; POST sends it back and gets 409 when the target moved. The instance is `Actor.instance` from `panelHeaders`; a caller with none (the Live Editor) has nothing to undo. Entries made before `panelId` existed never match.
- The Undo cell trusts the instance name the page sends (`X-Sode-Instance`), as every other instance feature does.
- The page keeps the answer in `undoNext` (`panelrun.js`) and greys the cell from it (`undoReady`). It asks at these times, and never on a timer, since each ask walks History:
  - when a poll first reaches Sode (load and reconnect)
  - after its own take or undo
  - on a rename or live update
  - when the tally of a destination in `undoNext.routes` moves (`undoMoved`).
- Grid panel Undo (`u`) does not keep `undoNext`. Each press asks GET, and only the newest ask's answer counts (`pressUndo` in `gridpanelrun.js`). `stageUndo` (`gridpanelundo.js`) puts the routes in `st.staged` per level and sets `st.undoId`. `openConfirm` sends that plan whole with `undoId` on the confirm's plan, and `send` reads it from there, never from `st`. A crosspoint press drops a staged undo first (`leaveUndo`). `keepLive` does not trim an undo. With routes staged, a first confirm (`replace` on the plan) asks to drop them. Instant mode opens the Undo confirm at once.
- A press is `pressUndo` (`panelmodel.js`). It puts `undoNext.routes` in `st.staged` as they are and sets `st.undoId`. There is no level trimming, no Fixed destination filter and no `multi` refusal, since the server sends its own plan for the whole take. `startTake` and `startInstant` hand `undoId` on. `takeOpts` (`panelrun.js`) sends a plan with one to `/panels/{id}/undo` with `{"id": undoId}`. It never sends `undoNext.id`, since it is possible that it moved. `dropUndo` empties the plan. `pressSource`, `pressPreset` (through `overUndo`, so a refused press keeps the undo), an unstage, `clear`, `failTake` and `finishUndo` all call it. `askUndo` drops a staged undo whose id no longer matches. `applyTally` leaves an undo plan whole, or a fully routed undo would be staged and dropped on every poll while GET still names it. `finishUndo` shares the results with `finishTake` and puts the status in `st.undone`, since a done undo is no error.

## Push, Rev and live update

`panelStore.applyLocked` writes the checkpoint, then the panel. A checkpoint that cannot be saved stops the Push. Open pages poll `GET /panels/{id}` every 5 seconds and compare `rev` with the `artDefaults` it carries. So a Push, an editor save and a restore all reach them through the same store write. The compare is `revOf` in `panelupdate.js`, and it includes `artDefaults` since a changed default moves no panel rev. `panellive.js` has a 10 s countdown banner with a bar, Snooze 60 s (one time per open page) and Apply now. Staged routes hold the plain countdown but not a Snooze or Apply now (see docs/panels-design.md). Push and import never copy `acts`, `client` or `clientRights`, nor id, name, owner or `share`. A Push also keeps the target's `settings.fixedDests` (`pushLayout`); a Checkpoint set and a restore put the whole layout back, list included. A layout carries `type`, and a Grid panel's `sources` and `destinations`. `applyLocked` refuses a layout of the other type (`errLayoutType`, 409), and an entry saved before Grid panels has no type and reads as Buttons. A template keeps the list only with `dests`. A new route that stores a panel must not widen that list. The group for Push is worked out in the page (`pushGroups`); the server only sees ids.

The four reads the page repeats (`/names`, `/tally`, `/protected`, `GET /panels/{id}`) go through `apiJSONTagged`. With the socket up, the page takes the tally from socket frames and polls less (docs/agents/web-layout.md). `TestChromePanelStillUpdatesAfter304` holds the socket down to check the poll path. The ETag hashes the finished body, never a revision. In the page, `withEtag` (`etagfetch.js`) wraps `call` in `panelrun.js`. It sends `If-None-Match` and turns a 304 into the kept body, so `jsonCall` never sees one. A fetch with an explicit `If-None-Match` is the one way the browser hands a 304 to the page.

## Monitoring

`panelmon.go` keeps devices in memory, so a restart alerts nothing. A device is dropped after 24 hours. A page holds `GET /panels/{id}/instances/stream` (a `fetch` with the Authorization header, in `panelkeepalive.js`). So Sode sees a closed page immediately and marks it lost 8 seconds later (`monGrace`). A device that never held a stream, or beat again with none open, keeps the 45 second keepalive miss (`monMiss`). A panel is online while any device counts.

Sode names a blank device (`askInstanceName` off and no name) by the caller's address (`deviceOrAddr`). So watches and notices work as for a named one. The page decides this one time at start, so a live update that flips the setting waits for a reload. Notices go only to connections signed in as a watcher and not under the Lock, and are never in the hello. The Sode page shows a banner for the offline panels (`panelwatch.js`, the badge on pages without one). Its Clear menu sends `panelAlarm`: `clear` hides the outage for that user until the panel's next notice (memory only), `stop` removes the watch.

The tests use `a.mon.now`, and `monHold` in `panelmonstream_test.go` for a real held connection. Each held stream (`monConn`) has a one-line `out` channel that its own handler goroutine writes, so nothing else writes to the response. An Assign or a rename is the only line sent on it, and the stream ends after it. The old name is forgotten with no lost notice (`panelassign.go`, `panelrename.go`). `assignHold` in `panelassign_test.go` reads the lines. `instances` rows carry `stream`, and only those rows are Sode's own panel pages and can be assigned.

A watch is the whole panel or one device (`?instance=`). `watchersOf` decides who hears an event, and an instance-only watcher gets the notice with `offline` false. `offlineFor` rows carry `instance` for those, and `panelAlarm` echoes it. `KeepAliveListener` (TCP keepalive, about 5 s) catches a dead peer with no FIN, and then the 8 s grace applies. `TestChromeClosedPanelTabIsLostInsideFifteenSeconds` runs a closed tab on the real clock. The panels page polls every 2 s (`MON_POLL_MS`) instead of having a push channel.

Panels page extras (`panelmonup.go`, `panelsmon.js`, rules in `panelsrules.js`):

- Uptime: each instance keeps its `up` and `down` changes for 24 hours, and at most 400 of them (`mark`). The window is `monHistory`, the same as `monForget`, so a longer window would describe instances already dropped. The down time is `seen` plus the instance's limit, not the sweep time. Instances go out with `uptime` (`from`, `to`, `start`, `trans`). The page draws the strip with `uptime.js` and `uptimebars.js`, the same code as the /log graph. It draws against the server's `to`, so the browser clock does not shift it. Before an instance was first heard the strip is grey (no record). Bars on /panels are plain marks, not buttons: `paintOpenNow` skips its rebuild while focus is inside `#panels-open`.
- Hide: per user, in memory, in `panelMon.hide` next to `clear`, keyed by watch key. A hide ends no key and no watch and other users still see the instance. It is lifted when the device is next heard after it was lost or forgotten (`touchLocked`). `forget` and `forgetDevice` drop it, but the 24 hour drop does not. So a hidden watched instance does not come back as a not-seen row. Not persisted, since the instances it hides are not. `hiddenInstances` is the caller's own; "Show them" lifts every hide of the panel.
- Status: `instancesOnline` and `instancesKnown` go to every reader, counted for the caller (known instances plus instances they watch by name, less the ones they hid). `panelStatus` reads All Online, Some Online or All Offline; no instance at all is All Offline. `online` is unchanged and still drives watches and alarms. Communication Log rows from a panel (takes, stream, lost, back, alarm) carry the panel's short name and the instance; docs/agents/comm-log.md has the headers and wording.

## Assign

- The key goes down the stream, never in the REST answer, and Sode makes it only after it knows that the stream is held. It goes to the device's newest stream only (`sendNewest`, `sendKeyless`). Anyone who is allowed to use the panel can hold a stream under any device name. The handler answers on the line's `got` channel whether it wrote the line. A stream that closes answers false for a line still queued (`unsent`). The Assign waits (`written`, `lastWait`). When no stream wrote the line, the key is dropped and the Assign answers 409. A name that the target already holds, as a key or as any instance Sode holds (`heldNames`, shared with Rename), answers 409 `name_taken`. The answer has `error.suggest` (`suggestInstance`), because `replaceInstance` would rotate another device's key away. The request's `name` sends it under another name. The cap is checked first, so a full target never offers a name. `jsonCall` copies `suggest` onto the thrown Error, and `clashOf` reads it.
- The page stores the key under the segment of the address it opens (`assignAddress` in `panelassignrules.js` returns it). This is because `storedKey` reads by address segment, not by panel id. With storage that does not read back, the key rides `#key=` instead, as `keepLinkKey` does.
- A target can act as a user: `as` `user`, the default for a Session-mode panel and a choice for `both` (`assignBySignIn`). That target gets no key, no name-clash or cap check and no rollback. The line carries `signIn` `user` and no `key`. `followAssign` forgets any key stored under the target's segment, since `panelrun.js` would open a `both` panel as its client with it. A device signed in as a user keeps its session there. Instance rows carry `trusted` (the user's flag, live in `monFields`). So `assignRows` can mark `notShared` with the same rule as `panelReach` (`opens`; keep in step), and the modal asks Send anyway first.
- Instance rows carry `page`, `addr`, `signIn`, `user` and `streamSince` from the last stream the device opened (`openStream`). `page` is kept apart from `streamed`, because a keepalive clears `streamed` and a timed-out page must still be told from a keepalive-only API client. `streamSince` is set when the device goes from no stream to one, so a second tab does not reset it and a reload does. The list shows uptime in whole minutes (`uptimeText`), since `paint` redraws only when a row's text changes.
- The Assign to list's Find box (`rankAssign`, `stepRow`, `enterRow` in `panelassignrules.js`) reuses `wordScore` and `stepPanel`. Its keys come from `resultStep`, as on the panels list. The highlight is a row `key` (`panel\ndevice`), kept while the row is listed, else the first row. The list redraws only when rows, busy or the highlight change.
- Keyless instances (`panelkeyless.go`, ADR 0009): `panelMon.keyless` and `addrs` sit apart from `inst`, so they never count as instances, uptime or alarms. Panel reads carry them as `keyless`, and `assignRows` lists them beside `instances`. The route is `scopeOpen` and must answer alike for a panel that does not exist. An Assign of one names `keyless`, sends to its newest stream only (`sendKeyless`) and checks `networkAllowed` against the address `clientIP` saw. The stream carries no session or user: a device signs in over the page socket, which the idle clock covers. The Chrome check is `TestChromeKeylessPageIsAssignedAndRuns`. In the page, `unannounce` runs when the keepalive starts and in `run.stop`. `announce` in `panelrun.js` starts:
  - before the first read (a Session-mode page waits there for a sign-in)
  - on a 401 at open or from a poll (`ended` only for `key_revoked` or `key_expired`)
  - on a session key's `ended` step.
- Rename (`panelrename.go`): the name clash reuses `nameTaken`, `suggestInstance` and `heldNames`. `heldNames` is the client's key names and `deviceNames`, offline ones too, since reuse of a lost name would read as that instance coming back. The clash check and key rename happen under `cfgMu`, and the send after it, as in an Assign. The rename line goes to every stream of the device (`sendEvery`). When no stream queued it, the key's old name comes back. A refusal with `trusted_required` shows the Advanced Settings PIN field beside the name (`renameRefusal`). There is no cap check, since a rename adds no key. `followRename` moves per-instance watches. In the page, `hold` returns on a `renameOf` line. `renamed` in `panelkeepalive.js` writes `sode-panel-device`, or rewrites `?instance=` for a page named by its link. It then restarts the keepalive. The browser check is `TestChromeRenameARunningPanelPageFromThePanelsPage` (two browsers, since the panel page cannot be framed).
- An Assign reads the target and never writes it, so `settings.fixedDests`, `acts` and `rev` stay. The editor's Authentication mode Confirm does not run for an Assign, since no panel's mode changes.

- The glossary scan rejects every word on a `_Avoid_` line, in docs and UI strings alike, and only a few are exempt in backticks. Check GLOSSARY.md before choosing a word. It fails only in the full `go test ./...`, because `TestDocsUseGlossaryWords` and `TestUIStringsUseGlossaryWords` scan the whole tree; a `-run` on one panel test will not show it.
- `panelRows` in `web/panelpage.js` is the rows of a grid. Its name collides with a retired phrase, so it has an `identAllow` entry; keep it when moving the code.
- Web modules are capped at 1000 lines (`imports.test.mjs`). The editor and panels page are close; split by concern before crossing.

The Cell tab's warning reads Page 1's cells from `storedGrid()` (`firstGrid`). `checkPageTargets` (Go) and `ITEM_FIELDS` (`gridmodel.js`, a kind change drops `page`) keep in step with them.
- Page Name and Info (`web/pagecells.js`): `pageCellText` gets the id of the Page that the cell sits on, never Page 1. That is `st.page` on the panel page, and the drawn Page's id in the editor (`paint`'s `page`). `show` is the stored list, checked by `checkShowParts` (Go); `SHOW_PARTS` keeps in step with it, and `ITEM_FIELDS` drops `show` on a kind change. - Fixed destination on the panel page: `createState` makes `fixed[0]` the view. So `currentSource`, the Current cell and `sourceState` read it, and `clear` puts it back instead of null. `carryView` returns the new state untouched when it has a list, or an old Destination cell could overwrite the new view. `drawnCells` (`panelrules.js`) drops Destination cells, in `panelrun.js` only. `cellsIn` stays whole, since the editor and the thumbnails use it and must keep stored Destination cells. The page has no list of the fixed destinations (a strip was removed on request). So a Result shows only through the Current cell and the router. Rules tests are `web/test/panelfixed.test.mjs`, the browser check `TestChromePanelFixedDests`.
- Editor clipboard: the block rules are `gridclip.js` (`copyBlock`, `readBlock`, `pastePlan`, `applyPaste`, `pasteNote`), the clipboard I/O is `editorclip.js`.
  - On a plain HTTP address other than localhost, `navigator.clipboard` is missing. So copy falls back to `execCommand('copy')`, and paste reads the browser's own `paste` event (no permission prompt). The paste chord's command returns `false`, so `onKey` leaves the key to the browser. `readText` runs only when no paste event followed. A synthetic key fires no paste event, so a Chrome check either stubs `readText` or dispatches a `ClipboardEvent` (`TestChromeEditorCopyPaste`).
  - Cut is `cutCells` in `paneleditor.js`: `copyCells` (which returns whether the write worked), then one `setGrid(clearSelection(g))`, the step an undo wraps. It removes nothing when the write fails or `g` moved during the await. Held Destination cells are out of `g`, so they are never copied or removed.
  - A paste is one `setGrid` in `pasteText` (`paneleditor.js`), the step an undo wraps. A plan that does not fit goes to `pasteOverflow`. It opens `askPasteEdge` (`editorpasteedge.js`) over `edgeChoices` (`gridedge.js`) and applies the pick as one `setGrid`. `edgeChoices` works out both choices first, so the dialog can count them. `pastePlan` drops skipped Destination cells itself, since passing them to `setGrid` would put them in `held` and store them.
  - Find hands its order in through `editor.useFillOrder(api.order)` at the end of `initFind`; Wrap reads it at paste time. `leave` ignores focus inside `#ed-edge`, or opening the dialog would deselect the grid and Cancel would not be a no-op.
  - Wrap walks the whole grid's `squareOrder` from the paste square to its last square, and returns the cells left in `left`. `edgeChoices` given `{ pages, from }` hands them to `cascadeWrap`, which fills later enabled blank Pages. `pasteOverflow` applies the choice inside one `edit` that also replaces the other Pages' cells, not through `setGrid`. So the paste and its cascade are one undo step. A Find fill does not cascade yet. `TestChromeEditorPasteEdge` drives Escape, Clip by the arrow keys, Wrap, undo and Find's order.
- Editor Pages: `g` is the focused Page (`focus`, its id), and `pages[fi()].cells` is stale while it is. `livePages()` is the list with them fresh. `pages()`, saves, the dirty check and painting read it. `open` is the ids side by side. `#ed-grid` always draws the focused Page, so Find, the grip, the menu and the paste reader keep their one node. `editorpageview.js` draws the others in a pool of three grids made one time, and places every frame with CSS `order`. Each `createEditorGrid` adds document listeners, so never make one per open. A press on another open Page calls `focusPage` and moves DOM focus to `#ed-grid`; only the press counts, not a drag that began there. `leave` ignores `#ed-open-pages`. Only an unsaved Page 1 has id `''`; the first save gives it one and `rekeyUndo` moves the undo steps to the new id. Page ops (`pageActs`) replace `pages` outside undo. A template apply is `replacePages(list, grid)`, a `list` step. The smart menu sits beside the selection and can cover the next Page's squares; the Chrome check presses Escape first.
- Editor undo: `edit(what, run, { join, list })` is the one place that records (rules in `gridundo.js`); `setGrid(next, { what, join })`, `setSize`, Copy to and `replacePages` go through it. It makes a `pageSnap` (every Page's cells by id, held Destination cells included) before the edit. It records only when `samePages` says some Page's cells changed, so selection moves and no-op edits store nothing. `what` is the status line's name for the step ("Undid <what>."). `join` merges a run of edits into one step (the Cell tab's caption and font size typing). A new caller that edits cells passes a `what`; a paste past the edge (Clip or Wrap) is one `setGrid(next, { what: 'paste' })`. `step` restores outside `edit` through `restorePages`, with `held` emptied first, so `holdOrPutBack` sets the Destination cells aside again. `restorePages` works by id, so a Page added since keeps its cells and one deleted since stays gone. A `list` step puts back the whole list. `show` empties the stack; `save` does not. `TestChromeEditorUndoRedo`, `TestChromeEditorPages` and the tail of `TestChromeEditorFixedDestsSaysWhatIsDropped` drive it.
- Fixed destination in the editor: while the list is not empty, `paneleditor.js` keeps Destination cells in `held`, out of `g`. It does this through `holdOrPutBack` in `setGrid`, `setFields` and `show`. `whole()` is the focused Page as stored, which `livePages()` reads. Other Pages are stored with their Destination cells and drawn with them set aside. Grid code never sees a held cell. So do not add a path that sets `g` outside those three and `step` (undo and redo). `myRights` is caught at import time in `editorrights.js`, which Find and the picker share.
