# Profiles (#161), guests (#187), sharing (#169)

A profile is a user's saved This browser settings, filter sets and presets, stored on the server so they follow the person. Third scope Me beside Everyone (global) and This browser (local). Exists only where users do; with nobody signed in there are no Me options or wording and a guest gets browser and everyone values.
- Config: User.Profile (config/profile.go: Prefs map, FilterSets, Presets; json:"-", never in hello). Normalized (what the browser gets) drops unknown prefs, and Normalize keeps them for the file. Validate reuses preset and filter rules, capped at MaxProfileBytes (48 KiB JSON). TestPrefTable compares Go prefs with prefs.js. SaveUsers carries a profile over by the row's user id (a rename keeps it); removed users lose theirs.
- Messages (app/profile.go): profile {name,prefs,filterSets,presets} is pushed only to connections signed in as that user (and after saves; {name:""} clears). profileSave {id,name,prefs?,filterSets?,presets?} (omitted parts kept) is allowed for your own name, or anyone's for a Trusted user or higher (rule.self, guardProfile under cfgMu). It answers profileSaveResult. profileGet needs a Trusted user. The command log notes whose profile and how many items, never values. profMemo caches each user's marshalled profile per config snapshot.
- Browser: web/profile.js is the one owner of the profile messages, since onMsg allows one handler per type. It has profile(), profileName(), bus profile, saveProfile(parts,name), fetchProfile, editTarget and pure toProfile. saveProfile is queued one at a time and updates its own copy at call time. A dropped socket settles pending calls with an error. saveProfile emits profileSaved. Prefs resolve this browser, then Me, then Everyone, then built-in (resolve in prefs.js; device.js defaultPref/myPref). Settings labels: Default (X), X (my default), X (everyone's default), with Set/Clear my default buttons. Sets and presets use scope user (userSets, userPresets). Active entries are {scope:'user', user, name}, so another user never picks up a same-named set; followProfile. Me presets have their own pinned; sode-preset-pins is for everyone's presets only. Saving to Me uses profilesaver.js profileSaver (no PIN row, refuses oversize).
- Guests: the last user's prefs are cached in localStorage sode-profile-prefs {user,prefs} for pre-paint. But cachedProfile (prefs.js, repeated in prepaint.js) uses them only while a session token is kept. device.js drops them on an access event for nobody or another user.
- Profile editor (profiles.js, profilesrules.js): bus openProfile {name} (own from cache, others through fetchProfile). It has a select per pref (prefFields, prefsWith; Not set removes) and Add/Edit/Remove for sets and presets, saved with saveProfile. Entry points: Profile… per saved row in Manage users (profileButtonOff for new or renamed rows). Trusted users without the PIN see S.userNames with Profile… buttons. My profile… and Export & Import… are in the signed-in user's block. Add/Edit emit openFilterEditor / openPresetEditor {user,name?,profile}. filters.js and presets.js then swap in a profile target from editortargets.js and save through profileSaver({target}). They must not import profiles.js. Pref changes apply optimistically (withParts). Wording: never call a profile private; admins and trusted users can see and edit all. Per-user restrictions are #184, not built; profiles.js marks where.
- Dialogs: trapDialog (dialogkeys.js) returns {show(), hide()}; use them, do not flip root.hidden. One document capture handler sends Esc to the newest open dialog (topDialog): no per-module Esc handlers or observers. Backdrop close needs mousedown and click both on the backdrop. show() moves the root to the end of its parent (bringToFront).
- Item links (itemlink.js, pure) hold ids only, never a copy. A preset's is `#preset=<id>&install=<uid>`. A panel's is the panel link plus `#install=<uid>`. The install is the config's `installUid` (made once, written back by Load, kept through a config import), sent as the hello's installUid. A link from another install opens nothing and says so; anything that goes to another install goes through Export. exportfmt.js is pure, for the review sheet: doc building, matching against live names (ambiguous never first-match), conflicts, "Name 2" renames, size checks. reviewsheet.js is the one review sheet (Use new / Use current / Skip / Rename, target scope). Use current and Skip leave the item out. It saves only through existing savers; a lock closes it. itemlinkopen.js opens a preset Item link in the preset popup on that preset. The link stays in the address until itemLinkStep can judge it. It waits for the install, the names, an access event and no lock up. For a signed-in user it also waits for the profile with the Me presets. Then the address is cleaned. The preset editor's Item link button (itemlinkview.js) shows the link, Copy link and a QR code. The panel link row (panellinkrow.js) shows the panel's Item link, with a QR code in the Share modal. A panel page opened by a link with an install waits for the hello before it runs (panelpage.js).
- Export file (v2, app/exportfile.go, exportload.go, exportschema.go, exportroute.go): one zip. It holds `manifest.yaml` and one YAML file per category. It also holds `names/<router uid>.yaml` per router, in the saved names table form. Images are plain files under `art/panels/<panel id>/`, `art/defaults/` and `art/icons/`. `exportEntryRe` is the fixed list of entry names, and the import refuses all other names. The manifest holds `exportFormat`, which is not config.Format. It also holds the Sode version, the install UID and per router the UID, prefix, title, matrix, levels, level offset and numbering. Per router it also holds `namesHash`, a hash of the names only. Items write the router prefix in `router` and `hiddenDstsRouter` (`toPrefixes`). With one router a reference (a mapping with `n`) leaves it out, and a filter set or `hiddenDstsRouter` keeps the prefix. The loader puts the UID back (`toUIDs`). With one router, a reference with `n` and no router gets that router. settings.yaml is by section (`exportSections`, the data-section names of the page). TestExportSectionsCoverTheConfig fails on a config key that is in no section and not in `exportNotSettings`. Users carry the PIN hash and length only with `includePins`. API clients keep the user id of their owner. No keys, tokens, History, Communication Log, uptime or Sent lists go. `POST /api/export` takes the JSON `exportReq` and answers the zip. `exportReq` has categories, per-item `pick`, `sections`, `includePins` and the values of This browser in `browser`. browser.yaml holds This browser's own preferences as top-level keys, with `filterSets` and `presets` beside them. `POST /api/import` writes the upload to `import-staging/` beside the config, checks it and answers `importCheck`, which holds the Add import plan. A zip body gets the preselected choices. A multipart body (plan, then file, as for the apply) gets the plan for those ticks and choices, and writes nothing. The Import tab uses it for its list and for Review…. Each plan item has `size`, the bytes of its file item with its images. Then it removes the staging directory. `GET /api/export/items` (exportitems.go) lists each category with its items and sizes. An item's `id` is what `pick` takes for it, and `router` says it names the router. TestExportItemsRoundTripThroughPick keeps the two in step. `POST /api/export/size` answers the zip size of an `exportReq`. All four routes need the session token of an Administrator in `X-Sode-Session` (`httpAdmin`). The socket message `exportSession` (any signed-in user; a Guest gets none) answers the connection's token. A connection with none gets a tab token, as with `sessionKey`. The page keeps the token in memory only. With no users, every caller is an Administrator, as in roleMu. Caps: `exportMaxUpload`, `exportMaxEntries`, `exportMaxEntry` (vars for tests). The import reads an entry through a limit and ignores its header size. A format above `exportFormat` is refused with "made by a newer Sode". Each format has a loader in `exportLoaders` and a hand-written fixture in testdata/export-v<N>/. The loader removes and lists the keys that a known format does not name (`pruneUnknown` walks the node beside the Go type). A file with two routers that share one UID is refused.
- Add import (app/importplan.go, importapply.go): `POST /api/import/apply` takes multipart/form-data, the `plan` part (`importReq` JSON: mode `add`, categories, pick, sections, choices) first, then the `file` part. It stages the file again, so no state is kept between check and apply. `planImport` runs under cfgMu and is the one source for both routes. Categories are planned in order: Settings, Routers, Users, Presets, Filter sets, API clients, Artwork, Panels, This browser. Each is planned on a copy that `validateSave` checks alone. So a refused category leaves the others (all or nothing per category). With no categories given, Routers and This browser are left out: a file brings its router for the references, and This browser is the page's. Only a router with the live UID applies. Matching: a file from this install (install UID) by hidden id, then by name; a foreign file by name. Choices per category and item key (`importItem.Key`): `new`, `current`, `skip`, `rename` ("Name 2", `nextName`); unset is `new` for this install and `rename` for a foreign file. An item equal to the live one is `same` and writes nothing. Critical: any `new` on a clash that changes something, Settings sections included. The route then needs a PIN recheck on a connection of the same session token (`tokenRechecked`), else 403 `recheck`. Users arrive PIN needed (no hashes in this release); `new` on a live user keeps that user's PIN. File user ids map to live ids, and API client and panel owners follow the map. An owner the import leaves out, or one without a PIN (as `dropOwnerless` would drop), becomes the importing Administrator. A panel's own API client is not imported and is listed with `refused`, since imported panels need a new key link. `new` on a panel keeps the live Authentication mode and client. Panel Share names follow the user map; a foreign name the import does not map is left out. Each panel passes `validatePanel`, and a public panel waits while Public panels allowed is off. Such an item gets `refused` and the rest of its category imports. References are checked against the live names (`refCheck`): router UID, level range, name at the number (case and spaces ignored, both blank agree). What does not agree goes in the item's `broken` list (`config.Missing`). Presets (Me presets too), filter sets (router only) and panels have it. On a panel, cells, Grid edges and preset buttons the import skipped are checked. Rights keep their references unmarked. With no names read yet, a category with references is refused and waits. The stores outside config.yaml are written after the config commit, one at a time (app/importrest.go). The order is Icon library icons, Default artwork, panels with art and Push checkpoints, templates, Checkpoint sets. A failed write is in `failed` by item key and the others stay. Plan items there carry `kind` (panel, template, checkpointSet, icon, default). An icon matches by id, then by name. Rename gives it a new id. Each `lib:<id>` in the file's items then gets the icon's id here (`libTo`), and Skip drops the reference. A Default artwork entry gets its preset through the preset map, or is refused for another router. It has no Rename. A new panel, template or set keeps its file id when it is free (`createAs`, `insertAs`), so links to it still open it. Set entries get the panel ids here, which the panel writes fill in. Push checkpoints are added to the panel's by id, newest `panelCheckpointMax` kept. This browser is one item. The check answers the file's values in `browser`, and the page applies them after the apply (web/browserimport.js). Only known preferences pass; filter sets and presets merge by name. One Settings saves row (why `import`) carries `import`: mode and counts per category, no values. The API audit rows (`auditAPISettings`, `auditRequireHTTPS`) follow as for a save; Require HTTPS from a request that is not secure refuses Settings.
- Send a copy and the Inbox (#603; app/inbox.go store, inboxsend.go, inboxaccept.go): socket messages `inboxList`, `inboxSend`, `inboxReview`, `inboxAccept`, `inboxDecline`, `inboxWithdraw`. Each carries its body in `inbox` (`inboxReq`) and is answered `inboxResult` with `op`. Every rule is open in the policy table; the handlers refuse a Guest (`errGuestInbox`), and a user with or without a PIN passes (`ownUser`). Never Critical, since an accept writes only the recipient's own items.
  - Send: `to` names users. Me (`user`) and Everyone (`global`) presets go by id, filter sets by name, panels by id. The server reads each item and checks that the sender can see it (`panelReach` for panels). This browser (`local`) items come whole and get a new id. One card per recipient holds a frozen copy. A panel loses its sharing, client, short name, Rev and owner, and its uploaded artwork is copied into the card. If one recipient has `inboxWaitingMax` (100) waiting cards, the whole send is refused with "<name>'s Inbox is full".
  - Store: `inbox/<card id>.yaml` beside the config, artwork in `inbox/<card id>.art/<panel id>/<art id>`; memory only without a config file. No export reads it. A card leaves `waiting` once: `accepted` (with `accepted`, the number of items written, for "Accepted 4 of 5"), `declined`, `withdrawn` or `expired`. Then its items and artwork go, and the line stays in the Sent list for `inboxKeep` (30 days). A waiting card expires `inboxTTL` (30 days, an App field so tests shorten it) after it was sent. `periodic` sweeps once a minute, and every send, list and answer sweeps first.
  - Push: `inbox` (`inboxMsg`) holds `cards` (waiting for the user), `sent` (by the user) and `new` (the card ids that arrived now, one toast each). It goes only to connections signed in as that user. It goes on every change to their cards and from `pushAccessMu`, so a sign-in gets the count. Losing the user sends an empty one. Not in the hello.
  - Accept: `inboxReview` plans and writes nothing; `inboxAccept` plans again under cfgMu and writes. Both answer the Add import's `importPlan` and take its `pick` and `choices` (`planCard`). The categories are presets, filterSets and panels. The keys are the card's preset id, filter set name and panel id. Clashes are only with the recipient's own Me presets, Me filter sets and panels, by name, and default to `rename`. `refCheck` marks Broken references as in the import, and with no names read a category waits. "Outside your Rights" in `note` marks an item with a route the recipient's Rights do not reach; it still imports. Me lists change in one commit; panels follow one by one. A new panel is the recipient's, shared with nobody. A panel that is its own API client gets a new client with no keys. That client has the recipient's Rights, as for a panel made in the editor. `new` on a panel keeps the recipient's panel's id, sharing, short name, mode and client. Decline and withdraw also take cfgMu, so they cannot cross an accept.
  - Users: `panelsFollowUsers` calls `inboxFollowUsers`, so the one Save and every import apply it. A removed recipient's waiting cards end `expired` for the sender. A removed sender's cards stay, and `from` is empty ("from a removed user").
  - Log: command rows `inboxSend` (Note `to <names>: <counts>`), `inboxAccept` (`from <name>: accepted N of M`), `inboxDecline`, `inboxWithdraw`, and `inboxExpired` by Sode. History gets nothing.
- Export & Import dialog (web/exportdialog.js, pure rules exportrules.js, routes and session token exportcalls.js; Settings > Server, `#xi-open`): `pb-modal--md` with Export and Import tabs. Export ticks categories and items from `api/export/items` and keeps Include PINs (default on). After each change it asks `api/export/size` (debounced) for the size on the Export button. It downloads the zip from `api/export`. Back up everything sends `backupBody`: all nine categories, PINs, This browser's values. The router shows Always included and Brought by <item> when a ticked item names it. A picked panel, template or Default artwork entry brings the Icon library icons it uses (`libIcons`, the list's `icons`). Those icons show ticked with Brought by <item>. The Import tab (importtab.js, pure rules importrules.js) is one long review. It shows the file line, Add import and the planned categories, open and ticked (Routers not). Each item has a tick and a size. A ticked clash shows its choices (`segmented`), and a Broken item its missing names. Router names come last (the remap step below). Settings and Routers offer no Rename, since the server turns it into Use new there. Default artwork offers no Rename (`choicesFor(cat, it)`). Review… sends the ticks and choices to the check and puts the answer in the dialog body. It shows counts per category, Broken items and dropped unknown keys. A Critical plan shows Back up everything first and the PIN field on one row. Import sends the PIN with recheck.js `recheckPin` (no second `pinRecheckResult` handler), then the apply. A 403 `recheck` shows on the PIN row. On the phone the dialog shows only the desktop-only message.
- Remap step (importremap.go; web importremap.js, pure rules remaprules.js): the plan's `remap` holds each file router's `target`, its candidates and its `refs`. The target is the one in `importReq.routers`, else the default: the same UID, then the same `namesHash`, then the only router. A candidate gives names found of total, with trim and case ignored. `refs` has one row per distinct file source or destination, with key `<file uid>:<kind>:<n>` and use counts. `targets` holds the live names. The page matches names (as is, moved, missing, dup-target, blank) and sends `importReq.names`: key to target numbers, two for Add both (destinations). `planRemap` runs before any check. It moves every reference of a router with a target to that router, then puts the chosen number and the live name in. A reference with no choice keeps its number, so an unmatched name is Skip and the item arrives Broken. A router with no target keeps the file's UID, so its items arrive Broken with the router missing. A slot that holds one reference (a cell, a Grid item, a preset source) takes the first number. `checkRouterTargets` refuses a target that is not a live router and two file routers on one target (400). In the list the item's Broken list is filtered by the page's choices (`stillBroken`); Review… gets the server's. Filter terms, bulk actions, row selection and the router offline are #598.
- Own items (app/ownexport.go, web/ownexport.js; My user, `#account-transfer`): any signed-in user exports and imports their own profile, Me presets and Me filter sets. The routes are `GET api/own/export/items`, `POST api/own/export`, `POST api/own/export/size`, `POST api/own/import` (check, multipart only) and `POST api/own/import/apply`. They take the user's session token (`httpOwn`: any Role, never a Guest). The export takes `profile`, `presets` and `filterSets` and refuses every other category. Its zip is an ordinary export. users.yaml holds the one user with Role and Rights and no PIN hash (`exportReq.only`). The profile holds only the picked parts, and the router goes with it as usual. An Administrator can import it in the Users category. The import reads one file user (`ownFrom`): the only one, else the importer by id on a file from this install, else by name. It plans with `cardPlanner`, the planner of the Inbox accept. With `file` set, an equal item is No change. With `same` (a file from this install), it matches by hidden id and preselects Use new. Profile (prefs and pin order) is one item, `Replaces your profile`, overwritten whole. Mode is `add` only, nothing is Critical, and the apply writes only the importer's profile in one commit. It writes one Settings saves row (why `import`), with counts and no values. The check answers `admin`: the file's categories that only an Administrator imports. The page shows them greyed as Administrators only (`ADMIN_ONLY`; presets and filterSets there are Everyone's). The dialog reuses importtab.js with `own`, and its Export tab lists the own categories and the greyed ones. It has no remap step: items that name another router arrive Broken. Desktop only.
