# Users and locks (#151)

Moved from AGENTS.md unchanged.

Off by default. cfg.Users [{name, pin hash (json:"-"), len, trusted, persistent}] (max 12, unique names ignoring case, PINs 4-12 digits unique across users), cfg.Locks{main,log}, cfg.AutoLockMinutes. A lock needs a user and a settings PIN (Validate; -reset-pin turns locks off). The user list and maxPinLen are saved only by the users message (SaveUsers), which needs the connection settings-unlocked (a trusted user is not enough); saveSettings carries it over. Locks and auto-lock are ordinary Settings fields tagged guard:"pin"; a config message without a locks or autoLockMinutes key keeps live values (a missing key must never read as every lock off). Web GUARDED in lockrules.js mirrors the tag.
- Policy table (internal/app/policy.go): one closed map from every client-to-server type to its need, checked once by admit before the read loop switch; unlisted types are dropped. TestPolicyCoversEveryMessage parses http.go and fails on a mismatch. Needs: open (hi, userUnlock, userLock, userSetPin, unlock, lock, history), needTake (batch: main lock), needMain (refreshNames; clearHistory also needAdmin), needLog (sent, uptime), needAdmin (users, clearHistory: settings PIN when set, and not the main lock, so a locked wall panel can still save with the PIN), needTrusted (config, filterSets, presets: settings PIN, or a connection unlocked as a user who still exists with the same hash and is Trusted now in live config). config becomes needAdmin when it carries pin or clearPin. guardSave repeats the check under cfgMu. A refusal logs a locked command and answers lockState (page lock), locked (settings PIN), or a failed <op>Result echoing id (batch gets a failed takeResult per item).
- Locks cover actions and log reads, not data: hello, names, tally, history keep streaming to locked browsers. Main lock: batch, refreshNames, clearHistory. Log lock: sent log and uptime. Pages declare type with hi {page, token}; /healthz and /api/health stay open. History Client, Why.By and event By use c.who() (user name, else IP).
- Access state (users.go): client.u is a connUser (page, token under mu, unlocked *config.User in an atomic.Pointer). pageAllowed: lock off, or an unlocked user who still exists with the same hash. ...Locked means caller holds mu. syncAccess(c) sends lock state and stops the sent feed for connections no longer allowed.
- PIN pools (pin.go): one method tryPin(pool, from, check). a.pin (settings): doubling waits from 30s after the 5th wrong try up to an hour, pinMaxTries locks for good, resets on success. a.userPin (userUnlock): same waits capped at 5 minutes, no permanent lock, a right PIN does not reset the count (else a holder of one PIN could guess the rest), forgotten after an hour clean. Pools never touch each other. PIN only, no name; a length no user has is just a wrong try.
- Persistent sessions (tokens.go, user flag persistent): userUnlock for a persistent user issues a token (issueSession, no disk I/O under mu): 32 random bytes base64url, only sha256 kept, in memory and tokens.json beside config (0600, temp file, fsync, rename). Record {user, pin hash, at}; tokenStore.user re-reads the live user on each use, so a changed PIN, removed or renamed user or unticked Persistent kills it. Max 8 per user and kind. Browser keeps it in localStorage sode-session and sends it in hi; a wrong one is ignored. userLock always revokes the connection's token and relocks other connections holding it. Non-persistent users get the idle timer and PIN on reconnect. Old admin-token files load as nothing; a damaged file is forgotten.
  - Catch-up (#159): catchUpSessions (end of applyConfig and UserSetPin) gives every connection unlocked as a persistent user without a good token one, as {t:"session",token}. issueSession is idempotent and drops its token if the connection locked or got another meanwhile.
  - localStorage rather than a cookie: hi already carries the token over the WebSocket, so no HTTP endpoint, cookie flags or CSRF. A cookie could be HttpOnly, but the page never uses innerHTML, the token only acts as that user, and the server caps and revokes.
- Hardening: tokenStore.prune(cfg) deletes every record invalid against live config, run at the end of a.update and in New, so untick/retick, rename A to B to A, or PIN changed and restored never revive a token. Tokens die after tokenMaxAge (90 days) unused; hi or an open connection (touchSessions hourly) renews. userSignOutAll {name,id} (needAdmin) deletes a user's tokens and relocks them. UserUnlock clears the connection's token. A trusted-only Settings save may not change router, trustedProxies or pinMaxTries (trustedMayNotChange; guardedErr counts as errLocked so the page asks for the PIN; guardedEdited in lockrules.js asks up front). CSP: secureHeaders in http.go sets one policy (script-src 'self', frame-ancestors 'none'), nosniff and Referrer-Policy same-origin; pages must have no inline scripts, on*= handlers or javascript: URLs (TestNoInlineScript).
- Trusted users make low-risk saves without the settings PIN (Settings form, filterSets, presets). Always the PIN: clearHistory, router or pin guarded fields, users, any settings PIN change. lockState carries trusted, lens, and hi (only on the answer to the page's own hi; lock.js forgets its token only then). pin.js trusted() and needsPin() (lockrules, pure) replace S.pinSet && !unlocked() in Settings and globalsave.js. That only hides the prompt: when the server refuses, demandPin() makes needsPin true until the PIN is entered or Settings close.
- Removed: adminUnlock, admin sign-in, Forget this browser, sode-lock-never, userLock suspend, exempt, the admin chip. lock.js deletes old sode-lock-token and sode-lock-never. A wall panel logs in once as a trusted persistent user.
- Frontend: lock.js (overlay, Ctrl+L, idle timer; emits locking, unlocked, access; restores focus), lockrules.js (pure), lock.css, users.js (#165/#168: Settings > Users is a summary plus Manage users… (#users-manage); the editor is its own pb-modal with trapDialog: row per user, lock main/log, auto-lock minutes, longest PIN, own Cancel/Save; saves with users, shows server errors, asks for the PIN in the popup and saves again on refusal; holds no rules; Esc with edits warns once; locking closes it). Other modals are closed by lock.js clicking their Cancel/Close.
- Lock polish:
  - Chip (lockchip.js): Logged in as <name>, fixed top left below the lost-link banner (--sode-down-h), on phone under the header (--sode-head-h). One icon lock button (Ctrl+L). Account block in This device (hidden unless logged in; DICT account, account-pin, account-logout): Change my PIN (bus changePin) and Log out (bus logout: ends session, revokes token, shows pad).
  - Phone chip: no lock button (CSS hides it, and the whole cell until a lock screen shows its closed lock, .is-hand); hidden when it has no name; the lock screen's brand text wraps. A phone locks by idle, the hand lock in Settings, or logging out. The chip's left/top transition exists only while data-sode-lock is set, so it doesn't float when the lost-link banner moves it.
  - Animation: logo move via Web Animations (moveBrand, brandFrames), fresh keyframes each run. Way out lasts OUT_FACTOR (1.5) times the way in. Reduced motion = no animation, text still shows. shouldFly: logo flies only for an unscrolled page with the logo fully in view.
  - Pad feedback: right PIN shows Welcome, <name> and unlocks after WELCOME_MS (600); wrong PIN shakes and shows Incorrect for WRONG_MS (1s); server wait notes go under it. Text always carries status.
  - Scroll survives lock and unlock (preventScroll focus, data-sode-lock on html stops desktop.js focus-scroll).
  - Pad auto-submits only at the longest PIN length in use (sendDelay null for shorter, so 1234 never sends when 12345 exists). Check key and Enter send if some user has that length. Pad stops at min(longest, maxPinLen).
  - maxPinLen (SODE_MAX_PIN_LEN seeds, default 8, 4-12, owned, saved by users, 0 keeps). Validate rejects longer user PINs; older files get max(8, longest) in Normalize.
  - userSetPin {old,new,id}: policy open but requires the connection unlocked as a user; old is a try in the user pool; saved without the settings PIN; this connection stays unlocked, the user's others relock and their tokens die.
  - Takes by a configured user show a small by <name> (byLabel, actorUser, folderActor); never an address; ext/found show none; a folder shows it only when all takes share one user.
- Tab login (users, no lock): Settings > This device shows Log in (bus login). userUnlock carries tab:true; issueSessionTab issues a tab-marked token for a non-persistent user only where the page's lock is off, same caps and revocation; valid only while the user is not persistent, 48h (tabTokenMaxAge, open tab renews); Hi ignores it once the page is locked. Browser keeps it in sessionStorage sode-tab-session. No idle lock. The hand lock has Log in as… (loginFromSoft); Cancel returns to it. The page's lock view is one value V {mode: page|soft|login, back} in lock.js with pure transitions in lockrules.js; lockState ends a login only on a real unlock or enforced lock. lock.js emits handlock {on}. html carries data-sode-lock while any overlay is up and data-sode-lock-on exactly with the overlay's is-on (drives chip geometry; 0ms under reduced motion). Chip button shows lock-open or lock (chip.setLocked); hidden under hand lock, where .sode-lock__who-ico shows a static closed lock.
- PIN popup (pinprompt.js): the one prompt for a settings PIN needed mid-session, so Settings keeps its layout. askPin(why) resolves true once pin.js unlock succeeds (false: cancelled, socket dropped, page locking; true also if a hello says no PIN is set now); reask(why) first marks this connection's unlock lost (pin.lostUnlock), for a refusal. Used by Manage users (open, usersList/users/userSignOutAll refusals), the config file (export, import begin, retry after a refusal), clear history (pre-check, and a bare `locked` while one is pending), the Settings form (pin/guarded edits by a trusted user; a configResult refusal) and profile read/save refusals. Each retries the action once the PIN is in. pin.needsPin is just pinSet && !unlocked && !trusted (no forced flag): only a non-trusted connection's Settings flips to the inline prompt at the top of the page (renderLock; also on a bare `locked`). globalsave.js keeps its own in-dialog PIN row (filters, presets, review) and relocks after. Clear history reports success from the server's historyCleared (history.js emits it on the bus), not at send time.
- Logged-in lock (#198): with a user logged in and no PIN lock on, every way into the hand lock (chip button, Ctrl+L, Settings Lock, idle) goes to pinLock in lock.js instead: view mode MODE.OWN (lockrules MODE; userLock; viewBody pad, no Cancel, Esc only clears), lockNow() ends the session on the server (userLock, tokens revoked), and a right PIN (userUnlock, tab token again) ends it through loginWon. softLock returns at once under MODE.OWN. The one Log out button in the foot (logOutBtn) does lockNow() under the hand lock and, for MODE.OWN, just takes the pad away (the session already ended). A reload shows the page with nobody in. The letter hand lock is for pages nobody is logged in on. The overlay is .sode-lock__main (brand + bodies, centred) over an in-flow foot, 100dvh tall.
- Hand lock (#158): where no PIN lock applies and nobody is logged in, Ctrl+L or Settings > This device > Lock screen (bus softLock) shows the overlay with softBody: Press X to unlock (churnKey, shared with keyconfirm.js), an Unlock button, and Log in as… / Log out. Honors confirm lockout and confirmEnter. Purely page state, no server message, reload clears it. While up, the capture keydown handler stops every key reaching the page (browser chords pass, so Ctrl+Z can't undo a take underneath). Idle timer raises it after autoLockMinutes (softIdleLock). An enforced lock cancels it. A guard against mashing, not security.
