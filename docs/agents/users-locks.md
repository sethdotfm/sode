# Users and locks (#151)

Moved from AGENTS.md unchanged.

Off by default. cfg.Users [{name, pin hash (json:"-"), len, trusted, persistent}] (max 12, unique names ignoring case, PINs 4-12 digits unique across users), cfg.Locks{main,log}, cfg.AutoLockMinutes. A lock needs a user and an Advanced Settings PIN (Validate; -reset-pin turns locks off). The user list and maxPinLen are saved only by the users message (SaveUsers), which needs a connection that holds the Advanced Settings PIN (a trusted user is not enough); saveSettings carries it over. Locks and auto-lock are ordinary Settings fields tagged guard:"pin"; a config message without a locks or autoLockMinutes key keeps live values (a missing key must never read as every lock off). Web GUARDED in lockrules.js mirrors the tag.
- Policy table (internal/app/policy.go): one closed map from every client-to-server type to its need and its handler (handle, run with the read loop's connCtx), checked once by admit before the handler runs; unlisted types are dropped. A handler chooses inline or goroutine itself (`unlock` and userUnlock inline). TestPolicyCoversEveryMessage fails on a rule without a handler or a switch on the type creeping back. Needs: open (hi, userUnlock, userLock, userSignOut, userSetPin, `unlock`, lock, history), needMain (`batch`, refreshNames; clearHistory also needAdmin), needLog (sent, uptime), needAdmin (users, clearHistory: Advanced Settings PIN when set, and not the main lock, so a locked wall panel can still save with the PIN), needTrusted (config, filterSets, presets: Advanced Settings PIN, or a connection signed in as a user who still exists with the same hash and is Trusted now in live config). config becomes needAdmin when it carries pin or clearPin. guardSave repeats the check under cfgMu. A refusal logs a locked command and answers lockState (page lock), locked (Advanced Settings PIN), or a failed <op>Result echoing id (`batch` gets a failed takeResult per item, via the rule's onRefuse).
- Locks cover actions and log reads, not data: hello, names, tally, history keep streaming to locked browsers. Main lock: `batch`, refreshNames, clearHistory. Log lock: Communication Log and uptime. Pages declare type with hi {page, token}; /healthz and /api/health stay open. History Client, Why.By and event By use c.who() (user name, else IP).
- Access state (users.go): client.u is a connUser (page, token under mu, the signed-in *config.User in an atomic.Pointer). pageAllowed: lock off, or a signed-in user who still exists with the same hash. Names ending in Mu mean the caller holds mu. syncAccess(c) sends lock state and stops the sent feed for connections no longer allowed.
- PIN pools (pin.go): one method tryPin(pool, from, check). a.pin (settings): doubling waits from 30s after the 5th wrong try up to an hour, pinMaxTries locks for good, resets on success. a.userPin (userUnlock): same waits capped at 5 minutes, no permanent lock, a right PIN does not reset the count (else a holder of one PIN could guess the rest), forgotten after an hour clean. Pools never touch each other. In PIN only mode a try carries no name; a length no user has is just a wrong try. Username and PIN mode: see Sign-in mode below.
- Persistent sessions (tokens.go and sessions.go, user flag persistent): userUnlock for a persistent user issues a token (issueSession, no disk I/O under mu): 32 random bytes base64url, only sha256 kept, in memory and tokens.json beside config (0600, temp file, fsync, rename). Record {user, pin hash, at}; tokenStore.user re-reads the live user on each use, so a changed PIN, removed or renamed user or unticked Persistent kills it. Max 8 per user and kind. Renaming a user ends their sessions (the lookup is by name); Manage users says so, and TestRenameEndsPersistentSession covers it. Browser keeps it in localStorage sode-session and sends it in hi; a wrong one is ignored. userSignOut always revokes the connection's token and signs out other connections holding it; userLock only sets the token's Locked flag. Non-persistent users get the idle timer and PIN on reconnect. Old admin-token files load as nothing; a damaged file is forgotten.
  - Catch-up (#159): catchUpSessions (end of applyConfig and UserSetPin) gives every connection signed in as a persistent user without a good token one, as {t:"session",token}. issueSession is idempotent and drops its token if the connection locked or got another meanwhile.
  - localStorage rather than a cookie: hi already carries the token over the WebSocket, so no HTTP endpoint, cookie flags or CSRF. A cookie could be HttpOnly, but the page never uses innerHTML, the token only acts as that user, and the server caps and revokes.
- Hardening: tokenStore.prune(cfg) deletes every record invalid against live config, run at the end of a.update and in New, so untick/retick, rename A to B to A, or PIN changed and restored never revive a token. Tokens die after tokenMaxAge (90 days) unused; hi or an open connection (touchSessions hourly) renews. userSignOutAll {name,id} (needAdmin) deletes a user's tokens and relocks them. UserUnlock clears the connection's token. A trusted-only Settings save may not change router, trustedProxies or pinMaxTries (trustedMayNotChange; guardedErr counts as errLocked so the page asks for the PIN; guardedEdited in lockrules.js asks up front). CSP: secureHeaders in http.go sets one policy (script-src 'self', frame-ancestors 'none'), nosniff and Referrer-Policy same-origin; pages must have no inline scripts, on*= handlers or javascript: URLs (TestNoInlineScript).
- Trusted users make low-risk saves without the Advanced Settings PIN (Settings form, filterSets, presets). Always the PIN: clearHistory, router or pin guarded fields, users, any Advanced Settings PIN change. lockState carries trusted, lens, and hi (only on the answer to the page's own hi; lock.js forgets its token only then). pin.js trusted() and needsPin() (lockrules, pure) replace the plain S.pinSet test in Settings and globalsave.js. That only hides the prompt: when the server refuses, demandPin() makes needsPin true until the PIN is entered or Settings close.
- Removed: adminUnlock, admin sign-in, Forget this browser, sode-lock-never, userLock suspend, exempt, the admin chip. lock.js deletes old sode-lock-token and sode-lock-never. A wall panel signs in once as a trusted persistent user.
- Frontend: lock.js (overlay, Ctrl+L, idle timer; emits locking, `unlocked`, access; restores focus), lockrules.js (pure), lock.css, users.js (#165/#168: Settings > Users is a summary plus Manage users… (#users-manage); the editor is its own pb-modal with trapDialog: row per user, lock main/log, auto-lock minutes, longest PIN, own Cancel/Save; saves with users, shows server errors, asks for the PIN in the popup and saves again on refusal; holds no rules; Esc with edits warns once; locking closes it). Other modals are closed by lock.js clicking their Cancel/Close.
- Lock polish:
  - Chip (lockchip.js): Signed in as <name>, fixed top left below the lost-link banner (--sode-down-h), on phone under the header (--sode-head-h). One icon lock button (Ctrl+L). The signed-in user's block in This browser (hidden unless signed in; DICT ids account-pin, account-logout): Change my PIN (bus changePin) and Sign out (bus `logout`: ends session, revokes token, shows pad).
  - Phone chip: no lock button (CSS hides it, and the whole cell until a lock screen shows its closed lock, .is-hand); hidden when it has no name; the lock screen's brand text wraps. A phone locks by idle, the Lock in Settings, or signing out. The chip's left/top transition exists only while data-sode-lock is set, so it doesn't float when the lost-link banner moves it.
  - Animation: logo move via Web Animations (moveBrand, brandFrames), fresh keyframes each run. Way out lasts OUT_FACTOR (1.5) times the way in. Reduced motion = no animation, text still shows. shouldFly: logo flies only for an unscrolled page with the logo fully in view.
  - Pad feedback: right PIN shows Welcome, <name> and signs in after WELCOME_MS (600); wrong PIN shakes and shows Incorrect for WRONG_MS (1s); server wait notes go under it. Text always carries status.
  - Scroll survives the Lock and its dismissal (preventScroll focus, data-sode-lock on html stops desktop.js focus-scroll).
  - Pad auto-submits only at the longest PIN length in use (sendDelay null for shorter, so 1234 never sends when 12345 exists). Check key and Enter send if some user has that length. Pad stops at min(longest, maxPinLen).
  - maxPinLen (SODE_MAX_PIN_LEN seeds, default 8, 4-12, owned, saved by users, 0 keeps). Validate rejects longer user PINs; older files get max(8, longest) in Normalize.
  - userSetPin {old,new,id}: policy open but requires the connection signed in as a user; old is a try in the user pool; saved without the Advanced Settings PIN; this connection stays signed in, the user's others relock and their tokens die.
  - Takes by a configured user show a small by <name> (byLabel, actorUser, groupActor); never an address; ext/found show none; a Group shows it only when all takes share one user.
- Tab sign-in (users, no lock): Settings > This browser shows Sign in (bus `login`). userUnlock carries tab:true; issueSessionTab issues a tab-marked token for a non-persistent user only where the page's lock is off, same caps and revocation; valid only while the user is not persistent, 48h (tabTokenMaxAge, open tab renews); Hi ignores it once the page is locked. Browser keeps it in sessionStorage sode-tab-session. The Lock has Sign in as… (loginFromSoft); Cancel returns to it. The page's lock view is one value V {mode: `page|soft|login`, back} in lock.js with pure transitions in lockrules.js; lockState ends the sign-in view only on a real sign-in or an enforced lock. lock.js emits handlock {on}. html carries data-sode-lock while any overlay is up and data-sode-lock-on exactly with the overlay's is-on (drives chip geometry; 0ms under reduced motion). Chip button shows lock-open or lock (chip.setLocked); hidden under the Lock, where .sode-lock__who-ico shows a static closed lock.
- PIN popup (pinprompt.js): the one prompt for an Advanced Settings PIN needed mid-session, so Settings keeps its layout. askPin(why) resolves true once pin.js `unlock` succeeds (false: cancelled, socket dropped, page locking; true also if a hello says no PIN is set now); reask(why) first marks this connection's PIN lost (pin.lostUnlock), for a refusal. Used by Manage users (open, usersList/users/userSignOutAll refusals), the config file (export, import begin, retry after a refusal), clear history (pre-check, and a bare `locked` while one is pending), the Settings form (pin/guarded edits by a trusted user; a configResult refusal) and profile read/save refusals. Each retries the action once the PIN is in. pin.needsPin is just pinSet && !`unlocked` && !trusted (no forced flag): only a non-trusted connection's Settings flips to the inline prompt at the top of the page (renderLock; also on a bare `locked`). globalsave.js keeps its own in-dialog PIN row (filters, presets, review) and relocks after. Clear history reports success from the server's historyCleared (history.js emits it on the bus), not at send time.
- Lock with a user signed in (ADR 0001, server-held): `userLock` (chip button, Ctrl+L, Settings Lock; lock.js lockNow()) raises the Lock and keeps the session. connUser.locked is under mu; the flag also rides the session token (tokenRec.Locked, tokens.json), so Hi with a locked token brings the connection up locked, and every connection sharing the token locks and resumes together. A non-persistent user has no token until the Lock: setHeld then issues a tab token (issueHeldTab, `session` with tab:true, sessionStorage), marked Locked, so a reload still shows the held Lock. Under a PIN lock Hi accepts such a token only while it is locked, and a resume deletes it, so a reload with no Lock still asks for the PIN. A locked connection is signed in to nothing: userOKMu is false, pageAllowedMu refuses every gate even with the page lock off, and trusted, profile and lockState's user fields go quiet. lockState carries held (no name, no flags) and locked; held with a user who is gone or whose PIN changed clears itself in lockStateMu. Resume is userUnlock (UserUnlock): while locked only the held user's hash is compared, another user's PIN is a wrong try in the user pool and never switches users. `userSignOut` (open, App.SignOut) ends the session: it revokes the token and signs out every connection sharing it. lock.js: lockrules lockCovers(L) (locked && (enforced || held)) decides the pad, raiseLock/signedOut give the state at once, tokenStale keeps the stored token while held; the foot's one Sign out button shows for held and does signOutNow(). A held Lock that ends with no user (heldEnded: signed out here or elsewhere, removed user, changed PIN) drops to the letter Lock when no PIN lock applies, so the page never uncovers by itself; one that ends with a user was resumed. The held pad names whose Lock it is from this tab's own memory (heldWho; sessionStorage `sode-held-user`, set in lockNow or when a held lockState arrives while a user was signed in; the server's held state stays nameless), shown in the chip (chipShown with heldUser). In Username and PIN mode a successful sign-in stores the name in localStorage `sode-last-user` (remembers: not for a Never sign out token), prefilled in the box and cleared by sign out or an ended Lock; it is the browser's memory and never comes from the server. With nobody signed in, userLock does nothing on the server and the letter Lock stays page state. The overlay is .sode-lock__main (brand + bodies, centred) over an in-flow foot, 100dvh tall.
- Lock with nobody signed in (#158): where no PIN lock applies and nobody is signed in, Ctrl+L or Settings > This browser > Lock screen (bus softLock) shows the overlay with softBody: the churning letter (churnKey, shared with keyconfirm.js), a button for touch screens, and Sign in as… / Sign out. Honors confirm lockout and confirmEnter. Purely page state, no server message, reload clears it. While up, the capture keydown handler stops every key reaching the page (browser chords pass, so Ctrl+Z can't undo a take underneath). Idle timer raises it after autoLockMinutes (localIdleLock). An enforced lock cancels it. A guard against mashing, not security.
- Auto-lock: the page times it (lock.js, idleLock in lockrules.js) and sends the same `userLock` as the Lock button, so the server-held flag already survives reload and reconnect and needs no server timer. Every signed-in user gets it, persistent users and tab sign-ins included, and it never signs anyone out. Idle is per browser: lock.js shares activity between tabs on a BroadcastChannel (seenActive, shouldShare in lockrules.js), so a background tab does not lock a session the user is working in. Known limit: a browser without BroadcastChannel, or two browsers sharing one session token, time idle on their own. With nobody signed in it raises the letter Lock (localIdleLock). lock_idle_test.go drives it through the policy table.
- Sign-in mode (#217): cfg.SignInMode, `pin` (default, also what a file without the key loads as, Normalize) or `username`. Owned, so a Settings save keeps the live value; it travels in the `users` message (usersReq.signInMode, "" keeps) and so needs the Advanced Settings PIN like any user change. A user has Username (yaml `username`, optional in `pin`, required for every user in `username`; trimmed, 24 runes at most, printable with no spaces, unique ignoring case, independent of Name). Switching to `username` keeps users, PINs and Profiles. Switching back is allowed unless users share a PIN (see below). A userEdit's username is a pointer: omitted keeps the old one, so a page that doesn't know usernames can't erase them.
  - PIN only is unchanged: PINs unique across users on save and on UserSetPin, and `userUnlock` ignores any `user`. Salted hashes can't show a shared PIN, so User.PinTag (yaml `pinTag`, never JSON) is a random token that users with equal PINs share. LinkEqualPin sets it wherever a PIN is typed in Username and PIN mode (SaveUsers, UserSetPin), by comparing the typed PIN with the other hashes; a unique PIN has none, TakePin carries it, and PIN only clears every tag. Going back runs SharedPinUsers over the users as they will be saved, after any new PINs, and refuses naming them; nothing is saved. A server config export without PINs also drops the tags (equal tags show who shares a PIN); a private backup keeps them. A file written before pinTag existed has no tags, so a clash made then is not seen. `usersListResult` marks each such user `shared` (needAdmin, never before the PIN), and the editor (pinClashes) asks for a new PIN for each before it sends.
  - Username and PIN: `userUnlock {user, pin, id, tab}` finds the user by `user` (FindUsername) and compares the PIN with that user's hash only. Unknown username, wrong PIN and another user's PIN are the same wrong try in the user pool. Shared PINs are allowed (SaveUsers and UserSetPin skip the uniqueness check). A held Lock resumes with the holder's PIN; `user` may be empty, and a `user` that names someone else is a wrong try.
  - Keeping usernames out of what is sent before the PIN: the hello blanks Users, lockState has `mode` (`pin` or `username`) but no username, and `names` stays display names. Only `usersListResult` (needAdmin) carries `username` per user and `signInMode`. TestUsernamesStayOutOfPublicMessages.
  - Screens (#218): `lockState.mode` lands in lock.js L.mode. lockrules asksUsername (mode `username` and not held) decides whether the pad shows the Username box; canSend and padDelay hold the send (the pad never auto-sends without a username, so a PIN typed first goes out when the name completes it), and signInMsg adds `user` only when asked. A held Lock resumes with the PIN alone. The box takes its own keys: the capture handler leaves digits and Backspace to it (Esc still leaves a sign-in) and Enter moves on to the PIN. Manage users (users.js, pure usersrules.js): a Sign-in mode select and a Username column shown only in `username` mode. usersReq sends `username` only while the column shows and `signInMode` only when changed from what usersListResult said, so the server's keep-the-old rules apply. The switch needs no warning either way. Fill empty usernames (#223, shown with the column): usersrules prefillUsernames gives each empty row its Name without whitespace, cut to 24 runes, with 2, 3... added on a clash ignoring case against typed usernames and earlier prefills. It never touches a typed username and is only a convenience: SaveUsers still refuses a missing or duplicate username.
