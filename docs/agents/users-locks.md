# Users and locks (#151)

Users and locks are off by default. The config fields are `cfg.Users`, `cfg.Locks{main,log,panel}` and `cfg.AutoLockMinutes`. `cfg.Users` is [{id, name, pin hash (json:"-"), len, role, persistent}]: at most 12 users. Names are trimmed, printable, at most 24 runes and unique ignoring case (`userNameRefusal` on save, Validate for files). PINs are 4-12 digits and need not be unique.
- User id (#546): `User.ID` (`u-` and 16 hex digits) is hidden and never changes. Everything stored refers to a user by it. That is session tokens (`tokenRec.User`) and user API keys (`keyOwner.User`). It is also the `owner` of a panel, a template and a Checkpoint set, and the set file name. Panel watch keys and an instance's `streamWho` use it too. So a rename keeps all of it. `FindUserByName` is only for a name a person typed (sign-in, `userSignOutAll`, profile reads); everything else uses `FindUserByID`. Normalize fills a missing id, and `config.Load` writes it back (as it does a new router UID), so the id outlives the start. `New` normalizes too. A config import (`KeepPins`) gives a file user with an unknown id the id of the live user of that name. JSON sent to pages carries the live name in `owner`, never the id (`panelOut`, `templateOut`, `setOut`). The users save names each row by `id` (none for a new row); `usersListResult` carries it. Panel `share.users` still lists names, kept in step by `panelsFollowUsers`. Checkpoint `by` and History keep the name from when they were made. `Actor.User` (json:"-") is the id of a user actor, for ownership checks. `panel` in `cfg.Locks` covers /panels, /panels/editor and /panels/<id> (page type `panel`).

- Roles (ADR 0010, `roles.go`): `User.Role` is `administrator`, `trusted` or `standard` (`config.Role*`; a missing role loads as `standard`). `cfg.GuestRole` (owned, `standard` or `trusted`, default `standard`) is the Role of a browser with nobody signed in; Guest Rights still bind its takes (`callerOf`). `roleMu(c)` is the one answer for a connection, read live. Under a held Lock, or for a Guest under its page's lock, it is "". While the config has no users, every browser is `administrator`. This interim rule is inferred: the setup wizard ends it for installs with a config file, and env-only mode keeps it. Otherwise it is the signed-in user's Role, else Guest role. `needRoleMu` turns that into nil, `errPageLocked` (no Role) or a `roleErr`. A `roleErr` is not `errLocked`: no PIN opens it, so replies carry `locked:false` and the page asks for no PIN. API keys never act above Trusted user (`a.trusted(id)`). The Advanced Settings PIN still loads, and `unlock` still checks it in its pool, but it opens nothing. The hello sends `pinSet:false`, so the page asks for it nowhere.
- At least one Administrator with a PIN: `update` runs `keepsAdministrator(old, new, envOnly)` under `cfgMu` for every save and import, so two concurrent saves cannot both pass. It refuses a change that leaves users but no Administrator with a PIN. It also refuses a save that removes every user, unless Sode runs without a config file. A config already without one (a file edited by hand) still saves other changes. Tests seed one with `withAdministrator` (Ada, 2468); `saveUsers` in roles_test.go keeps her row in lists that leave her out.
- No Administrator (users, none an Administrator with a PIN: `noAdministrator`): Sode starts. `needRoleMu` refuses an Administrator rule with `roleErr.noAdmin`, whose text names `recoverCommand` (roles.go). The hello's `noAdministrator` shows the `#no-admin` banner (web/noadmin.js, index.html); only a restart changes it. Keep the command in step in roles.go, index.html (banner and lock help) and docs/reference.md.
- Recovery command `-make-administrator NAME` (cmd/sode, `config.MakeAdministrator`): reads the PIN from stdin, never a flag (ps, shell history). Promotes the named user or adds one; a new name at `MaxUsers` is refused. Its tests are in internal/app/recovery_test.go for the cheap test hashes.
- Removed user's panels: `usersReq.panelOwners` maps a removed user id to a kept user id. `newPanelOwners` refuses a save that removes a panel owner without one. After the save, `panelStore.moveOwners` moves panels by their owner at that time. A removed user with no entry goes to the acting user, so a panel made meanwhile moves too. `usersListResult` carries each user's `panels` count and `me`, so Manage users offers a New owner select that defaults to the acting user (`ownerChoices` in usersrules.js). Templates and Checkpoint sets keep the removed id. A Replace import that drops users does not move panels.

A lock needs a user (Validate). Only the users message (`SaveUsers`) saves the user list, each Role, Guest role and `maxPinLen`. It needs an Administrator. Locks and auto-lock are ordinary Settings fields tagged guard:"pin", which only an Administrator changes. A config message without a `locks` or `autoLockMinutes` key keeps live values (a missing key must never read as every lock off). In Settings, each section's role tag (web/settingsrolerules.js) decides what a Role sees; see docs/agents/settings-saves.md.

- Policy table (`internal/app/policy.go`): one closed map from every client-to-server type to its need, its Role and its handler. The handler is `handle`, run with the read loop's `connCtx`. `admit` checks the page lock, then the Role, one time before the handler runs; Sode drops unlisted types. A handler chooses inline or goroutine itself (`unlock` and `userUnlock` inline). `TestPolicyCoversEveryMessage` fails on a rule without a handler or a Role, or if a switch on the type comes back. `TestPolicyMatrix` runs every rule against every connection state. A refusal logs a locked command. Its answer is `lockState` (page lock or no Role) or a failed `<op>Result` that echoes `id`. `batch` gets a failed `takeResult` per item, and `clearHistory` a failed `clearHistoryResult`, through the rule's `onRefuse`. Roles:
  - `roleAnyone`: `hi`, `userUnlock`, `userLock`, `userSignOut`, `userSetPin`, `unlock`, `lock`, `history`, `activity`, own keys, `sessionKey`, `panelAlarm`. The handler checks any sign-in it needs.
  - Standard user, with `needMain`: `batch`, `refreshNames`; with `needLog`: `sent`, `uptime`.
  - Trusted user: `config`, `filterSets`, `presets`, `profileGet`, `profileSave` (the user's own name passes, `rule.self`). `config` needs an Administrator when it carries `pin` or `clearPin` (`strict`), and `trustedMayNotChange` keeps the guarded fields (router and guard:"pin") for an Administrator.
  - Administrator: `clearHistory` (also `needMain`), `users`, `usersList`, `userSignOutAll`, `apiSettings`, `configExport`, `configImportBegin`, `configImport`, `keyListAll`, `keyCreateFor`, `keyRevokeAny`, `keyRevokeAll`. Not the main lock, so a locked wall panel signed in as an Administrator still saves.
  - `guardSave(c, role)` and `guardProfile` repeat the Role check under `cfgMu`, since a Role or sign-in can change before the save holds it.
- Locks cover actions and log reads, not data. `hello`, `names`, `tally` and `history` keep streaming to locked browsers. The main lock covers `batch`, `refreshNames` and `clearHistory`. The log lock covers the Communication Log and uptime. Pages declare their type with `hi {page, token}`; /healthz and /api/health stay open. History `Client`, `Why.By` and event `By` use `c.who()` (user name, else IP).
- Access state (`users.go`): `client.u` is a `connUser`. It holds `page` and `sess` under `mu`, and the signed-in `*config.User` in an `atomic.Pointer`. `sess` is a `*session {token, locked}` (`sessions.go`). All connections signed in with one token share it (`adoptMu` at `hi`). `eachOnSessionMu` is the one loop over them, used by `syncSessionMu` and `SignOut`. So a Lock, a resume or a sign out reaches every tab at the same time. A connection without a token has its own session. A sign-in as another user gets a fresh session. `pageAllowed` needs the lock off, or a signed-in user who still exists with the same hash. Names ending in Mu mean the caller holds mu. `syncAccess(c)` sends lock state and stops the sent feed for connections no longer allowed.
- PIN pools (`pin.go`): one method, `tryPin(pool, from, check)`.
  - `a.pin` (settings): after the 5th wrong try, waits double from 30s up to an hour. `pinMaxTries` locks for good. Success resets it.
  - `a.userPin` (`userUnlock`): the same waits, capped at 5 minutes, and no permanent lock. A right PIN does not reset the count, or a holder of one PIN could guess the rest. The entry is forgotten after an hour clean.
  - Pools never touch each other. A sign-in try carries a name: see Sign-in below.
- Persistent sessions (`tokens.go` and `sessions.go`, user flag `persistent`): `userUnlock` for a persistent user issues a token (`issueToken`, no disk I/O under `mu`). The token is 32 random bytes base64url. Sode keeps only its sha256, in memory and in `tokens.json` beside config (0600, temp file, fsync, rename). A record is {user id, pin hash, at}. `tokenStore.user` re-reads the live user on each use. So a changed PIN, a removed user, or an unticked Persistent kills the token. Each user has at most 8 tokens of each kind. A rename keeps the sessions, and `renameSignedInMu` gives open connections the new name (`TestRenameKeepsPersistentSession`). The browser keeps the token in `localStorage` `sode-session` and sends it in `hi`; the server ignores a wrong one. `userSignOut` always revokes the connection's token and signs out other connections that hold it. `userLock` only sets the token's `Locked` flag. Non-persistent users get the idle timer and PIN on reconnect. Old admin-token files load as nothing; Sode forgets a damaged file.
  - Catch-up (#159): `catchUpSessions` (end of `applyConfig` and `UserSetPin`) gives a token to every connection signed in as a persistent user without a good token. It sends it as {t:"session",token}. `issueToken` is idempotent. It drops its token if the connection signed in again, changed its Lock or got another meanwhile.
  - If a Lock is raised while Sode issues a token for a persistent user, the new token is stale. `issueToken` sees that `s.locked` changed and forgets the token. That user is then locked with no token until the next sign-in.
  - Sode uses `localStorage`, not a cookie. `hi` already carries the token over the WebSocket, so there is no HTTP endpoint, no cookie flags and no CSRF. A cookie could be HttpOnly, but the page never uses innerHTML, the token only acts as that user, and the server caps and revokes.
- Hardening: `tokenStore.prune(cfg)` deletes every record that is not valid against live config. It runs at the end of `a.update` and in `New`. So untick/retick, a user removed and added again under the same name, or a PIN changed and restored never revive a token. Tokens die after `tokenMaxAge` (90 days) without use; `hi` or an open connection (`touchSessions`, hourly) renews them. `userSignOutAll {name,id}` (Administrator) deletes a user's tokens and relocks them. `UserUnlockAs` clears the connection's token. A Settings save below Administrator must not change `router`, `trustedProxies` or `pinMaxTries` (`trustedMayNotChange`). `guardedErr` is a `roleErr` for Administrator. CSP: `secureHeaders` in `http.go` sets one policy (`script-src 'self'`, `frame-ancestors 'none'`), `nosniff` and `Referrer-Policy` `same-origin`. Pages must have no inline scripts, `on*=` handlers or `javascript:` URLs (`TestNoInlineScript`).
- lockState carries `role` (from `roleMu`) and `trusted` (that Role is Trusted user or higher). It also carries lens, and hi (only on the answer to the page's own hi; lock.js forgets its token only then). Pages read `trusted` with `user` for the signed-in user. With `pinSet` always false, pin.js needsPin() is false, and the PIN prompts below never open; they go with the Advanced Settings PIN. Some REST routes took a `pin` in the body: Everyone templates and Checkpoint sets, Icon library, Default artwork, Assign and rename. They ignore it now, and `mayEveryone` checks for a Trusted user.
- Removed: adminUnlock, admin sign-in, Forget this browser, sode-lock-never, userLock suspend, exempt, the admin chip. A wall panel signs in once as a trusted persistent user.
- No auto-lock (`User.NoAutoLock`, set by an administrator): a deliberate, narrower return of one piece of the removed exempt flag. The idle timer skips that user; the Lock button still works. It is not the removed `exempt`. It only skips `idleLock` in the page (`lockrules.js`) and the server's idle sweep (`idleLimit` in `idle.go`). The held Lock, its resume and Sign out behave as for anyone. The flag reaches only that signed-in user, in lockState, and travels in the `users` save (Administrator), so a Trusted user cannot set it. A change writes a `noAutoLockEdit` `api` row.
- Frontend:
  - `lock.js`: overlay, Ctrl+L, idle timer; emits `locking`, `unlocked`, `access`; restores focus. Other modals are closed by `lock.js` clicking their Cancel/Close.
  - `lockrules.js` (pure) and `lock.css`.
  - `users.js` (#165/#168): Settings > Users is a summary plus Manage users… (`#users-manage`). The editor is its own `pb-modal` with `trapDialog`. It has a row per user with a Role select (`ROLES` in usersrules.js), longest PIN and its own Cancel/Save. Guest role (`GUEST_ROLES`) goes only when changed. It saves with `users` and shows server errors. On a refusal it asks for the PIN in the popup and saves again. It holds no rules. Esc with edits warns one time. Locking closes it.
- Lock polish:
  - Chip (lockchip.js): Signed in as <name>, fixed top left below the lost-link banner (--sode-down-h), on phone under the header (--sode-head-h). One icon lock button (Ctrl+L). This browser has a block for the signed-in user, hidden unless someone is signed in (DICT ids `account-pin`, `account-logout`). It has Change my PIN (bus `changePin`) and Sign out (bus `logout`: ends the session, revokes the token, shows the pad).
  - Phone chip: no lock button. CSS hides the button, and hides the whole cell until a lock screen shows its closed lock (`.is-hand`). The chip is hidden when it has no name. The lock screen's brand text wraps. A phone locks by idle, the Lock in Settings, or signing out. The chip's left/top transition exists only while data-sode-lock is set, so it does not float when the lost-link banner moves it.
  - Animation: logo move through Web Animations (moveBrand, brandFrames), fresh keyframes each run. Way out lasts OUT_FACTOR (1.5) times the way in. Reduced motion = no animation, text still shows. shouldFly: logo flies only for an unscrolled page with the logo fully in view.
  - Pad feedback: a right PIN shows Welcome, <name> and signs in after `WELCOME_MS` (600). A wrong PIN shakes and shows Incorrect for `WRONG_MS` (1s). Server wait notes go under it. Text always carries status.
  - Scroll survives the Lock and its dismissal (preventScroll focus, data-sode-lock on html stops desktop.js focus-scroll).
  - Pad auto-submits only at the longest PIN length in use (sendDelay null for shorter, so 1234 never sends when 12345 exists). Check key and Enter send if some user has that length. Pad stops at min(longest, maxPinLen).
  - maxPinLen (SODE_MAX_PIN_LEN seeds, default 8, 4-12, owned, saved by users, 0 keeps). Validate rejects longer user PINs; older files get max(8, longest) in Normalize.
  - `userSetPin {old,new,id}`: the policy is open, but the connection must be signed in as a user. `old` is a try in the user pool. It needs no other Role. This connection stays signed in; the user's other connections relock and their tokens die.
  - Takes by a configured user show a small by <name> (`byLabel`, `actorUser`, `groupActor`), never an address. ext/found show none. A Group shows it only when all takes share one user.
- Tab sign-in (users, no lock): Settings > This browser shows Sign in (bus `login`). `userUnlock` carries `tab:true`. `issueToken` (`wantTab`) issues a tab-marked token for a non-persistent user, only where the page's lock is off, with the same caps and revocation. The token is valid only while the user is not persistent, for 48h (`tabTokenMaxAge`; an open tab renews it). `Hi` ignores it after the page is locked. The browser keeps it in `sessionStorage` `sode-tab-session`. The Lock has Sign in as… (signInFromLock); Cancel returns to it. The page's lock view is one value, V {mode: `page|lock|signIn`, back}, in `lock.js`, with pure transitions in `lockrules.js`. `lockState` ends the sign-in view only on a real sign-in or an enforced lock. lock.js emits lockcover {on}. html carries data-sode-lock while any overlay is up and data-sode-lock-on exactly with the overlay's is-on (drives chip geometry; 0ms under reduced motion). Chip button shows lock-open or lock (chip.setLocked); hidden under the Lock, where .sode-lock__who-ico shows a static closed lock.
- PIN popup (pinprompt.js), now never opened (see Roles above): the one prompt for an Advanced Settings PIN needed mid-session, so Settings keeps its layout. `askPin(why)` resolves true when `pin.js` `unlock` succeeds. It resolves false if cancelled, if the socket dropped or if the page is locking. It also resolves true if a hello says no PIN is set now. `reask(why)` first marks this connection's PIN lost (`pin.lostUnlock`), for a refusal. These callers use it, and each retries the action after the PIN is in:
  - Manage users (open, `usersList`/`users`/`userSignOutAll` refusals).
  - The config file (export, import begin, retry after a refusal).
  - Clear history (pre-check, and a bare `locked` while one is pending).
  - The Settings form (pin/guarded edits by a trusted user; a `configResult` refusal).
  - Profile read/save refusals.

  `pin.needsPin` is pinSet && !`unlocked` && !trusted, with no forced flag. Only a non-trusted connection's Settings flips to the inline prompt at the top of the page (`renderLock`; also on a bare `locked`). globalsave.js keeps its own in-dialog PIN row (filters, presets, review) and relocks after. Clear history reports success from the server's historyCleared (history.js emits it on the bus), not at send time.
- Lock with a user signed in (ADR 0001, server-held): `userLock` (chip button, Ctrl+L, Settings Lock; `lock.js` `lockNow()`) raises the Lock and keeps the session. With nobody signed in, userLock does nothing on the server and the letter Lock stays page state. The overlay is .sode-lock__main (brand + bodies, centred) over an in-flow foot, 100dvh tall.
  - `session.locked` is under `mu`. The flag also rides the session token (`tokenRec.Locked`, `tokens.json`). `setHeld` changes both, and the policy handler calls it directly. So `Hi` with a locked token brings the connection up locked, and every connection that shares the token locks and resumes together.
  - A resume that deletes the token (see below) parts those connections. Each gets its own tokenless session (`holdMu`), so a later Lock or sign-out of one tab leaves the others alone. `issueToken` swaps c's session for a new one instead of editing it, because `catchUpSessions` compares session pointers.
  - A non-persistent user has no token until the Lock. Then `setHeld` issues a tab token, so a reload still shows the held Lock. It uses `issueToken`, with one `tokens.issue` write that carries `Locked`. The page gets `session` with `tab:true` and keeps it in `sessionStorage`.
  - Under a PIN lock, `Hi` accepts such a token only while it is locked, and a resume deletes it. So a reload with no Lock still asks for the PIN. `heldOnly` in `tokens.go` is the one predicate for `Hi`, `issueToken` and the resume.
  - A locked connection is signed in to nothing. `userOKMu` is false, and `pageAllowedMu` refuses every gate even with the page lock off. `trusted`, profile and `lockState`'s user fields go quiet.
  - `lockState` carries `held` (no name, no flags) and `locked`. `held` comes from `heldMu`. A Lock whose user is gone or whose PIN changed ends in `endDeadHeldMu`, run by `commit` where a config change applies. `lockStateMu` only builds the message.
  - Resume is `userUnlock` (`UserUnlockAs`). While locked, Sode compares only the held user's hash. Another user's PIN is a wrong try in the user pool and never switches users. `userSignOut` (open, `App.SignOut`) ends the session: it revokes the token and signs out every connection that shares it.
  - In `lock.js`, `lockCovers(L)` in lockrules (locked && (enforced || held)) decides the pad. `raiseLock`/`signedOut` give the state immediately, and `tokenStale` keeps the stored token while held. The foot's one Sign out button shows for held and does `signOutNow()`.
  - A `userLock` that wsSend refused is kept in owed.js and sent again when lockState shows the session signed in with no Lock. `userSignOut` is not kept. `signOutNow` clears the stored tokens first, so the next hello is signed out anyway. The server token lives on until it expires.
  - A held Lock can end with no user (`heldEnded`: signed out here or elsewhere, removed user, changed PIN). If no PIN lock applies, it then drops to the letter Lock, so the page never uncovers by itself. A held Lock that ends with a user was resumed.
  - The held pad names whose Lock it is from this tab's own memory (`heldWho`), and the chip shows it (`chipShown` with `heldUser`). The name is in `sessionStorage` `sode-held-user`. `lockNow` sets it, and so does a held `lockState` that arrives while a user was signed in. The server's held state stays nameless.
  - A successful sign-in by name stores it in `localStorage` `sode-last-user`, so the browser remembers the last name. The box is prefilled with it while the hello still lists that name (`prefillName`), and the pad then has the keys. A sign out keeps it.
- Lock with nobody signed in (#158): this applies where no PIN lock applies and nobody is signed in. Ctrl+L or Settings > This browser > Lock screen (bus `localLock`) shows the overlay with `letterBody` (`MODE.LOCK`). It has the churning letter (`churnKey`, shared with `keyconfirm.js`), a button for touch screens, and Sign in as… / Sign out. Honors confirm lockout and confirmEnter. Purely page state, no server message, reload clears it. While up, the capture keydown handler stops every key reaching the page (browser chords pass, so Ctrl+Z cannot undo a take underneath). Idle timer raises it after autoLockMinutes (localIdleLock). An enforced lock cancels it. A guard against mashing, not security.
- Auto-lock has two timers. The page's (lock.js, idleLock in lockrules.js) is the fast path and sends the same `userLock` as the Lock button. Every signed-in user gets it, persistent users and tab sign-ins included, and it never signs anyone out. Idle is per browser. `lock.js` shares activity between tabs on a BroadcastChannel (`idleshare.js`), so a background tab does not lock a session that the user is active in. With nobody signed in it raises the letter Lock (localIdleLock); guests and nobody-signed-in stay browser-only.
  - Server idle clock (#221, idle.go): the clock belongs to the session, not the page, so main, log and panel connections (any `acts`) are all covered. A tokenless session keeps it in `session.seen`; a token keeps it in `tokenStore.seen` (memory only, keyed like the records), so it runs with zero connections. A zero or missing time is stamped when first looked at, so a restart starts every clock at load. idleSweep runs from periodic every `App.idleEvery` (10 s) on `App.now`; tests swap both. It locks an open session with `holdMu` (the same `lockState` push as `userLock`). It locks an unconnected token with `tokenStore.lockIdle`, under `App.mu`, so a `Hi` that races sees the flag. Hi also checks overdueMu after adopting a token, so a browser back before the next sweep meets the Lock. idleLimit reads `autoLockMinutes` live (0 = off) and skips No auto-lock users.
  - Activity: the page sends `activity` (open, never logged) at most every 30 s while `lastActive` has moved (`pingDue`, `lockrules.js`), from every tab on the BroadcastChannel. The server stamps the session and its token only for a signed-in connection not under the Lock. Signing in and a resume (holdMu with on false) also stamp it, or the next sweep would lock again. Hi does not refresh it, but a Hi that reaches overdueMu seeds a zero clock with now (idle.go), the same as the sweep does.
  - Known limit: a Session-mode panel's session key (`tokens.live`) still works under any Lock, manual or idle. `sessionKey` refuses a new one and the page drops its key on the Lock (sessionkey.js). A resume keeps the key, except under the panel page lock, where the resume drops the tab token and so ends it. `TestIdleLockCoversAPanelPageSessionKeyStillAnswers` pins this.
  - lock_idle_test.go drives both timers.
- Public panel (docs/panels-design.md, docs/agents/panels.md): the one page where the panel page lock shows no PIN pad. After panelrun.js sends `publicPanel`, lock.js reads `lockState` through `pinFreeView` (lockrules.js). So the page sees no enforced lock and the idle timer raises the letter Lock. The server's lockState is unchanged (locked, no names): nothing reaches the page before a PIN that it did not get before. A held Lock still covers it with the pad.
- Sign-in (#560): one sign-in everywhere (Main page, Settings, /log, panel pages), always name then PIN. There is no sign-in mode and no PIN only sign-in. PINs need not be unique (SaveUsers, UserSetPin and MakeAdministrator check no clash).
  - The hello's `users` is [{name, len}] for every user, `len` 0 for no PIN (#561 adds those users). It reaches locked pages, so it holds nothing else: `hello()` blanks `cfg.users` and builds `helloUser` rows. `TestUsernamesStayOutOfPublicMessages` pins the keys. A users save goes through applyConfig, which sends every page a new hello. core.js keeps it in `S.users` and `S.userNames`.
  - Server: `userUnlock {user, pin, id, tab}` finds the user by `user` (`FindUserByName`) and compares the PIN with that user's hash only (`matchPin`, a pure function of the config). An empty or unknown name burns a check, so it costs what a right one does. A wrong-length PIN for a known name is hashed too. Unknown name, wrong PIN and another user's PIN are the same wrong try in the user pool. A held Lock resumes with the holder's PIN; `user` can be empty, and a `user` that names someone else is a wrong try. The test-only `UserUnlock(c, pin)` looks up the one user with that PIN and names them.
  - Pad (lock.js, pure lockrules.js): `asksName` is true except under a held Lock. The name box is `namePicker` (namepick.js, pure namepickrules.js): fuzzy find with `fuzzyScore`, and an empty box lists every user in the hello's order. Focus opens the list; arrows move, Enter picks the highlighted name (else the best match), Escape closes an open list, a click picks. lock.js's capture handler hands the box's keydowns to `picker.key` first. The list is `.sode-namepick__list` (a little `SCROLLERS` entry). Only a listed name (`listedUser`, case ignored) sends. `padLens` uses the picked user's own length, so the pad sends at that length at once; with no listed user it falls back to `lockState.lens`. Under a held Lock the holder (`heldUser`) gives the length. `canSend` and `padDelay` hold the send until a name is listed, so a PIN typed first goes out when the name is picked. `signInMsg` adds `user` except under a held Lock.

- API keys, rights and the users save (#243, `keyserve.go`, ADR 0003):
  - `keyCreate` is open and needs a sign-in. The user's own PIN is a try in the user pool, as for `userSetPin`. The reply `keyCreateResult` carries the key one time.
  - `keyRevoke` and `keyListOwn` are open, need a sign-in, and act on own keys only.
  - `keyListAll`, `keyCreateFor`, `keyRevokeAny` and `keyRevokeAll` need an Administrator.
  - Caps come from `API.MaxUserKeys` and `MaxClientKeys`; expiry is unix ms in the request, 0 = never.
  - `a.update` runs `pruneKeys` on every config change. A user's keys end on PIN change or removal; a rename keeps them. A client's keys end on removal or rename; client keys ignore user PINs.
  - `New` runs `keyStore.reconcile`. It drops keys with no owner. It also drops a user's keys whose PIN hash no longer matches `pinFp`. `pinFp` is a one-way stamp of the owner's PIN hash that keys.json records at creation (never the PIN or hash). So a PIN edited in config.yaml while down still ends them.
  - A key from an older keys.json has no `pinFp`. Sode keeps it and stamps it at that first startup; Sode cannot tell a PIN edited while down before this version ran. Each ending writes a `keyEnded` row.
  - `configImport` writes the same `api` rows as the saves it replaces (`auditRights`, `auditAPISettings`, `auditRequireHTTPS`). It refuses to turn on Require HTTPS from an insecure request.
  - `expireKeys` runs from `periodic`.
  - The `users` save carries `rights` and `noAutoLock` per userEdit and `apiClients`, `guestRights`, `guestScopes` on usersReq; a nil field keeps the live value. usersReq's `guestRole` and each userEdit's `role` ride it too. usersListResult (Administrator) returns them all, with `guestRole`.
  - Rights store sources and destinations as `config.Ref` and presets as preset ids. The wire carries the references; `Ref` also decodes a bare number. `update` (settings.go) calls `nameRights` before Normalize: a reference with no name gets the router's name, else the name any Rights stored for that number before. Normalize fills a blank router. Matching (`Allows*`, `Within`) uses the number only, never the name. A take carries `presetId` beside `preset`; `outsideRights` checks the id. The Rights editors (`rightsrules.js`) show Everyone preset names and send ids. They refuse a name with no preset and keep an id they cannot name.
  - Rights and key lists never ride the hello or lockState; lockState carries only the signed-in user's own `noAutoLock`.
  - Audit rows (kind `api`): keyCreate, keyRevoke, keyEnded, keyExpired, rightsEdit, noAutoLockEdit, clientEdit. A client has no stable id, so a rename of one ends its keys.
- Session key (#265, `sessionkey.go`, `web/sessionkey.js`): `sessionKey` answers `sessionKeyResult` like `keyCreateResult`. It is open, and needs a connection that is signed in and not under the Lock. It needs no PIN recheck: the signed-in connection is the proof. The key is an ordinary user key plus `sess` in keys.json, which is the sha256 of the session token. `apiAuth` also needs that token live for the same user (`tokenStore.live`). A connection with no token gets a tab token first, even a held-only user (`issueTokenFor` forKey), which `Hi` still refuses after the Lock ends. A session holds up to 16 keys, one per tab (`sessionKeyMax`); past that, the oldest ends. Session keys have the shape `sode_ses.` plus 43 characters. So a session key that Sode no longer holds reads as ended (`key_revoked`), not counted toward the failed-key throttle (docs/agents/panels.md, Ended keys). `endSessionKeys` drops keys whose token is gone. It runs from `SignOut`, `SignOutAll`, a Lock resume that drops the token, `pruneKeys` (every config commit, so a PIN change) and `expireKeys` (so token expiry). The page holds the key in memory only. `sessionFetch` adds the Bearer header. It asks one more time after `key_revoked`, `key_expired` or `invalid_key`, then stops for good if the server refuses the fresh key too. sessionStep (sessionkeyrules.js) raises the PIN pad through the `login` event when signed out and no page lock draws one.
- Rights in the page (#249): a signed-in connection gets its own user's rights in a separate `myRights` message. `pushRightsMu` sends it, from `pushAccessMu`, so every sign-in, lock change and config save refreshes it. It is cleared when the Lock covers the page or the user signs out. Never in the hello or lockState. The page (`plans.js`, `S.myRights`) greys out source and destination rows. It blocks a plan in `planBlocked` with the server's own words; the server stays the authority. `noAutoLock` from lockState is the skip in `idleLock` (lockrules.js). The old per-user `exempt` auto-lock exemption stays removed; No auto-lock is a narrower return of one piece of it, set per user by an administrator.
- Manage users is one dialog with Users, API clients and Rights tabs (users.js, usersclients.js, usersrights.js, tabs.js; pure rules in rightsrules.js, apirules.js, keyrules.js). One Save sends the `users` message. It carries per-row `rights` and `noAutoLock` only for rows that loaded them. `accessReq` sends untouched rights back as loaded, so a save never rewrites them through the editor's text. It carries `apiClients`, `guestRights` and `guestScopes` only after the directory loaded. A user's own keys are in My API keys (mykeys.js). The one-time key and its QR code (qr.js, hand-written, level M, versions 1-6) live only in the open dialog.
