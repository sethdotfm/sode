# Settings, the Advanced Settings PIN, shared saves

- Advanced Settings PIN: PBKDF2 hash in settingsPin (json:"-", never sent to browsers, SaveSettings carries it over). Access is per connection and per hash, and ends when Settings closes or the PIN changes. The PIN-entry message is handled inline in the read loop so a following lock wins. Wrong PINs counted globally, one check at a time, waits double from 30s after the 5th. pinMaxTries (default 10, 0 = never) locks until -reset-pin or restart. A non-hash settingsPin stops startup. SaveSettings is serialized by cfgMu and re-checks the lock.
- Device defaults (#49): deviceDefaults (theme, layout, clock, flip, scrollTop, searchFilters, setStack, stackGap, nextMode, compact) is what This browser uses until a browser picks its own. Not router-side, no reconnect. Browser values are localStorage strings (sode-theme, sode-layout, sode-clock, sode-flip, sode-scroll-top, sode-search-filters, sode-set-stack, sode-stack-gap, sode-next-mode, sode-compact); missing or unknown means Global. resolve() in web/prefs.js (pure) picks own, then global, then built-in. device.js pref/setPref ('' removes) are the only readers and writers. Global defaults are cached in localStorage sode-device-defaults on every hello for web/prepaint.js (sync in each head; other pages pass data-only="theme"). prepaint.js repeats resolve() inline. web/test/prepaint.test.mjs runs it against resolve() and fails on any disagreement. The This browser section and its my-default buttons live in web/devicesettings.js.
- Settings search: settingsindex.js (pure, own scorer) indexes fieldsets and labels (label[for], .sode__field-label[id], .pb-check, [data-find][data-label] for buttons etc). DICT maps section slugs (each fieldset's data-section) and control ids to search words. A new settings section must add its slug to DICT or settingsindex.test.mjs fails; add terms for new settings too. Each result names its topic (and router) through hitWhere; a topic's name finds its sections. Esc in the box clears it, the next Esc leaves Settings. Its input events must not reach the form.


- Filter sets and presets save through saveShared and replyOp(c, kind, id, n, noun, err). saveShared (app/shared.go) holds cfgMu, and guardSave(c,true) re-checks PIN or trusted user. update mutates a copy, then Normalize, Validate, save and an optional small broadcast run. replyOp logs the command, answers <kind>Result that echoes id, and sets locked. New saved-apart features use both. Name rules: validateNames in config/names.go (count, empty, 32 runes, unique ignoring case).
- Owned fields: Config fields saved outside the Settings form carry owned:"true" (filterSets, presets, settingsPin, deviceDefaults, users, maxPinLen, signInMode). saveSettings does cur.KeepOwned(live) so a stale browser copy cannot change them. Form-saved fields carry guard:"router|pin|open": router reconnects (config.Changed(old,c,"router")), pin means only the Advanced Settings PIN is allowed to change it. TestEveryFieldChooses fails if a new Config field has neither tag. The embedded `config.Router` counts as Config's own fields (configFields in owned.go): its UID and prefix are owned, the rest guarded. Its JSON keys stay flat in the Settings message (`router` is the address, `routerName` the title); only `config.yaml` nests them under `routers` (MarshalYAML in config/router.go). Load writes back a router UID it had to make. The Settings dialog strips owned lists from its config message (OWNED_KEYS in owned.js; socket limit wsReadLimit 64 KiB).
- Unknown keys: every config struct keeps keys that this release does not know in Extra (json:"-"). So form saves, saveShared, the users editor (carries each user's Extra over) and imports keep them. Config.UnknownKeys lists them, with profile prefs that this release does not know (users[i].profile.prefs.<key>). Profile.Normalized drops those from what the browser gets; normalizeProfiles and the profile save keep them (config.WithUnknownPrefs). An import without a top-level router key is refused as not a Sode configuration. A profile export shares filterSets and presets with Config, so only router tells them apart. Otherwise, configImportResult names the unknown keys in `kept` (config.NameKeys, at most 10). Saves that replace a list from browser JSON are SaveFilterSets, SavePresets, the profile save, and the users editor's rights, API clients and Guest rights. They get each item's Extra from the saved item of the same name (config.WithFilterSetExtras and its siblings in keepextra.go). So a browser can neither drop nor add unknown keys. Preset items match on source and destinations; a renamed, edited or new item starts with none. Known limit: a new value of a known key still fails Validate or the decode and stops startup. Examples are an API scope, a deviceDefaults theme and a changed type. A feature PR that adds a pref, scope or enum value must say in its description what a rollback does.
- Settings modules:
  - settings.js: open, close, Clear History and the wiring.
  - settingsform.js: fills, reads and checks the form fields.
  - settingssave.js: the unsaved check, Save and configResult.
  - settingslock.js: the PIN prompt of Settings. settingsfind.js: search. settingstoc.js: the sidebar tree, built by settingstree.js (pure). settingsrouters.js: the Routers list and the sub-heading of each router block.
- Topics: Settings is one page in five topics (Preferences, Look and feel, Routers, Access, Server). Each section is a fieldset in web/index.html with data-section (its slug) and data-topic. The band of a topic is an h3.sode__topic before its sections. Fieldsets stay direct children of the form, because the lock and phone CSS select them with `>`. Per-router sections (Router & matrix, Router names, Takes) also carry data-router and come after the h4.sode__router sub-heading of that router. The sidebar and search read them at load. settingshtml.test.mjs checks topics and order, and fails if a module adds a section. TestEverySettingsSectionSaves saves the form fields of each section; a new section with none must be in its list of sections saved apart.
- Inputs saved apart from the Settings form carry data-apart so the unsaved check skips them. emit('settingsClose',{discard:true}) closes Settings discarding the form.
