# Settings, the Advanced Settings PIN, shared saves

- Advanced Settings PIN: PBKDF2 hash in settingsPin (json:"-", never sent to browsers, SaveSettings carries it over). Access is per connection and per hash, and ends when Settings closes or the PIN changes. The PIN-entry message is handled inline in the read loop so a following lock wins. Wrong PINs counted globally, one check at a time, waits double from 30s after the 5th, never a permanent lock. A non-hash settingsPin stops startup. SaveSettings is serialized by cfgMu and re-checks the lock.
- Device defaults (#49): browserDefaults (theme, layout, clock, flip, scrollTop, searchFilters, setStack, stackGap, nextMode, compact) is what This browser uses until a browser picks its own. Not router-side, no reconnect. Browser values are localStorage strings (sode-theme, sode-layout, sode-clock, sode-flip, sode-scroll-top, sode-search-filters, sode-set-stack, sode-stack-gap, sode-next-mode, sode-compact); missing or unknown means Global. resolve() in web/prefs.js (pure) picks own, then global, then built-in. device.js pref/setPref ('' removes) are the only readers and writers. Global defaults are cached in localStorage sode-browser-defaults on every hello for web/prepaint.js (sync in each head; other pages pass data-only="theme"). prepaint.js repeats resolve() inline. web/test/prepaint.test.mjs runs it against resolve() and fails on any disagreement. The This browser section and its my-default buttons live in web/devicesettings.js.
- Settings search: settingsindex.js (pure, own scorer) indexes fieldsets and labels (label[for], .sode__field-label[id], .pb-check, [data-find][data-label] for buttons etc). DICT maps section slugs (each fieldset's data-section) and control ids to search words. A new settings section must add its slug to DICT or settingsindex.test.mjs fails; add terms for new settings too. Each result names its topic (and router) through hitWhere; a topic's name finds its sections. Esc in the box clears it, the next Esc leaves Settings. Its input events must not reach the form.


- Filter sets and presets save through saveShared and replyOp(c, kind, id, n, noun, err). saveShared (app/shared.go) holds cfgMu, and guardSave(c,true) re-checks the user's Role (Trusted user or higher). update mutates a copy, then Normalize, Validate, save and an optional small broadcast run. replyOp logs the command, answers <kind>Result that echoes id, and sets locked. New saved-apart features use both. Name rules: validateNames in config/names.go (count, empty, 32 runes, unique ignoring case).
- Owned fields: Config fields saved outside the Settings form carry owned:"true" (filterSets, presets, settingsPin, browserDefaults, users, maxPinLen). saveSettings does cur.KeepOwned(live) so a stale browser copy cannot change them. Form-saved fields carry guard:"router|pin|open": router reconnects (config.Changed(old,c,"router")), pin means only the Advanced Settings PIN is allowed to change it. TestEveryFieldChooses fails if a new Config field has neither tag. The embedded `config.Router` counts as Config's own fields (configFields in owned.go): its UID and prefix are owned, the rest guarded. Its JSON keys stay flat in the Settings message (`router` is the address, `routerName` the title); only `config.yaml` nests them under `routers` (MarshalYAML in config/router.go). Load writes back a router UID it had to make. The Settings page sends only one Save fields, so owned lists never ride it (socket limit wsReadLimit 64 KiB).
- Unknown keys: every config struct keeps keys that this release does not know in Extra (json:"-"). So form saves, saveShared, and the users editor (carries each user's Extra over) keep them. Config.UnknownKeys lists them, with profile prefs that this release does not know (users[i].profile.prefs.<key>). Profile.Normalized drops those from what the browser gets; normalizeProfiles and the profile save keep them (config.WithUnknownPrefs). The export file drops and lists them (docs/agents/profiles.md). Saves that replace a list from browser JSON are SaveFilterSets, SavePresets, the profile save, and the users editor's rights, API clients and Guest rights. They get each item's Extra from the saved item of the same name (config.WithFilterSetExtras and its siblings in keepextra.go). So a browser can neither drop nor add unknown keys. A preset matches on its hidden id (a preset sent without one takes the saved id of its name). Preset items match on source and destination numbers; an edited or new item starts with none. Known limit: a new value of a known key still fails Validate or the decode and stops startup. Examples are an API scope, a browserDefaults theme and a changed type. A feature PR that adds a pref, scope or enum value must say in its description what a rollback does.
- Settings modules:
  - settings.js: open, close, Clear History and the wiring.
  - settingsform.js: fills, reads and checks the form fields.
  - settingssave.js: the unsaved check, the exit warning, the one Save and its answers, the marks on refused fields.
  - savereview.js: the review dialog. savereviewrules.js (pure): `SAVE_FIELDS`, the was/now diff, its grouping, the Save button text and the refusal notes.
  - settingslock.js: the PIN prompt of Settings. settingsfind.js: search. settingstoc.js: the sidebar tree, built by settingstree.js (pure). settingsrouters.js: the Routers list and the sub-heading of each router block.
- Topics: Settings is one page in five topics (Preferences, Look and feel, Routers, Access, Server). Each section is a fieldset in web/index.html with data-section (its slug) and data-topic. The band of a topic is an h3.sode__topic before its sections. Fieldsets stay direct children of the form, because the lock and phone CSS select them with `>`. Per-router sections (Router & matrix, Router names, Takes) also carry data-router and come after the h4.sode__router sub-heading of that router. The sidebar and search read them at load. settingshtml.test.mjs checks topics and order, and fails if a module adds a section. TestEverySettingsSectionSaves saves the form fields of each section; a new section with none must be in its list of sections saved apart.
- Role tags: `SECTION_ROLES` in settingsrolerules.js (pure) gives each section slug who edits it (Anyone, Trusted, Administrator) and whether lower roles see it (Shown or Hidden). `sectionView(slug, role, phone)` answers edit, read or hidden; `''` (a held Lock) and unknown roles rank as a Standard user. The phone keeps only Anyone's sections (Preferences). settingsroles.js applies it on open, on `access` (lockState's `role`) and on a layout change. A read section is a disabled fieldset with a View only note. A data-apart one stays enabled, since its buttons only jump. A hidden section has `hidden`. A band or router sub-heading goes with its last shown section. The sidebar (`toc.setOff`), Ctrl+J/K and search skip hidden sections. A new section needs a tag, or settingsroles.test.mjs fails. The tags only shape the page: the server decides every save.
- The one Save, server side (`internal/app/onesave.go`): `settingsSave {id, fields: {<key>: {value, version}}}` answers `settingsSaveResult {id, ok, err, results: {<key>: {status, reason, err, value, version}}}`. A key is a Config JSON key in `saveFields`, which gives its section. `sectionRoles` is the Go copy of `SECTION_ROLES` (TestSectionRolesMatchPage). Every guard-tagged field needs a section (TestEveryGuardedFieldHasSection). The hello carries `versions`, a hash of each field's live value, so any writer (import, API, file) moves it. Under `cfgMu`, each field is checked alone against live, in this order:
  1. Section above the Role: `needs Approval` when Shown, `Role` when Hidden or for an unknown key.
  2. Value equal to live: `unchanged`, not written.
  3. Stale version: `conflict`, with the live value and version.
  4. Validate fails: `invalid`.
  5. `criticalEdits` without a recheck: `needs PIN recheck`.
  6. Require HTTPS from a connection that is not secure: `missing prerequisite`. The fields that pass go in one `applyConfig`; when none pass, nothing is written. The policy rule needs a Standard user, so each field gets its own refusal.
- The one Save, page side (`settingssave.js`, `savereview.js`): the baseline is `readSettings()` right after the form fills, with the hello's `versions` copied at that moment. A later hello does not move them, so another person's save shows as a conflict. A change is a `diffRows` row against that baseline; an object field (`locks`, `browserDefaults`) gives a row per key and `levelColors` a row per level. `SAVE_FIELDS` in savereviewrules.js is the page copy of `saveFields` (TestSaveFieldsMatchPage, which also checks the reconnect list against the guard:"router" tags). The steps are the review (was/now table by topic and section), the PIN recheck, and Save and reconnect. Nothing is sent before the last step. The recheck shows when a row is Critical and users exist. Save and reconnect shows when a row is a router connection field. Back from Save and reconnect goes to the review. A row in a section the Role cannot edit is counted as kept ("Save 2, keep 2 unsaved") but still sent, so the server gives its reason. Saved and unchanged fields move the baseline and version. A refused field keeps its own and gets a `.sode__refused` note (`data-refused` is the key). The note stays until the field saves or goes back to the baseline. A conflict takes the returned version, so the next Save overwrites the other person's value on purpose. A refusal for the PIN recheck asks one recheck and sends those fields again. The exit warning names each section with changes. The Advanced Settings PIN fields still go on a `config` message with an empty config after the fields, until that PIN goes.
- The `config` message keeps the same section rule: `trustedMayNotChange` refuses a Trusted user's change to a field of an Administrator section (`guardedErr`).
- Inputs saved apart from the Settings form carry data-apart so the unsaved check skips them. emit('settingsClose',{discard:true}) closes Settings discarding the form.
