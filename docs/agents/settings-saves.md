# Settings and shared saves

- Roles decide every save (ADR 0010, docs/agents/users-locks.md). v2 has no settings secret: Load drops its v1 key (`retiredKeys` in config/config.go), so no later write carries it. saveSettings is serialized by cfgMu and checks the Role again.
- Device defaults (#49): browserDefaults (theme, layout, clock, flip, scrollTop, searchFilters, setStack, stackGap, nextMode, compact) is what This browser uses until a browser picks its own. Not router-side, no reconnect. Browser values are localStorage strings (sode-theme, sode-layout, sode-clock, sode-flip, sode-scroll-top, sode-search-filters, sode-set-stack, sode-stack-gap, sode-next-mode, sode-compact); missing or unknown means Global. resolve() in web/prefs.js (pure) picks own, then global, then built-in. device.js pref/setPref ('' removes) are the only readers and writers. Global defaults are cached in localStorage sode-browser-defaults on every hello for web/prepaint.js (sync in each head; other pages pass data-only="theme"). prepaint.js repeats resolve() inline. web/test/prepaint.test.mjs runs it against resolve() and fails on any disagreement. The This browser section and its my-default buttons live in web/devicesettings.js.
- Settings search: settingsindex.js (pure, own scorer) indexes fieldsets and labels (label[for], .sode__field-label[id], .pb-check, [data-find][data-label] for buttons etc). DICT maps section slugs (each fieldset's data-section) and control ids to search words. A new settings section must add its slug to DICT or settingsindex.test.mjs fails; add terms for new settings too. Each result names its topic (and router) through hitWhere; a topic's name finds its sections. Esc in the box clears it, the next Esc leaves Settings. Its input events must not reach the form.


- Filter sets and presets are edited outside Settings. They save through saveList and replyOp(c, kind, id, n, noun, err). saveList (app/shared.go) holds cfgMu, and guardSave(c, Trusted) checks the user's Role again. It commits and broadcasts one small message. replyOp logs the command, answers <kind>Result that echoes id. Name rules: validateNames in config/names.go (count, empty, 32 runes, unique ignoring case).
- The stale-copy guard is the one Save's field versions: a page sends only the fields it changed, each with the version it loaded. Nothing is "owned" any more. The `config` message takes only the form's fields (`configKeys`: rows of `settingFields` without `source`), so it cannot write users, lists or API settings. No page sends it since the one Save took the form; server tests still save through it. A field tagged reconnect:"true" reconnects the router when it changes (config.ReconnectChanged). Who edits a field is its section's role tag, not a field tag. The embedded `config.Router` counts as Config's own fields (configFields in config/changed.go). Its JSON keys stay flat in the Settings message (`router` is the address, `routerName` the title); only `config.yaml` nests them under `routers` (MarshalYAML in config/router.go). Load writes back a router UID it had to make. A save message stays under the socket limit (wsReadLimit 64 KiB), since only changed fields go.
- Unknown keys: every config struct keeps keys that this release does not know in Extra (json:"-"). So form saves, saveList, and the one Save's user and API client keys (each edits one attribute in place) keep them. Config.UnknownKeys lists them, with profile prefs that this release does not know (users[i].profile.prefs.<key>). Profile.Normalized drops those from what the browser gets; normalizeProfiles and the profile save keep them (config.WithUnknownPrefs). The export file drops and lists them (docs/agents/profiles.md). Some saves replace a list or Rights from browser JSON. They are SaveFilterSets, SavePresets, the profile save, and the Rights keys of the one Save. They get each item's Extra from the saved item that matches it (config.WithFilterSetExtras and its siblings in keepextra.go). So a browser can neither drop nor add unknown keys. A preset and a filter set match on their hidden id (one sent without an id takes the saved id of its name). Other items match on the name. Preset items match on source and destination numbers; an edited or new item starts with none. Known limit: a new value of a known key still fails Validate or the decode and stops startup. Examples are an API scope, a browserDefaults theme and a changed type. A feature PR that adds a pref, scope or enum value must say in its description what a rollback does.
- Settings modules:
  - settings.js: open, close, Clear History and the wiring.
  - settingsform.js: fills, reads and checks the form fields.
  - settingssave.js: the unsaved check, the exit warning, the one Save and its answers, the marks on refused fields.
  - savereview.js: the review dialog. savereviewrules.js (pure): `SAVE_FIELDS`, `ITEM_SECTIONS`, the was/now diff, its grouping, the Save button text and the refusal notes.
  - interruptions.js asks `settingsReview` for the Interruptions; interruptionrules.js (pure) gives the Save button's words and the "do not come back" line.
  - Backup offer: backuprules.js (pure) `offersBackup` shows it when a row that saves is Critical or the Interruptions are not empty or unknown. A row that an Approval saves counts. Only an Administrator gets the offer, since `exportSession` refuses other Roles. Download a backup calls exportcalls.js `downloadBackup`, the same call as Back up everything. The Export & Import button ends the review (edits stay staged) and opens the dialog. "Last backup" reads `localStorage` `sode-last-backup` (ISO time), written when either button downloads.
  - savesources.js: the save sources. The form is one (`formSource` in settingssave.js); usersstage.js (Manage users, with pure usersstagerules.js) and apisettings.js (the API section) register one each.
  - settingsfind.js: search. settingstoc.js: the sidebar tree, built by settingstree.js (pure). settingsrouters.js: the Routers list and the sub-heading of each router block.
- Topics: Settings is one page in five topics (Preferences, Look and feel, Routers, Access, Server). Each section is a fieldset in web/index.html with data-section (its slug) and data-topic. The band of a topic is an h3.sode__topic before its sections. Fieldsets stay direct children of the form, because the phone CSS selects them with `>`. Per-router sections (Router & matrix, Router names, Takes) also carry data-router and come after the h4.sode__router sub-heading of that router. The sidebar and search read them at load. settingshtml.test.mjs checks topics and order, and fails if a module adds a section. TestEverySettingsSectionSaves saves the form fields of each section; a new section with none must be in its list of sections saved apart.
- Role tags: `SECTION_ROLES` in settingsrolerules.js (pure) gives each section slug who edits it (Anyone, Trusted, Administrator) and whether lower roles see it (Shown or Hidden). `sectionView(slug, role, phone)` answers edit, read or hidden; `''` (a held Lock) and unknown roles rank as a Standard user. The phone keeps only Anyone's sections (Preferences). settingsroles.js applies it on open, on `access` (lockState's `role`) and on a layout change. A read section stays editable, with a note that its changes need Approval. The one Save sends them and asks for the Approval on the refusal (docs/agents/users-locks.md). A hidden section has `hidden`. A band or router sub-heading goes with its last shown section. The sidebar (`toc.setOff`), Ctrl+J/K and search skip hidden sections. A new section needs a tag, or settingsroles.test.mjs fails. The tags only shape the page: the server decides every save.
- The one Save, server side (`internal/app/onesave.go`, keys in `onesavefields.go`): `settingsSave {id, fields: {<key>: {value, version}}}` answers `settingsSaveResult {id, ok, err, results: {<key>: {status, reason, err, value, version}}}`. A key is a Config key in `settingFields` (internal/app/settingsfields.go), or an item key. Its row gives the section, the record label and the export group. It also says when only Manage users or the API section writes the key. `saveFields`, `fieldLabels`, `exportSections` and `configKeys` come from it. `guestRole`, `guestRights` and `guestApiScopes` are json:"-", so `hiddenFields` reads and writes them. Item keys are one per attribute: `user/<id>/{name,role,pin,rights,persistent,noAutoLock,remove}`, `user/new:<n>/add`, `client/<name>/{scopes,rights,remove}` and `client/<name>/add`. So two people who change different attributes of one user do not conflict. A PIN key's value is the new PIN, or "" to remove it; its conflict sends no value. A remove key's value can name the new owner of the user's panels (`{"owner": id}`); a user who owns panels needs one the save keeps. An add key has no version and its result `value` is `{id, versions}` of the new item. The versions of users, API clients and the json:"-" fields ride `usersListResult` (Administrator only), never the hello. A field that fails Validate alone is tried again with the other fields of its item, then with every field of the save. So a Role with a new PIN saves together, and so does a rename with a new user of the old name. After the commit come the panel moves, `panelsFollowUsers` and the `api` audit rows. `sectionRoles` is the Go copy of `SECTION_ROLES` (TestSectionRolesMatchPage). Every Config JSON key is in `settingFields` or saved apart (TestEveryFormFieldHasSection). To add a plain setting, add a Config field with its `Defaults` value and `Validate` rule. Then add one `settingFields` row and one form row with `data-key` in web/index.html. Last, add one `SAVE_FIELDS` entry in web/savereviewrules.js and one line in docs/reference.md. The hello carries `versions`, a hash of each field's live value, so any writer (import, API, file) moves it. Under `cfgMu`, each field is checked alone against live, in this order:
  1. Section above the Role: `needs Approval` when Shown, `Role` when Hidden or for an unknown key. Then a value the field cannot take: `invalid`. The PIN field refuses the saver's own PIN (`user/<own id>/pin`, a user who has a PIN; during a step-in, the stepped-in user) with `own PIN` (`saveCtx.self`). Only `userSetPin` changes your own PIN, since it asks for the current PIN.
  2. Value equal to live: `unchanged`, not written.
  3. Stale version: `conflict`, with the live value and version.
  4. Validate fails: `invalid`.
  5. `criticalEdits` without a recheck: `needs PIN recheck`.
  6. Require HTTPS from a connection that is not secure: `missing prerequisite`. The fields that pass go in one `applyConfig`; when none pass, nothing is written. The policy rule needs a Standard user, so each field gets its own refusal.
- The one Save, page side (`settingssave.js`, `savereview.js`): the baseline is `readSettings()` right after the form fills, with the hello's `versions` copied at that moment. A later hello does not move them, so another person's save shows as a conflict. A change is a `diffRows` row against that baseline; an object field (`locks`, `browserDefaults`) gives a row per key and `levelColors` a row per level. `SAVE_FIELDS` in savereviewrules.js is the page copy of `saveFields` (TestSaveFieldsMatchPage, which also checks the reconnect list against the reconnect tags). The steps are the review (was/now table by topic and section), the PIN recheck, and Save and reconnect. Nothing is sent before the last step. The recheck shows when a row is Critical and users exist. Save and reconnect shows when a row is a router connection field. Back from Save and reconnect goes to the review. A row in a section the Role cannot edit is counted as kept ("Save 2, keep 2 unsaved") but still sent, so the server gives its reason. Saved and unchanged fields move the baseline and version. A refused field keeps its own and gets a `.sode__refused` note (`data-refused` is the key). The note stays until the field saves or goes back to the baseline. A conflict takes the returned version, so the next Save overwrites the other person's value on purpose. A refusal for the PIN recheck asks one recheck and sends those fields again. The exit warning names each section with changes. Authors (stagedrules.js, pure): `noteEdits` runs on each form `input`, `change` and `saveSourceChanged`, never on `access`. So an edit keeps its author (the user name, else Guest) across Step in and Step out. The review adds a Staged by column when a row is not the saver's own. A row in a section that the saver's Role hides (`sectionView` without the phone) stays a change. It is not in the table or the sent keys. The review and the exit warning show it only as a count per author ("3 changes by Bo that your Role cannot see").
- Interruptions (`interruptions.go`, GLOSSARY.md): the page sends `settingsReview {id, fields}` with the fields it would save, before the review opens. `planSave` runs every check of a save but writes nothing and refuses nothing for a PIN recheck, which comes after the review. `interruptions(live, next)` reads the kept fields only, so a Role never sees lines for fields it cannot save. The one Save finds the list again from its kept fields before `applyConfig`. It sends the list in `settingsSaveResult.interruptions` and puts the texts in the Settings saves row. Each line has `text`, counts (`panels`, `streams`, `sessions`, `keys`, `browsers`, `stepIns`) and `ends`. The Save button names the counts ("Save and stop 3 panels"). When a line has `ends`, the review says that what the save ends does not come back. Nothing is refused for an Interruption. What ends for each change:
  - Keyless API off: every keyless stream (`refreshStreams`).
  - A keyless scope removed: the keyless streams on a topic that needs it. The others narrow.
  - Public panels allowed off: every Public panel's keys (`endEveryPublicKey`). The line names each Public panel and its tablets open now (`mon.liveCount`).
  - Never sign out unticked: that user's persistent sessions, with their Session panel keys.
  - A PIN changed: that user's sessions and keys.
  - Panel pages lock on: the Session panel keys of users without a PIN (`endNoPinSessionKeys`).
  - A stepped-in user removed, renamed, re-PINned or lowered: their step-ins (`stepInStops`, `stepOutsOnSaveMu`, docs/agents/users-locks.md).
  - Ticking Never sign out ends nothing. `promoteTabs` turns the tab tokens that open pages hold into ordinary ones before `prune`. `pruneKeys` judges session keys by the new config. Each page lock turned on also gets a line. It counts the Guest browsers and browsers of users without a PIN on that page type. It names the users without a PIN. A lower Guest role and auto-lock going off get a line that ends nothing. Tests: interruptions_test.go (one per row, on a floor with one of each live thing), web/test/interruptionrules.test.mjs.
- Save sources, page side: Manage users stages its edits. Done closes the dialog and keeps them. They are unsaved changes of the Users section until the one Save, or until an exit discards them. The base is the usersList answer the dialog filled from; a later list fills it again only when nothing is staged. A saved field moves the base; a saved add gives the row its new id; a saved PIN clears the PIN box. The review names a removed user with the API clients that go with them (`clients` in usersList). The API section's inputs sit in the form; its base moves with a hello or list only while it holds no edits. Opening Settings resets every source.
- Swap (`internal/app/swap.go`, page `swap.js` with pure `swaprules.js`, GLOSSARY.md): numbers on the wire are internal (`Ref.N`). Filter set text holds shown numbers, so the server adds `numberOffset`. `swapList {swap: {side, from, mine}}` lists the items that use From (`swapItem`: id, kind, name, owner, broken). Everyone's list needs an Administrator. `mine` lists the user's own Me items and panels. The Administrator's Swap is the one Save key `swap` (section `routers`, so a Trusted user needs Approval). Only an Administrator sees Swap… on the Routers row. It is a save source, and Settings holds one staged Swap at a time. Only Broken also limits what is sent to the Broken items shown. Its fieldSpec has `action`: never unchanged, no version, and `savedFields` skips it. `planSave` makes the `swapper` once in `saveCtx` with the router's names. `set` changes presets and filter sets, and after the commit `swapPanelsAfter` writes the panels. Then the Settings saves row gets one field: "Swap destination 23 for 40" with the counts per owner as the new value. `swapMine` changes only the user's own items and saves at once. Like other My user changes it writes no Settings saves row. The ids only narrow what changes: the server checks use and owner again. A swapped reference takes the name at To, its Broken and Moved marks go, and a list that then holds To twice keeps one. Filter sets change number terms and exact terms (negated ones too) through the term spans of `filterTerms`. Contains, regex and range terms stay. Panels change cells, the Grid edge (members, hidden items, item settings) and fixed destinations. Tests: swap_test.go, web/test/swaprules.test.mjs.
- Apply an access preset (`accesspreset.js`, pure `accesspresetrules.js`, server `internal/app/accesspreset.go`): Administrator only, in Locks. The values come from `usersListResult.accessPresets`, built from `config.AccessPreset.Apply` (TestPresetSaveFieldsMatchApply), so the page keeps no copy. `api` carries only `guestEnabled`. Apply writes the form inputs, the API section (`stageKeyless`) and each ticked user's flags (`stageUserFlags` in users.js) as hand edits. Then `markPreset` in settingssave.js marks the rows that equal the preset's values. A mark goes when its row changes by hand. Marks show as a badge in the form and in the review. `settingsSave` sends `accessPreset` (the name) when a sent row is marked. The server puts it in the Settings saves row when a kept field is one that a preset writes. After a save with refusals, `presetGaps` against the moved baselines lists the fields that still differ and `gapText` says what each does now. Nothing is deleted: a preset writes only its fields and ticked users' Persistent and No auto-lock.
- Run setup again (`setupagain.js`, pure `setupagainrules.js`; `openAgain` and `closeAgain` in setupwizard.js): Administrator only, in Server. It opens the setup steps over Settings with no Add a first user, no custom border color and no Done. The values come from the form with its unsaved edits (`readSettings` and each save source). The preset is the one that the values match (`presetGaps` against `usersListResult.accessPresets`, which also carries the sheet's `rows`). If none matches, none is picked and Finish keeps the access fields. Nothing is sent before Finish: the Router step sends no `setupRouter`, and the status line shows only for the live address. Finish writes only the changed form fields (the Router salvo group only in Router salvo). It stages a newly picked preset with `stagePreset` (accesspreset.js) with no user ticked, then submits the form, so the one Save review opens. Esc and Cancel discard the answers, and the brand goes back to the saved one. The one Save does the recheck for the Critical rows. Nothing is deleted and no user changes.
- The `config` message keeps the same section rule: `trustedMayNotChange` refuses a Trusted user's change to a field of an Administrator section (`guardedErr`).
- Tie lines (Settings > Routers > Tie lines, section `tie-lines`, Administrator Hidden): `settingstielines.js` with pure `tielinerules.js`. The Hop weight (`tieHopWeight`) is a plain form field of the section and saves with the one Save. The tie line form (`#tielines-form`) is data-apart. Every change sends the whole list in the `tieLines` message (`SaveTieLines` in internal/app/tielines.go, Administrator under cfgMu), which broadcasts `{t: "tieLines", tieLines}`. Each end keeps its router name at save time (`nameTieLines`). The form fills the Tie line name from the source name until a person types another (`fillName`). `config.TieLineProblem` and `tieLineProblem` share web/test/tieline_cases.json. The list is not yet in the export (`exportNotSettings`).
- Inputs saved apart from the Settings form carry data-apart so the unsaved check skips them. emit('settingsClose',{discard:true}) closes Settings discarding the form.
