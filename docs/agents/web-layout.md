# Web layout: modules, keys, layouts

- Control heights (base.css): there are three, and one for the Confirm button. `--sode-h-field` (4rem) is the big patch boxes. `--sode-h-action` (2.5rem) is for anything used live: patching, panels, Take, chips and list rows that take a press. Nothing used live is lower. `--sode-h-compact` (2rem) is for toolbars and forms away from the patch flow. `--sode-h-confirm` (3rem) is only for the churning-letter Confirm button. On the desktop layout base.css sets patchbay's control sizes from them. A plain or small control is compact, a large one is an action and an icon button is square. A page part used live lifts its buttons to the action height with a `:where()` rule (`#patch-view` has one). Then a button with its own size keeps it. A History row is the press target and is an action high, so its buttons stay compact. The phone keeps patchbay's own sizes.
- Root size (base.css, top): html font-size is 100%, and 90% on a Grid panel page and its Live Editor. The Live Editor of a Grid panel gets it when it starts (`data-live="grid"` on `.sode-ed`, editorlive.js). Its grid comes after a fetch, and the Edit lists drawer must not move then. The phone is 100% on every page. On the desktop layout a window wider than 2400 px is a big screen with no OS scale. There `@media (min-width: 2400px)` adds 1px to the root for each 360 px over 2400: `min(125%, 100% + (100vw - 2400px) / 360)`. That is about 103% at 2560 px and 125% at 3840 px and wider. The Grid panel page grows the same way from 90%, to 112.5% (`/ 400`). At 2400 px there is no step. A 4K screen with an OS scale of 150% or more is 2560 CSS px wide or less. It changes little or not at all. Media queries use 16px rems, not the root, so no breakpoint moves. JS that changes rem to px reads the root's computed font size (editorrouterlist.js, lock.js). bigscroll.js measures its bars and needs no change.
- Main page width (base.css `--sode-main-w`): `.sode` is 75rem wide at most up to a 1920 px window. On a wider window it keeps 69rem of side space, so it is about 64% of a 3840 px window. Compact view and the side pad for the icon bar (desktop.css) use the same width. Help text and other running text keep their `ch` limits.
- Big scroll bars (bigscroll.js, rule in AGENTS.md): Firefox cannot set a scroll bar's width, and macOS overlay bars show only during a scroll. So Sode draws its own bar, a track and a thumb in a `.sode-bigscroll` div, 1.4rem wide (`--sode-bigscroll-w`). That is the big size, the default. The little size (`.sode-bigscroll--little`, `--sode-littlescroll-w`, 0.7rem) is for small secondary lists where a big bar hides the content. Use `{ size: 'little' }` in `bigScroll`, or a third `'little'` entry in `SCROLLERS`. The page's bar is always big. Little today: the History filter match lists (`.sode__search .sode__menu`), the sign-in name list (`.sode-namepick__list`), the filter sets row and the key lists in dialogs. The panel editor's Pages list (`.sode-pages__list`) is little too. Put a little entry before any broader big entry, since the first match wins. `[data-bigscroll]` on the scroller hides the native bar (base.css). The bar shows only while there is something to scroll. While it shows, the scroller gets padding for it, so the thumb never covers a row. Drag the thumb, or press the track to page (hold to repeat). A wheel over a sideways bar scrolls it sideways. Pointer events, so touch and pen work too. The bar has `aria-hidden` and no tab stop, because keys already scroll. pointerdown and mousedown on it keep focus, so an open match list stays open.
  - `bigScroll(el, axis, size, { watch })` draws one bar, or two for axis `'xy'`, and returns `{ update, now, stop, bar, room }`. The bar is the scroller's next sibling, placed over its inside edge. A static parent gets `.sode-bigscroll-host` (position: relative). The page's own scroller (`document.scrollingElement`) gets a fixed bar at the window's right edge. While it shows, html gets `data-bigscroll-on`. On the desktop layout html keeps the bar's room (`padding-right` and `--sode-page-bar`) while the bar is hidden too. So the page never moves sideways when the bar shows or goes. A Grid panel's Live Editor never scrolls, so it keeps the room only while the bar shows. Fixed items at the right edge use `--sode-page-bar` to keep clear of the bar (`#conn`, the pick bar, the Settings sections).
  - Axis `'xy'` (the Grid page) draws a bar on each axis, both big, and a `.sode-bigscroll__corner` square where they meet. Each bar is shorter by the other's thickness while the other shows. One layout pass decides both, since the side gutter can make the grid overflow across. `room()` gives `{ right, bottom }`, the px of the shown bars in the client box. A drawn bar is on the client box, but a native bar is outside it. gridpanelview.js takes it off `clientWidth` and `clientHeight` in `read()`, so the window maths, `cellAt`, `hit` and `bodyBox` stop at the bars. `now()` lays out at once; `setAxes` calls it before it sizes the pools, since a pool never shrinks. `watch` is an element whose size changes with the content. It replaces the subtree MutationObserver: on the Grid, crosspoint writes would run a layout each time. The Grid scroller has `isolation: isolate` on the desktop layout, so its sticky bands never paint over the bars. The bars are siblings of the scroller, so the Grid's own pointer and wheel listeners never get a press or a wheel on them.
  - `bigScrollAll()` runs on the main page (main.js), /log (log.js), /panels and the editor (panelpage.js), but not on a panel page. The Grid page calls `bigScroll` itself (gridpanelview.js). It draws the page's bar and one on each `SCROLLERS` match, also on ones added later. A bar goes when its scroller leaves the page. On the main page, `SCROLLERS` holds the match lists (`.sode__menu`), the Settings search results and sections, the Protects list (`.sode__plist`), and every dialog body. The router list of Settings > Routers (`.sode__rlist`) is not in it: it is a row of chips that wraps. It also holds the Tie lines table (`.sode__tlist`). It also holds the Currently and Sending lists, and the Grid popup's staged list (little). It also holds the Inbox and Sent lists (`.sode-inbox__list`) and the router list of the status bar (`.sode-routerlist`). It also holds the Presets list, the key list, the filter sets row, the Communication Log table and the Lock. It also holds the Levels box's picks (`.sode__box--levels .sode__levels`, sideways). They are the main control for levels, so their bar is big in a small box. The Lock does not make its own bar inert. In the editor, it holds the sidebar, the Pages list, the lists, the router lists, the icon lists, Find, Templates and the overview lists. It also holds the Artwork panel in the Live Editor's drawer. A new scroller that users need goes in that list.
  - After the bar is drawn, a scroll only changes the thumb's transform. No element is added or removed, so a MutationObserver on the content sees nothing. ResizeObserver (scroller, its parent, the body's children for the page) and a MutationObserver on the scroller's rows keep the size right. A sticky scroller also gets an update on each page scroll.
  - The phone layout keeps native bars (a touch screen scrolls the content). On the Grid page they are the thin styled bars in gridpanel.css. Geometry is in bigscrollrules.js (pure, node tests). `TestChromeBigScroll` checks it.

- Router state (core.js): `routerData(uid)` is the one accessor for one router's names, tally, Via rows, levels and link (`{ first, uid, prefix, title, off, levels, levelBy, numbering, defaultLevels, srcs, dsts, srcBy, dstBy, tally, via, namesAt, namesSavedAt, link, addr, err }`). Blank, the first router's UID or a UID that the hello did not list gives the first router. `S` has no fields of one router: read them only through `routerData`. The first router's state is one object that a hello fills in place, so tests set the fields of `routerData('')`. Its `off` reads the settings (`off()`). Every router comes from the hello's `routers` list and from the messages that carry `routerUid`. `S.routers` lists `{ uid, prefix, title }` of every router. An item of a router after the first has `router` and `prefix`. With two or more routers, an item of the first router has `prefix` too (no `router`). Its label and `numText` show the prefix (A.12, B.12), and `num` stays the number alone. So History rows, presets and every match show the prefix. The hello sets the routers before the first router's names for this. `srcItem`, `dstItem`, `tallyText`, `bySource` and `fedBy` take an optional router UID. `protectsOf(uid)` gives the Protects of one router (`prot`, `by`, `device`): the first router's are `S.prot` and `S.protBy`. The route view and the x key offer Protect on the router of the destination. `routerOfItem` gives the UID that a take sends (blank for the first router), and `sameEnd` compares number and router. Prefix typing (routerprefix.js, `typedPrefix`): a router prefix is one or two letters, then an optional dot, then digits (A.11, A11, BA.11, BA11). With one router only the dotted form counts, so A11 stays a name. Without the dot, letters that no router has are a name (TX1). `routerNamed` gives the router a text names (blank for the first router, null for none). `boxSearch(kind, text, { def, n, keep })` gives the matches of a patch box. A prefix with digits searches the numbers of that router, and those matches always come first. Without the dot, the name matches of the whole text come after them (B42 gives B.42, then "B42 MON"). A bare number searches `def`. Other text searches the names of every router, `def` first on a tie. Each desktop patch box has a default router for this browser (boxrouter.js, `localStorage` `sode-box-routers`, by router UID). A new browser, or a router that is gone, gives the first router. Its button is under the left side of the box (`#src-router`, `#dst-router`), level with Show all. It shows "Router B" and moves to the next router; it hides with one router. The Levels box does not name its router. A box's router (`routerOfBox` in desktop.js) is the one its text names, else its default router. `planBlocked` gives `tie` for a plan with routes across routers, which opens the Tie line picker (tieflow.js). Each item across routers must have one route, and the plan has no undo, retry, put-back or extra. Else it refuses the plan. It also refuses a plan whose router has no link. Levels belong to a router: levelview.js takes an optional router UID (`levelSource`, `parseLevels`, `levelText`, `levelBar`, `allLevels`, `oneLevel`). The desktop Levels box and the phone's Levels step parse against the router of the route's destination. That is `levelRouterOf` in levels.js, called by `lvlRouter` in desktop.js and mobile.js. Their picks follow it. On a router with one level, any typed levels mean level 1 (`parseLevelsIn`), and `levelBar` and the History notes say "All levels". Some parts of the panel pages are of the first router only (docs/agents/panels.md). The phone uses `boxSearch` too, with the first router as the default router: it has no default router button.

main.js wires modules then calls connect(). core.js is state/socket/bus (S, WebSocket, on/onFirst/emit/onMsg, el, fuzzy search, status helpers, nameProblem). It imports only tooltip.js, sprite.js, fuzzy.js and buildrules.js. The hello handler reloads the page when the build label differs from the first hello (buildChanged). prepaint.js runs first on every page: a browser without the `sode-format` stamp loses every `sode-*` key before anything reads one. It also sets the accent tokens from `sode-accent`, which brand.js writes (docs/color-roles.md, Accent). Imports must not form a cycle (test/imports.test.mjs checks this, and that every import exists). ESLint enforces the keys.js and core.js import lists, and bans DOM and storage globals in web/*rules.js. Modules reach handle() through events (helloCfg, helloData, wsclose, onMsg), so a page only gets them if it imports the module. Tests import everything through web/test/all.mjs.

- Icons: `icon()` in core.js makes `<use href="#pb-i-<name>">`, and sprite.js copies that one symbol from `lucide.svg` into a hidden `<svg>` in the page. Static markup writes the same local href and `adoptIcons` brings its symbols in. Never point a `<use>` at `lucide.svg#...`. For every such `<use>` made, Chrome loads and lays out its own copy of the 370 KB sprite. It frees that copy only at a major GC. A panel's tick icon grew the renderer from 0.4 to 4 GB in two minutes. `test/sprite.test.mjs` fails on one. A name that starts with `sode-` is read from `web/sodeicons.svg` instead (Sode-owned, owner-approved). `sode-grid` marks Grid panels and the Grid popup button. Buttons panels keep `layout-grid`. Add one only with the owner's approval. A `#pb-i-` href means nothing outside the page, so an icon serialised out (export, print) needs its symbol inline.
- Panel pages (`panelrun.js`) apply the socket's tally frames (`tallyRows` from core.js) to the last `GET /api/v1/tally` (`paneltally.js`). After a hello, until the socket closes, the 2 s poll leaves out `/tally`. A check reads it every 60 s. The 2 s poll of the small reads stays, since it finds a revoked key or a lost Sode API. A hello, a `protectedRows` or `names` event, or a Router link change starts a poll at once. If the 60 s check differs from the kept tally, the page reads the tally every 2 s until the next hello. A Hidden caller's tally leaves routes out, so for that caller a frame only starts a poll. With the socket down the page polls every 2 s, as before.
- Service worker (`sw.js`, served by `internal/app/sw.go`): it keeps the app shell. So a main page or panel page that the device opened also opens while Sode is down. When Sode serves the file, it fills in `BUILD` and `SHELL`. `BUILD` is the version label and a hash of every web file. `SHELL` is every .js, .css, .svg, .png and .woff2 file. On install the worker keeps `SHELL`; on activate it deletes the other builds' caches and keeps the address of each open page. A page (`/`, `/panels`, `/panels/editor`, `/panels/<id>`) is kept by its path without the query. A page or a shell file goes to Sode first, and a new ETag replaces the kept copy. With no answer, or a 5xx from a proxy, the kept copy answers. It never keeps `/api` (so `/api/v1`, PINs, tokens and session keys), the WebSocket (the hello), `healthz` or `sw.js`. The rules are top-level functions that `test/sw.test.mjs` runs in a vm.
  - The skipWaiting and reload rule: a new build's worker takes over at once (`skipWaiting`, `clients.claim`). A page that started online has its files from Sode, and the hello's build check reloads it when Sode changes. A page that started while Sode was down (its socket closed before the first hello) has the old build's files. At its first hello `swreg.js` asks for the worker again (`update()`), and a `controllerchange` reloads it, so it never runs with a newer Sode.
  - `swreg.js` registers it from main.js and panelpage.js, only on a secure origin (localhost, or HTTPS through the user's proxy; README). The main page's Offline state is the lost-link banner and the socket's own retries. A panel page waits in `waitForSode` (`panelwait.js`) before it opens: the Offline cover shows and `healthz` is asked every 2 s. The Live Editor does not wait. `TestChromeServiceWorkerOpensWithSodeDown` checks both pages; `TestServiceWorkerIsFilledIn` and `TestServiceWorkerBuildFollowsTheFiles` check the served file.
- Socket freshness (#142): core.js keeps ws.lastRx (set on open and each message; test stub sockets need it). A 1s check drops an open socket silent for 15s; wsSend refuses one silent for 7s; drop(ws) reports at once and the page reconnects. sendTakes shows Not sent when wsSend returns false.

- desktop.js and mobile.js are the two layouts. layout.js picks: auto on narrow touch screens, per-browser override; index.html applies the same rule before first paint. desktop.js splits into desktophistory.js (History rows, pager, keyboard mode; owns that state) and desktopkeys.js (the document keydown handler). Factories that get desktop.js's hooks build both, and neither imports desktop.js. Phone: one input stepping Source, Destination, Levels; summary pinned at top; match list floating; number pad for Levels.
- Compact view (pref compact): html[data-compact] (prepaint.js, then device.js) and the desktop.css Compact view rules, desktop only. They hide #patch-view's History and make .sode a viewport-high grid with place-content:center. Then compactcentre.js nudges #patch-view so the patch row (the three groups, Source to Clear) is at the viewport's centre. The nudge is relative left/top from --sode-centre-x/y (centreNudge in compactrules.js, clamped to the viewport). The nudge is active only while that grid is. The rules also put #result out of flow below Presets, so a result never moves the boxes (the match lists already are out of flow). They shrink Presets and centre them under the boxes. All of that gives way while a preset picks takes from History (data-sode-pick=""). The Lock bar's bar and #conn fade with opacity over --sode-motion-reveal (250ms, 0 under reduced motion). They never fade with visibility, so hover and :focus-within still reach them. #conn fades only while it has sode__conn--ok, set by renderConn from connState().ok (both links up), never by prepaint. Each has a transparent ::before apron (6rem toward the middle, out to the viewport edges) so a pointer near the corner reveals it. The apron must stay off the patch boxes, Take and Presets, which TestChromeMainCompact checks. historyShown() in desktophistory.js mirrors that rule. While it is false, keyboard mode never starts (Esc with empty boxes does nothing, keys on the page body skip onListKey). When it turns on, focus moves out of History to Source. Alt+Shift+C writes the opposite of the resolved value to This browser, never '' (with Everyone on, '' would change nothing). It is chord 'alt+shift+c' in desktopkeys.js and works from any focus, including a box. preventDefault stops macOS Option+Shift+C from typing Ç. test/compact.test.mjs fails if another module binds it or the ? list shows it twice.
- Level picks on the desktop main page are small squares, 1.375rem (`--sode-pick-w` in desktop.css), always in two rows. levelbox.js sets the columns as `--sode-bar-cols`. The patch row is three groups of one width (desktop.css `.sode__boxes`): Source, Destination with + (`.sode__group--dst`), and Levels with Take and Clear (`.sode__group--levels`). An empty grid track gives the Levels group its wider gap. levelview.js sets `data-levels` (`on` or `off`) on `.sode__boxes` on each hello, and the CSS for a hidden Levels box reads it. The Levels text box is beside Take and Clear, and the picks go under all three (subgrid). Thus from 850 to 1600 px the picks show 9 columns (17 levels) and Select All. Below about 1100 px the Levels group keeps the room of its controls and is wider than the other two. More columns, or a narrower box, scroll sideways inside the picks with a big scroll bar. They show only whole columns (`round(down, …)` against the picker, a size container). They never wrap into a tall stack. Select All is two rows high and always beside the picks, in the same place. Only an odd number of levels makes the first pick two rows high (`sode__levels--odd`, base.css); with an even number every pick is a square. Compact view keeps the page width, so the boxes keep their width. `TestChromeMainBoxesLayout` and `TestChromeMainCompact` check 4, 5, 11, 12 and 17 levels (no scroll) and 24 (scroll).
- Level clicks (levelbox.js): a pick click while every level is on selects only that level, as typing "2" does. Further clicks add or remove a level, also after they add up to every level again (`picking`). Select All, typed text, a clear or a fill from outside (`set`) start over. The panel editor's level subset (editorlevels.js) is a setting, not a take, and keeps plain toggles.
- The take Confirm (`#confirm`, the main page and a Grid panel page) has a fixed top (12vh) and width (46rem). So it never moves as the plan changes, and a long plan scrolls in its body. Every churning-letter Confirm button ("Take (X)", "Delete (X)", "Confirm (X)": keyconfirm.js, confirmbox.js, editorlib.js) has the class `sode__confirm-ok`. It has one height on every page: `--sode-h-confirm` (3rem), between the action height and the main Take. The letter itself (`.sode__key`) has one size and look everywhere, the Lock too.
- One Take's Confirm (gridpopup.js marks the boxes' route `box`, gridPlan makes a `mixed` plan): the question names each destination. The boxes' route shows first under "Patch boxes", then the staged routes under "Staged routes", each with a Staged badge (text, not color only). A destination in both shows in both parts.
- Tie line picker (GLOSSARY.md, docs/tielines-design.md; `tiepicker.js`, rules in `tiepickrules.js`, CSS in `tiepicker.css`): when `planBlocked` gives `tie`, `openConfirm` (desktop.js) and the phone's sheet (mobileconfirm.js) call `tieTake`. It is in tieflow.js, with rules in `tietakerules.js`. It asks one question for each hop that the tie routes share (`nextQuestion`), and opens the picker (`pickRoute`) for each question. A hop is shared when the routes have the same source, levels, choices before it and routers of the hop. A preset's or a Redo's stored tie line for that hop is part of it too. The heading names the hop and its destinations ("A → B, for B.1 B.2 B.3", `questionHead`). When every route of a question ends on one router, the question goes on to the destination. Else it is one hop. Then `fitQuestion` sets `from`, `to` and `only` on the state. The picker shows those steps only (`shownSteps`), and the choices of the hop go to router `only`. The picker shows the plan of the first route of the question (`at`) and the destinations of each one (`members`). "Choose per destination" (`#tiepick-split`, D) gives each destination of the hop its own question (`f.split`). A take with other routes has Clear this route (`#tiepick-clear`), which clears every route of the question ("Clear these routes"). The picker only chooses; tieflow.js sends. A take with a plain route then opens the confirm with each route that stays (`keptItems`). The `confirm` option gives the desktop `keyConfirm` or the phone's sheet. A tie item has `via`, and the confirm marks it "via TIE 1". Its plan has `send`, which `sendTakes` calls in place of the `take` message. In a take of tie routes only, the last question's Take sends (`finalAt`); the others say Next. If its routes are cleared, the confirm comes after all. The take is one `tieTake` with every route (`takeRequest`). Each question plans every route (`planRequest`). First come the plain routes, then the tie routes with a path in the order that they got it (`seq`). The open tie routes with no ties come last. An open route sends `through` with the tie lines that an earlier question chose for it, so its plan holds the paths through them. The take keeps that order, so the stale check sees the plan that the person saw. The server counts the other routes (`planTieRoutes`). The first route of a question gets its pick from the picker. Each other route whose choice reaches its destination gets its pick from one more plan through the chosen tie lines (`answerQuestion`). A route that the choice leaves halfway keeps `{ ids }` and gets a later question. Two destinations with one source share a tie line. A tie line that another route uses for a different source is `taken`. A `tiePlan` is the same plan as a `tieTake` with no ties, with no take and no Communication Log row. The 409 `tie_line_needed` body gives the ranked paths, and the picker opens on them. On `no_path` the picker opens too, with each reason by name (`reasonText`) in a `pb-alert--error`, and Take stays off. Other refusals (`tie_lines_off`) show as a result banner. The page never computes paths. `tiepickrules.js` is pure. A step is a hop that feeds a tie line. The choices of a step are the tie lines of the paths that agree with the steps before it. A choice stands for its best path: the first usable one, else the first. Thus a change on a step gives the later steps of that path. A hop that sends to a Protected tie line is grey (`held`). J and K skip it. A tap shows it, but Take stays off. A tie line Reserved by a panel is not held: it says "Reserved by panel X" and sorts with the Protected ones (the server ranks it so). Take on a path that sends to one asks one more time (`reserveAsk`). The first Take shows a `pb-alert--warn` (`reserveText`) and starts the lockout again, and the next Take sends. `reserveOk` keeps the key of the path that the person confirmed, so another path asks again. Keys (`keyStep`, by `chord`): J, K or the arrows choose, H, L, Tab or Shift+Tab move between steps, Enter sends, Esc cancels. The keys go to the dialog before `trapDialog`, so Tab moves between steps. A tap on a choice or its wire chooses it. The focus stays on the dialog. Take (`pb-btn--commit`) waits for the lockout (lockout.js). The last change timer ticks each second and stops on close. The take sends `ties` with `expect` from what each hop showed (`expectOf`), and `affected`. The answer shows as a result banner ("Success" or "Take failed" with each failed route). A 409 `conflict` shows its message. Live update: some bus events can change the plan (`tally`, `protectedRows`, `protectedOther` for a router after the first, `conn`, `tieLines`). While the picker is open, each burst of them asks `tiePlan` again (`REPLAN_MS`). `refresh` keeps the selection on the path with the same tie lines (`pathKey`). It never moves it by itself. A path that the new plan leaves out stays as a `gone` path, grey, and Take stays off. A change of the cost, the Protect state or a hop of the chosen path (`pathChanges`) starts the lockout again and marks the row. A path that comes into a picker with no usable path turns Take on, and that starts the lockout again too. The mark is a `pb-badge--warn` "Changed" on the tie line, the destination or the Affected destinations. A new Affected destination gets "New". The server keeps nothing for an open picker. - Palette (GLOSSARY.md): palette.js is the dialog and its keys, on every page (main.js, log.js, panelpage.js). The rows come from the catalogue in palettecatalogue.js (pure; its header documents `catalogue(src)` and the Row shape). Bookmarks reuse that catalogue and the row keys (`<kind>:<target>`). paletterules.js (pure) holds the Palette character check, the last picks, the lists and the ranking. `paletteView` drops every grey row (outside the Rights or Role) that is not a Palette pin. The empty top is Home, Pinned, Last picks without the pins, then Categories. Pinned lists the pins in their saved order (`pinRows`). When the settings and panels are read, a pin whose row is gone is a grey Missing row. A pin ranks as any row in a typed query. Alt+arrows on a pinned row, or a drag in the Pinned section, put the pins in order (`movePin`). `rankMatches` puts a grey mark after every usable row, and `firstIndex` starts the cursor on a usable row. Tests: also web/test/paletterank.test.mjs, `TestChromePaletteFocus`. Look: no title (the header is `pb-sr-only`, so the dialog keeps its name). It is `min(60vw, 60rem)` wide with a list up to 70vh. On the desktop a row has fixed columns: icon, name, where, status and the ⋯ button. The ⋯ menu (palettemenu.js) has Pin or Unpin (Alt+P) and Bookmark or Remove bookmark (Alt+B). Each item has an icon, text and key. The keys work without the menu, and the note line says what changed and where. The key hint is short, in kbd. It shows only the keys that do something on the item under the cursor and at that level (`footKeys` in palettehints.js). ⇧Enter shows only on a preset or a filter set, and Esc says clear, back or close. The ⋯ button's tip is a tooltip.js floating tip, since a CSS tip under the last row made the list scroll. Tests: web/test/palette.test.mjs, web/test/palettematch.test.mjs, `TestChromePaletteMain`, `TestChromePalettePanelPage`, `TestChromePaletteHiddenMatches`, `TestChromePalettePins`.
  - Search: `match` gives each row a strength (`STRENGTH`). From the best: the full label, the label start, a whole word, a word start, and every query word as a word start. Then text inside a word, the hint, and last a loose match: the letters in order, from a word start. Marks in a label do not count ("reread" finds Re-read). The words of an action, a page or a setting count almost as the label. The words of a panel, preset or filter set are only the category word, so they count less. The hint counts only at a word start. A category boost (`CAT_BOOST`) adds more than one strength step: panels, presets and filter sets most, then pages and actions, settings none. Thus "theme" is the theme action before the Theme setting, and a close match of a name that a person gave wins.
  - Weak rows: a loose match and a danger row are weak. A danger row (`isDanger`) is a `danger` button of the catalogue, such as Clear History. A label that starts with Clear, Delete, Remove or Reset is one too. `rankMatches` puts them after every other row, and `paletteView` lists them under "Other matches" with `weak: true`. `firstIndex` never starts on a weak row, so with only weak rows no row is picked and Enter does nothing.
  - Twin settings: most preferences are in This browser and again in Everyone's defaults. A search lists only the This browser row (`dropTwins`), and the Everyone's defaults section still lists its rows. The my default buttons have a search name with their setting ("Save Theme as my default", devicesettings.js), so the Palette and Settings search show different rows. A save emits the bus event `myDefaultDone`, and palettehome.js shows a result banner for a button that a row pressed. The theme and Compact view actions show a result banner too.
  - Empty box: Enter picks nothing (`firstIndex` with `empty`), unless the first item is a category or a Settings section. So Enter never fires a bookmarked preset. Backspace in an empty box goes up one level, and does nothing at the top (`emptyBackspace`). Only Esc closes the Palette.
  - Keys: Tab and Shift+Tab step the cursor, and the focus stays in the box (`keyMove`; the handler stops the dialog's Tab trap). PageUp and PageDown jump the rows that the list shows. Ctrl+Home and Ctrl+End go to the first and the last row. Plain Home and End stay text keys.
  - Focus: a close always gives the focus back (`giveBack` in palette.js). It goes to the element that had it before the Palette opened, else to Source on Home. A row runs after that, so a dialog or a field that it opens takes the focus. Then a watch puts the focus back when it drops to body and no dialog or Lock is open. This occurs after a Confirm or the Lock closes. The watch stops after it puts the focus back, or at a pointer press or a key outside a dialog. It also stops at the next open and after 10 minutes. A key that reaches body puts the focus back first, so the key reaches the box.
  - Home: the catalogue has Home on every page. On Home it has `here` and `home`, and it emits `homeKey`, as the Home key does. The empty Palette lists it only on the other pages.
  - Category word: `paletteScope` reads the first word of the query. `guessCategories` matches it against each category's `names` (CATEGORIES). A match is a prefix, or one typo (Damerau, 4 letters or more). The letters in order with the same first letter match too, when no vowel comes after the first letter (pnl, stg, but not "sing"). The `short` words (p, pre, ps, pg, a, act, f, fs, s, set, cfg) win at once, so one letter has one meaning. A tie (pa: pages or panels) does not scope: the word alone lists the rows of both first. A name of a panel, preset or filter set in a different category can start with the whole query. Then there is no scope (a preset "P 1" for "p 1"). The scope is a soft one. A word alone puts the category itself first, so Enter opens it. A row of a different category with the word as its full label comes next (the Settings page for "settings"), then the category's rows. With more text, the category's rows that match the rest come first. Then "Other matches" for the whole query. When the category has no match, the list says "No match in <category>" and shows every match. The line above the list shows "<category> first". There is no chip: the text stays as typed, so Backspace edits it as usual.
